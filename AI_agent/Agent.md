# 每次会话的项目初始上下文

Codex、Claude 及其他开发助手共用本文件。用户当前指令优先，所有项目管理与交互记录放在 `AI_agent/`，不在仓库根另建管理文件。

## 开始会话

完整阅读本文、[产品目标](project/goal.md)、[当前任务](project/roadmap.md) 和 [工作方式](workflow/development.md)，再打开“当前任务”的“当前交接”指定的最新一份收工/交接记录（若有），然后按任务读取源码与相关设计。其余资料从 [总目录](README.md) 查找，不以通读历史日志作为开工条件。
检查 `git status --short --branch`、`git worktree list` 和近期提交。会话加载方法见 [设置](workflow/session_setup.md)。

## 目标与开发取向

- 最终开发一套统一的 Agent，产出可查看、可修改、可用于后续分析的轻量 BIM。还原建模、部分推理建模、完全推理建模按信息充分程度命名，仅作研发分工与评价分类，不拆成独立产品或长期管线。09-25 用户确认 Astra 与 Opus 5.5 均为最高档开发负责人，各自按需选派子代理；模型家族不绑定路线，由 Astra 根据进度统筹工作包，用户统一与 Astra 沟通。各工作包共用总 Agent、源 BIM 和工具底座，具体分工见 [当前任务](project/roadmap.md)。
- 当前关键目标是在有限模型智力下稳定生成相对精准的丐版 BIM。时间不是当前关键约束，耗时优化后置，prescan 等可随后按需考虑；不以抢早首稿主导排期。见[当前优先级](project/goal.md#当前优先级09-14-收工确认)。
- 当前只做目标单体，不考虑环境。用户生成前决定通用 BIM 对实际建筑空间的简化/合并程度，再选后端模拟。分块以实体隔墙为依据，最细保留实际空间，大开敞办公区不能因朝向或复杂度增加而被细分；低档可直接推断合并后的表达，无需先推全楼。物理/抽象边界仍区分，但抽象边界不授权凭空拆空间。输入信息量、源简化与后端热区合并独立；档数、控件和对应关系后续详细设计，办公楼仅为理解示例。
- 产品形态是模型驱动的总 Agent：根据目标、输入和工具反馈组织任务，按需调用代码工具、模型工具及专门能力。确定性几何操作可封装固定步骤，整案不写死为唯一流程；架构取舍与复杂度由开发助手总体把控，见 [系统设计](design/architecture.md)。
- 定性大于定量：先保房间、外形、楼层、门窗和空间关系正确、几何自洽可用。图纸/CAD/GT 的细小偏差允许有记录的容差规整；judge + GT 用于自动判断效果、减少人工逐项核对，不以逐点吻合或 GT 精修为主线。具体边界见 [验证与评价](design/evaluation.md)。
- 源分区保真优先于尺寸微差：漏墙、多墙、错误拆房/并房、假楼板和连通改变属于严重问题。计算切片/热区拆并只能是显式派生，不能变成源 BIM 的物理隔断；EP 跑通或历史 judge 放行不证明源模型正确。
- 我方主线是几何，物性由协作者负责；EnergyPlus 是首个下游。保留源房间、隔断、门窗和空间关系，仿真热区从源模型派生。
- 信息不足可用明确标注的推断、默认值和简化。不能静默丢房间/窗或掩盖失败，不能把推断当实测。
- 09-27用户补充：房间类型原则上尽量选择合理类别、尽量不标未知，允许依据建筑语境/家具作推断并供用户后续调整。丐版BIM不追求用途细类的高精度，避免完全离谱的错配即可；类型歧义不应主导复核或阻塞交付。具体几何、门窗和连接的要求不随之降低。
- 先取得真实 case 的可查看输出，再改善下游连通和质量。现有代码与工具按用途复用或替换；毫米级复刻、全实体墙、完整治理和旧债清零均非普遍前置。
- 09-28 用户最终澄清：主力朝 Qwen 27B 这种可本地部署级模型发展；Flash 工作档对标 Sonnet，更看重速度和低消耗，成本优先并衡量 token，不设严格智力上限、允许同档能力随时间提升，也不按名字筛选。产品支持用户自接模型及服务器多模型配置/调度，不能只在一种组合上做好；降低能力依赖、提速、降本逐步实现，视觉/OCR/检索等按需纳入。旧 Sonnet 硬上限不再用于排除本档候选。见 [模型与费用](workflow/models.md) 与 [配置设计](design/model_configuration.md)。
- 生产模型目标档从首批实验参与，按上述最新档位与任务质量/成本目标选型；开发派工前读取 [模型与费用](workflow/models.md)，按最新子代理分配偏好选择，不直接沿用主助手型号。
- 09-28 最新排期及再次确认：保留有效开发成果，先让 Sonnet 级工作模型配合现有工具把整案做顺、做稳并恢复出模质量；之后逐步把部分任务拆给其他模型，每次核质量保持与成本/速度收益。当前不把多角色/API入口接入与质量修复混在同一能力包。此前三例各两次较好结果均为单 Sonnet、无局部子模型参与。已有可选委派工具和角色配置雏形不等于已验证的分工方案；按功能角色组织、型号可替换仍是后续方向。
- 09-28 用户进一步决定：本轮质量基线恢复后，后续不再使用Claude作为工作模型，避免反复等待额度。恢复阶段顺序保持；恢复后先迁移到非Claude工作模型并核质量保持，再逐步拆角色/降低能力依赖。按功能角色配置、27B本地主力与低成本Flash辅助方向保持；不把该决定当作立即换模、补跑或新增实验的批准。具体安排见[模型与费用](workflow/models.md)。

- 09-28 用户补充授权：若当前修复耗时过长，可从旧基线开始逐步加回能力包，由主助手综合判断；保留当前有效成果，不把旧版本自动当成已恢复的稳定基线。用户另明确安排Opus 5.5最高思考档独立调查质量退步，属于开发调查，不改变产品先单Sonnet的顺序。

## 权限与执行

- Codex 主助手可直接设计、修改、验证和提交，包括核心代码；用户已将 Claude 的开发任务与权限范围交由主助手管理。主助手决定派工、可修改文件/共享接口、验收、返工和合并时机；Claude 在获派范围内开发、验证和提交，扩大范围先与主助手协调，不自行合入 main 或推送 main。保持一条 main，并行使用主助手安排的短期工作树；具体约定见 [工作方式](workflow/development.md#统一统筹与开发协作09-25确认)。
- **Claude、GLM 现有订阅调用与派工已获授权，无需逐次确认。DeepSeek 的任何调用必须先获用户对本次任务/批次的明确同意**，主助手、子代理、管线、探测、重试与自动回退均适用。普通任务授权、旧记录或已有凭据不代替该许可；订阅授权不自动扩展到付费 API。
- 本项目 Git 备份、tag、分支/worktree 整理、commit 和正常 push 已全权授权。保留可回退的小提交，不强推共享历史，不丢弃未知改动。
- 验证按影响选择，复用同代码同范围的有效结果；不强制跨模型复审、每步全量或逐锁清债。代码里仍生效的检查需查明后再改，不能靠改文档宣称已取消。
- 09-27 用户新增约定：完整开发改动节点应安排回归，由主助手判断触发时机、准备具体范围并主动提请，用户拍板后执行。常规离线局部检查继续随开发进行；既有订阅授权不代替节点回归的批准。见[节点回归](workflow/development.md#节点回归09-27用户确认)。
- 09-28 用户将开发推进与质量回退的节奏判断、范围把控和主动提醒交给主助手：按完整能力包组织相关改动，允许包内有界波动，不让未解释的严重回退跨多个无关工作包累积；发现退步不自动等于停工或回滚。见[能力包与回归节奏](workflow/development.md#能力包与回归节奏09-28用户确认)。
- 09-28 续谈采纳用户建议：开发测试重点追踪实际行为/步骤与结果质量的对应，定位证据、对象解释、执行或复核哪里失效；代码差异用于追溯。看图/工具次数和自我确认不代替效果，也不固化唯一成功顺序。见[行为与质量](workflow/development.md#用实际行为解释质量09-28续谈)。
- 09-28 收工确认：主助手把控推进，针对已证失效加强对象覆盖、单位/坐标落值与返工后实际变化的约束；必要时可请Opus讨论，及时反馈，不陷入局部修复。若局部改动不能改善整案，重新判断假设和范围，保留旧基线逐包加回的选项；不靠堆提醒或反复抽样宣称恢复。见[能力包与回归节奏](workflow/development.md#能力包与回归节奏09-28用户确认)。
- 几何计算、变换、切配和装配优先用确定性代码。失败先复用已有产物定位阶段，再做最短验证；新实验独立 run，不覆盖原始输入和旧结果。
- GT 留在评测侧。人工辅助、旧观测重放与冷启动生成分别报告，单测通过不等于整案完成。普通测试离线，凭据和私有配置不入 Git。
- 正常技术选择自行推进；遇到无法安全保留的冲突、无法判定的产品矛盾或新的外部权限障碍，说明具体问题后确认。

## 项目记忆与收工

Codex 主助手统一维护项目文档与交接；Claude 保存获派任务的执行证据，并将结论、变更、验证和未决项交回主助手，不独立改写全局目标、路线或当前交接。所有助手的项目记忆由主助手同次同步到仓库对应文档：目标归 `project/`，设计/实现结论归 `design/`，操作约定归 `workflow/`，执行证据归 `logs/`。本地 memory 只留索引，不能独存项目事实或用户要求。收工和切模型前检查遗漏，敏感内容除外。
用中文先说明结果、影响和建议，尽量用白话讲明白，不堆砌技术术语、变量名或内部任务代号；必要术语要解释它对用户意味着什么。每完成一个大节点，主动汇报这一程做成了什么、带来什么变化、还有什么未完成。每轮由 Codex 主助手统一收工：用户说“收工”即按 [工作方式](workflow/development.md) 汇总全部获派任务及未完成状态，更新文档与交接、核对验证/diff、commit/push、收回完成的临时树，并总结本轮会话的全部工作；不重复全量，也不再问是否做 Git。
