这套体系管理目标、任务、实现事实与证据，让任何助手从仓库接续工作。当前协作入口是 [Agent.md](Agent.md)。

## 一项工作怎样推进

1. 在计划中写清本次要得到的结果和完成依据。小任务一行即可；只有任务够复杂才另开提案。
2. 查看相关源码和已有产物，选择最小可交付改动。历史缺陷只在影响本次目标时转为任务。
3. 实现并做相称验证。失败留下阶段、输入、错误与下一步，能独立交付的部分照常提交。
4. 把实现结论更新到相应技术文档，把本轮经过与证据写入工作记录，再从计划移走已完成的过程叙述。
5. Git 提交/推送后汇报结果和未完成范围；用户说收工时按手册执行全部交接动作。

计划使用“进行中、下一步、阻塞、待后续”即可。阻塞写具体原因和解开条件，不以旧批次编号或“等全量/等复审”代替事实。提案是建议；纳入计划才是当前任务，写下设计不等于已实现。

## 证据与记忆

实验记录至少让后来者能定位代码版本、输入/命令、模型与人工参与、产物、实际结果和未验证范围。可直接复用现有 run README，不为同一次实验重复建多份报告。
项目工作记录放 `AI_agent/logs/worklog/`；诊断材料放 `AI_agent/logs/experiments/`；运行产物沿用 `case_tests/` 等既有目录。重要证据不只保存在 `/tmp`。

所有模型的项目记忆必须先同步到上述对应文档。本地 memory 只引用它们，不维护副本；发现独存的旧记忆时补档，区分有效约定、过期事实和未验证线索。

## 精简与历史兼容

已完成的逐日叙述移入日志；被替代的方案保留原文到归档。没有持续用途的当前文件可删除；被源码或历史记录引用的路径只留短跳转页，注明“历史入口”，不继续承载规则。
归档不生成待办，不要求逐项补审。历史产物保留原样，目录 README 负责说明其时效。不要为了文档整理修改 GT、运行结果或业务行为。
文档出现第二份状态或规则时直接合并，不靠不断添加“新规则覆盖旧规则”的横幅维持。无需字数检查器、收工测试锁或新的管理平台。
