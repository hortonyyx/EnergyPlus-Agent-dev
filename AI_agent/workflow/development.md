# 开发、文档维护与收工

共同权限见 [Agent.md](../Agent.md)。本页说明从一个问题到可交付结果的工作方法。

## 推进一项任务

1. **每个助手聚焦获派工作包，由 Codex 主助手统筹并行。** 还原建模和部分推理是同一 Agent 的研发分工，可在同一轮分别推进；共用入口、源模型与工具能力，不按开发助手划分产品架构。
2. 主助手在 [当前任务](../project/roadmap.md) 明确本次结果、负责人、输入和完成依据，小任务一行即可。需要设计取舍才补设计正文。
3. 查看相关源码、原始输入和已有产物，定位信息在哪一层丢失或改变。先选最短可交付改动，不恢复全部历史批次。
4. 复用已有工具与确定性内核；模型负责感知、语义和信息不足时的判断。改完检查实际输出及适用边界。
5. 按影响验证，记录结果与未覆盖范围。失败说明具体阶段和下一步，可独立交付的部分照常提交。
6. 执行助手保存证据并提交任务成果；主助手决定集成，统一更新设计/操作说明、交接和正常 commit/push，汇报变化、证据和遗留。

对用户尽量讲白话，先讲结果和影响，再给必要依据，不堆内部代号、变量名和技术术语。每完成一个大节点，主动汇报从上一节点到现在做成了什么、怎么确认有效、还有什么没解决；进度简报不代替节点汇报。用户说“收工”时，总结本轮会话的全部工作，不能只报最后一个小改动或最后一次提交。

现有约束如果不适合目标，先弄清实际消费者，再修改并验证。不能只靠放宽检查、增加 accepted 数或合法 JSON 声称模型变好。

## 验证怎样选择

| 改动 | 通常需要什么 |
|---|---|
| 文档、索引或引用路径 | diff、链接、受影响路径/启动入口；无需 pytest 全量 |
| 单模块行为 | 相关行为检查，必要时补实际缺陷回归 |
| 相邻阶段接口 | 相关测试与一次真实产物贯通 |
| 广泛内核或依赖 | 先局部检查，再按影响决定一次全量 |
| 模型实验 | 独立 run，保留配置、人工参与、输出、质量/费用/耗时 |

同代码同范围的有效验证可以复用，换助手或收工不重复全量。不为可逆小改加测试锁，不规定每轮必须多模型复审。
测试采用现有环境的 `python -m pytest`；局部测试显式选择较少 worker，避免默认 `-n auto` 过量并发。普通测试离线；模型调用及派工遵守 [模型与费用](models.md)，DeepSeek 专项许可不能由跑 case 的一般授权替代。
观察到的改进先在问题样本成立，再按具体不确定性选另一个代表输入；不把单次高分或人工修补当普遍能力。评价细则见 [验证与评价](../design/evaluation.md)。

当前研发优先级按[09-14收工确认](../project/goal.md#当前优先级09-14-收工确认)：先验证有限模型智力下的准确性与稳定生成，时间优化后置。实验时限按质量验证所需工作合理配置，不机械沿用历史短时限或以抢早首稿为目的；记录耗时不等于本轮要优化耗时。

## 节点回归（09-27用户确认）

完整开发改动节点需要安排回归；主助手负责判断何时到达值得回归的节点并主动提出，用户决定是否执行。不要等用户发现退步才提，也不要每个小提交都跑整案。

- 连贯功能/修复完成，尤其影响读图指引、工具输入输出、源几何、装配或交付行为时，主助手评估受影响的旧能力；多个相关小改合成一次节点回归。发现已有退步或局部检查不能解释的行为变化，也应提出有界对照。
- 提请前完成可以离线完成的定位、实现、局部检查和实验准备，说明本节点改动、触发原因、拟跑案例/对照/次数、模型与时限、验收口径及未覆盖范围，让用户批准具体方案。
- 用户批准后按该范围运行；不擅自扩大案例、次数或开启下一批。用户已明确批准的批次无需逐次询问，单纯“继续开发”和历史订阅授权不视为新增节点回归许可。
- 分批运行时，上一批结束后先读取真实模型回执，再在独立工具步骤中启动下一批；外层实验脚本退出0不代表模型调用成功。出现429/额度限制时保存中断，不让同一编排脚本在回执检查失败后继续发起后续调用。09-27 run77/78零token拒绝暴露了这一执行失误，见[收工记录](../logs/worklog/2026-09-27_reconstruction_use_guidance_close.md)。
- 开发中的定向单测、语法/接口检查、已有产物的确定性重放仍按影响自行开展。涉及真实模型调用的本轮退步对照归入提请范围，不以“诊断实验”绕过用户决定。
- 节点记录区分“局部检查通过”“回归待用户决定”“已批准/已执行的范围及结果”；回归未执行或未通过时，不宣称能力已恢复。完整整案评价继续检查房间/隔墙/门窗/连接、高度和可查看交付，不以用途覆盖率代替几何质量。

节点回归用于在稳定质量下持续推进；旧版本仅为对照。开发助手同时说明本节点新增能力的实际收益和既有能力的变化，保留逐次失败/中断/未评项，并区分尺寸差异与实质空间/连接错误。已有结果可先用[离线BIM节点报告](../design/evaluation.md#持续推进与质量波动09-27)汇总，不以一次分数或未触发的功能实验决定回退。工具报告不新增审批环节或自动验收门槛。

## 能力包与回归节奏（09-28用户确认）

用户担心逐改整案测试会妨碍多项改动协同，也担心长时间不验证会积累无法定位的回退；明确由主助手负责判断、把控并主动提醒。原则是**允许有界的短期质量波动，限制未验证改动累积**。观察到退步与决定停止开发分开，不因单次坏结果立即停工或回滚，也不以波动为由忽略持续退步。

以完整能力包作为推进和评价单位。开始时说明预期能力、关联改动及协同理由、需保住的已有能力、下一次评价边界；例如 A 引入新能力、B 约束其不稳定性，可以一起完成后验证。包内离线检查照常进行，不能不断追加 C/D 来推迟原定评价。能力包是研发安排，不固化产品运行流水线，也不新增一套准入清单。

| 工作阶段 | 主助手负责的判断与动作 |
|---|---|
| 包内小改 | 按影响做接口、确定性检查和已有失败轨迹重放；通常不逐提交调用整案模型 |
| 能力包闭合，或关键假设发生变化 | 判断是否需要代表性真实整案，先准备明确范围；同时验证新增能力实际采用及已有能力变化 |
| 准备采用新能力基线 | 按影响选择跨例与必要重复，预先确定条件并保留全部结果；不能以一轮最好结果替换旧对照 |

结果按具体影响处理：细小尺寸波动单列记录；漏实体隔墙、错拆错并、错接等实质错误优先收敛。同类严重失败反复出现、工作包扩展到无关功能、原定评价边界被推迟，或关键假设改变而旧证据失效时，主助手主动提醒，说明证据、未验证范围和建议的下一步；必要时暂停无关扩展。**短期回退可留在一个有明确闭合点的能力包内，不把未解释的严重回退带过多个无关工作包。**

已采用基线与开发中状态分别记录在同一 main 的提交/run 中，保留可回退证据，不为此建立长期双分支或双架构。每个节点分别汇报“功能实现及实际收益”和“整案质量是否恢复”，两者不能互相替代。模型批次执行仍遵守上节已确认的范围；这里补充主助手持续判断和提醒的责任，不增加审批环节，也不授权自动反复抽样直到通过。

09-28 收工时用户再次交由主助手把控推进，允许必要时请Opus讨论，要求及时反馈、避免陷入局部问题。局部修复反复不能改善整案、证据推翻原假设或方案取舍超出当前包时，先汇报已知和未决，重新判断修复入口与范围；可围绕明确问题请Opus独立讨论，并保留从旧基线逐包加回的选项。讨论不要求每步发生，也不替代实际验证；不得以扩大补丁、增加提醒或重复整案抽样掩盖停滞。恢复质量后停止使用Claude工作模型的决定不禁止必要的Opus开发讨论。

### 用实际行为解释质量（09-28续谈）

用户建议将开发测试的主要观察单位转为“实际行为、步骤与结果质量的对应关系”，主助手采纳。每个能力包说明希望工作模型改变什么行为、解决哪类结果缺陷、用哪些真实对象验证。代码差异、提示和运行配置继续记录，用于解释行为为什么变化与复现实验条件；它们本身不代替方法有效性的判断。

复用公开工具请求/回执、原图范围、声明、中间源模型、修订及独立评价，追踪“输入证据 → 对象/参数解释 → 动作 → 保存后的变化 → 结果与结束判断”。只记录可观察依据和外显决策，不需要模型隐藏思维链。先定位错误首次进入哪一份声明，检查后续为何保留或改正；不能把未看、看错、对象对应错、执行错和发现后未修都统称模型波动。

从好结果提炼候选有效做法，同时找反例：同样做法是否也曾失败，没做某动作是否仍成功。看过图、调用工具、提交claim、通过确认或增加版本都不直接算高质量行为；要核实际解释和保存结果。未发生目标行为的整案不能证明该方法有效/无效。先有行为与结果的对应证据，控制条件改变方法后再判断因果，不能将少量相关性写成稳定规律。

行为原则可通过指引、工具反馈、任务组织和局部返工一起落地，保持Agent按问题选择路径；不把成功轨迹抄成唯一固定流水线，也不新增过程打分来代替源BIM保真。开发辅助重放仅证明方法可执行，工作模型采用及独立稳定性分别验证。具体分析口径见[评价](../design/evaluation.md#行为与结果的对象级对应09-28)。

**10-01 用户要求：“从现在开始模型行为要完全记录，这样方便后续比对”。** 每次工作模型运行结束后，与质量评价一起归档完整行为记录：逐步工具调用的完整参数与文字返回（返回图片记哈希，原图在运行目录）、每步前模型的可见文字与思考量、token 用量、5 小时/7 天额度读数，以及首稿时刻、立面核对、高度依据来源立面与套用立面等对比指标。CLI 只给思考块签名、不给内容时如实注明只记数量。当前由分支 `dev/opus-guidance-recovery-20260929` 的离线脚本 `AI_agent/logs/experiments/2026-10-01_behaviour_records/record.py` 生成，已补好结果时期与近期共 11 次运行；该分支合入时接入运行器，使每次运行结束自动生成。

本轮所说“加强行为约束”优先针对已有证据的失效：观察到的对象有没有进入声明，单位/坐标有没有正确成为保存值，返工有没有修正目标且保住其他对象，结束前是否用原始证据核实际结果。具体约束落在指引、工具接口还是反馈，由开发和离线反例决定；当前尚未实现新的硬门。保留自主选择观察和操作路径的空间，不以固定工具顺序或调用次数验收，也不因旧树同样出现行为差异就将原因定为纯随机方差。

## 定期独立审查（10-03用户确认）

用户：“间隔一堆时间之后，需要独立审查一遍当前agent，迁移底座完之后还要包括底座，用意主要是为了避免开发迭代造成的整体过度熵增，具体的节奏你来把控”；随后确认节奏按 Opus 提议试行，“审查最好是两边旗舰各自独立”。起因同 09-27–29 的回退：一层层叠加的提醒与反馈拖累了整体。

- **触发**（满足任一）：每合入约 3 个能力包；写给模型的指引总量比上次审查增长 15% 以上，或工具多 5 个以上；准备换基线或跑节点回归之前；最长间隔一周。底座迁移完成后，底座一并审查。
- **审查人**：Astra 与 Opus 各自从空白上下文独立审查（最高思考档），互不先看对方结论；Opus 汇总两份结论，分歧单列。量大的清点（字数、工具使用率）可先交开发子代理做。
- **固定清单**（每次同样的指标，便于前后比较）：指引总长度、重复或互相冲突的要求、过时规则、改指令是否“替换不追加”；工具数量、功能重叠、实际使用与报错率、无人使用的工具；死代码、重复逻辑、只为锁住旧行为的测试、检查总数与全量耗时（10-07 起，目标全量约 30 分钟以内）；最近几次运行的轮数、报错数、首稿时刻与总耗时；底座迁移后加上运行开销、未用功能与接口复杂度。10-03 起点：图纸系统提示 9,179 字符、工具 42 个。
- **产出**：审查报告与“删、并、简化”清单，放仓库；是否先插清理包由 Opus 判断并告知用户。
- **首次**：10-03 用户定在迁移成功后就做一次（迁移对照通过、工具改进包有用部分合入、两底座同一版 Agent），审查范围含新底座，好在新底座上无负担继续开发，也便于针对 Opus 亲做三例继续改进 Agent。
- **10-03 晚已做首次**：两份报告与汇总见 [首次完整审查](../logs/reviews/2026-10-03_first_full_review/summary.md)。下次起“指引总长度”按四项合计（系统提示、工具说明、参数结构、几乎每次必读的参考），本次基线 62,431 字符；报错分“调用报错／领域未成功／可用源稿”三列。

## 文档怎样维护

| 内容变化 | 更新位置 |
|---|---|
| 用户目标、交付边界或重要决定 | `project/goal.md`、`project/decisions.md` |
| 当前进度、阻塞和下一步 | `project/roadmap.md` |
| 系统结构、共同模型、实现范围或评价办法 | `design/` 对应正文 |
| 开发、模型费用、case 用法或会话设置 | `workflow/` 对应正文 |
| 本轮过程与证据 | `logs/worklog/`、`logs/experiments/` 或既有 run README |

一条事实在对应位置维护，其他页引用它。项目记忆同次入仓，本地只留索引；切模型前补齐尚未入文档的事实和用户要求。
**10-01 用户要求：之后汇总、报告等网页都输出为仓库内的本地 HTML 文件**（完整独立页面，含 `<!doctype>` 与 `charset`，放在对应工作记录或实验目录），不发布到 claude.ai 等只属于某一模型家族的平台；原因是开发可能换模型家族，产物要让任何助手都能打开和维护。
旧文件没有继续存在的必要就删除或归档，不为旧路径保留兼容入口。内容按目标归并，不将旧文件一一搬到新目录。历史原稿与 Git 保存可追溯性，历史记录不自动产生待办。

## 统一统筹与开发协作（09-25确认）

用户将 Claude 的开发权限与任务管理交由 Codex 主助手，并指定主助手统一维护项目文档、交接和每轮收工。用户随后明确 Astra 与 Opus 5.5 均为最高档开发负责人，如同两位项目经理，各自按需选择子代理；两个模型家族不绑定还原/部分推理路线。Astra 根据进度、接口依赖与实际结果统筹工作包和合并时机，用户统一与 Astra 沟通；正常派工与合并不逐次请用户审批。用户仍决定产品目标和明确要求人工验收的结果。

- 派工写清任务目标、基准提交、工作目录/分支、可修改文件、共享接口边界、验证与交付要求。Claude 在范围内自行实现、验证和提交；需要扩展范围或改变公共接口时先交主助手协调，不自行切换主线、合入或推送 main。
- 并行写代码使用独立短期 worktree；共享源 BIM、几何内核、总运行入口及查看器等文件每项改动指定负责人。两边代码按提交集成，未提交修改不会自动同步；避免两个助手同时改同一共享接口。
- Claude 交回基准与成果提交、改动文件、实际验证、结果/证据路径、未完成项及活动进程。主助手审核共享语义与两方向受影响行为，决定合入、返工或保留；公共能力小步集成，再通知 Claude 同步主线，不积累长期分叉。
- 项目目标、设计、操作规则、roadmap 和正式交接由主助手统一维护。Claude 只在获派范围保存任务笔记和实验原始证据，交接材料作为主助手汇总输入；不各写一套全局状态，也不让用户负责搬运合并。
- 这是开发协作安排，不固定产品运行中的 Agent 数量、角色或模型。既有产品模型上限、调用费用授权、GT 隔离与用户验收边界继续适用。

## 从 Claude Code 派 Astra（Windows 原生，10-06 实测修正）

Windows CLI 的 `workspace-write` 已用真实写入验证：仓库内文件可写，仓库外的独立探测目录拒绝写入。首次设置写权限花了约 47 秒，设置完成后探测正常。容器时期“只能完全访问”的限制不再用于这台本机。

**10-06 首次实际派工前，用 `codex sandbox -P :workspace` 逐项核对（0 次模型请求），修正了三处：**
- **工作树位置：** 沙箱进程在 `%LOCALAPPDATA%` 下的目录启动不了（`CreateProcessWithLogonW failed: 267`）；桌面、用户目录、D 盘下的目录都实测可以。用户定“那就放桌面就行，反正要回收”：工作树放仓库旁的 `C:\Users\Horton\Desktop\EnergyPlus-Agent-worktrees\<任务名>`。每个约 3.6 GB（含 0.45 GB 虚拟环境），建一个约 40 秒；包合入后整个收回，没有在用的工作树时连这个文件夹也删掉。不放进仓库目录里：那样标准答案会多出一份副本，旧底座防偷看的路径规则管不到。
- **不能提交：** 工作空间写模式下所有 `.git` 都只读。工作树的 Git 目录、另加主仓库 `.git` 写权限、独立本地克隆自己的 `.git`，三种都写不进 `index.lock`。所以执行方不提交：改动留在工作树，报告给出建议的提交分组，由 Opus 复核后在工作树里提交。这是 Codex 对 Git 元数据的保护，不用绕开它的办法。
- **启动方式：** 用 `Start-Process` 拉起的进程在工具调用结束后继续运行，不受 Claude Code 后台任务 2 小时上限影响。沙箱里用虚拟环境的完整路径能运行 Python，也能联网。

派工前先把已包含派工单的提交推上主线，再建工作树。新工作树按自己的锁文件建 `.venv`，不能继承主树虚拟环境：

```powershell
$taskTree = 'C:\Users\Horton\Desktop\EnergyPlus-Agent-worktrees\<任务名>'
git worktree add -b <分支> $taskTree main
Push-Location $taskTree; uv sync --frozen --python 3.12; Pop-Location
$state = Join-Path $taskTree 'AI_agent\archive\local_backup\<任务名>-dispatch'   # 已忽略：提示、启动脚本、事件、错误输出
New-Item -ItemType Directory -Force -Path $state | Out-Null
Set-Content -Encoding utf8 -Path "$state\prompt.txt" -Value '<派工提示：先完整读 Agent.md；再到工作树根目录执行派工单；沙箱下不提交>'
Set-Content -Encoding ascii -Path "$state\launch.cmd" -Value @"
@echo off
cd /d "$taskTree\AI_agent"
call codex exec -m gpt-6-astra -c "model_reasoning_effort='max'" -c "project_doc_fallback_filenames=['Agent.md']" -c "sandbox_workspace_write.network_access=true" -s workspace-write -C "$taskTree\AI_agent" --add-dir "$taskTree" --json -o "$state\final.md" - < "$state\prompt.txt" > "$state\events.jsonl" 2> "$state\stderr.log"
echo exit=%ERRORLEVEL% > "$state\exit.txt"
"@
$p = Start-Process -FilePath 'cmd.exe' -ArgumentList '/c', ('"' + "$state\launch.cmd" + '"') -WindowStyle Hidden -PassThru
Set-Content -Path "$state\pid.txt" -Value $p.Id
```

`AI_agent` 作为启动目录，是为适配本机 CLI 对嵌套备用文件名的实际加载行为；`--add-dir` 提供整个工作树的写入范围。配置值内部使用 TOML 单引号，避免 Windows PowerShell 5.1 把双引号剥掉而误传成字符串；同样适用于 PowerShell 7。提示放文件、用 `-` 从标准输入读，避免长中文提示的转义问题。旧 `Bash(codex *)` 允许规则不代表 PowerShell 的执行权限，实际权限以客户端显示为准。续接时先切到同一工作树的 `AI_agent`，再用 `codex exec resume <线程> -m gpt-6-astra -c "model_reasoning_effort='max'" --json -o <最终回复文件> -`（续接提示同样从标准输入给）；resume 不接受 `-C`。线程号在 `events.jsonl` 第一行。

- 每个阶段：验收标准与派工单入主线 → 建工作树 → 启动 → 复核改动范围与关键证据 → 必要检查 → Opus 按报告的分组在工作树里提交 → 合入并推送 → 收回工作树。长包开工即保存报告初稿，逐步更新报告，保留中断后的续接入口。
- **收回工作树前**，先把工作树里的派工状态目录（`AI_agent/archive/local_backup/<任务名>-dispatch/`，含 `events.jsonl` 的用量回执与 `final.md`）拷到主树同名的已忽略目录，并记下用量。10-06 收回 `d1c` 时一并删掉，D1c 的用量没取到。
- 检查时将 `PYTHONPATH` 指向该工作树，先确认导入模块的 `__file__`；不能把共享 editable 安装的主树结果当作分支验证。pytest 用 `--basetemp AI_agent/archive/local_backup/<任务名>/pytest` 将临时产物留在已忽略的工作树目录。
- 新证据按哈希引用已有字节，不重复打包；每阶段新增证据尽量约 10 MB。

## 用户说“收工”时

由 Codex 主助手统一执行。先让所有执行助手保存并交回当前成果、未提交改动、验证和运行状态；结束或安全停止本轮活动任务，保留未完成内容，不把 Claude 的局部交付当作全项目已收工。

1. 更新当前状态、具体卡点和下一次入口；本轮过程移入工作记录，目标/设计变化同步对应正文。把最新一份收工/交接记录链接放在 `project/roadmap.md` 的“当前交接”，保持 Agent.md → 当前任务 → 最新交接的阅读路径；不在 Agent.md 累加历次日志链接。
2. 核对全部助手项目记忆和会话内容是否已落文档，移走过期状态。
3. 检查完整 diff/status、验证结果及未验证范围，只提交本轮改动。收工不触发额外全量。
4. commit 并正常 push，核对远端一致，按需增加里程碑标签；收回完成的临时树，未完内容保存并交接。
5. 总结本轮会话的全部工作及其影响，同时汇报提交、验证、遗留和下一次入口。出现失败如实说明，不声称已收工。
