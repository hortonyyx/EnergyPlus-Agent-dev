# 开发、文档维护与收工

共同权限见 [Agent.md](../Agent.md)。本页说明从一个问题到可交付结果的工作方法。

## 推进一项任务

1. **每个助手聚焦获派工作包，由 Codex 主助手统筹并行。** 还原建模和部分推理是同一 Agent 的研发分工，可在同一轮分别推进；共用入口、源模型与工具能力，不按开发助手划分产品架构。
2. 主助手在 [当前任务](../project/roadmap.md) 明确本次结果、负责人、输入和完成依据，小任务一行即可。需要设计取舍才补设计正文。
3. 查看相关源码、原始输入和已有产物，定位信息在哪一层丢失或改变。先选最短可交付改动，不恢复全部历史批次。
4. 复用已有工具与确定性内核；模型负责感知、语义和信息不足时的判断。改完检查实际输出及适用边界。
5. 按影响验证，记录结果与未覆盖范围。失败说明具体阶段和下一步，可独立交付的部分照常提交。
6. 执行助手保存证据并提交任务成果；主助手决定集成，统一更新设计/操作说明、交接和正常 commit/push，汇报变化、证据和遗留。

对用户尽量讲白话，先讲结果和影响，再给必要依据，不堆内部代号、变量名和技术术语。每完成一个大节点，主动汇报从上一节点到现在做成了什么、怎么确认有效、还有什么没解决；进度简报不代替节点汇报。用户说“收工”时，总结本轮会话的全部工作，不能只报最后一个小改动或最后一次提交。

现有约束如果不适合目标，先弄清实际消费者，再修改并验证。不能只靠放宽检查、增加 accepted 数或合法 JSON 声称模型变好。

## 验证怎样选择

| 改动 | 通常需要什么 |
|---|---|
| 文档、索引或引用路径 | diff、链接、受影响路径/启动入口；无需 pytest 全量 |
| 单模块行为 | 相关行为检查，必要时补实际缺陷回归 |
| 相邻阶段接口 | 相关测试与一次真实产物贯通 |
| 广泛内核或依赖 | 先局部检查，再按影响决定一次全量 |
| 模型实验 | 独立 run，保留配置、人工参与、输出、质量/费用/耗时 |

同代码同范围的有效验证可以复用，换助手或收工不重复全量。不为可逆小改加测试锁，不规定每轮必须多模型复审。
测试采用现有环境的 `python -m pytest`；局部测试显式选择较少 worker，避免默认 `-n auto` 过量并发。普通测试离线；模型调用及派工遵守 [模型与费用](models.md)，DeepSeek 专项许可不能由跑 case 的一般授权替代。
观察到的改进先在问题样本成立，再按具体不确定性选另一个代表输入；不把单次高分或人工修补当普遍能力。评价细则见 [验证与评价](../design/evaluation.md)。

当前研发优先级按[09-14收工确认](../project/goal.md#当前优先级09-14-收工确认)：先验证有限模型智力下的准确性与稳定生成，时间优化后置。实验时限按质量验证所需工作合理配置，不机械沿用历史短时限或以抢早首稿为目的；记录耗时不等于本轮要优化耗时。

## 文档怎样维护

| 内容变化 | 更新位置 |
|---|---|
| 用户目标、交付边界或重要决定 | `project/goal.md`、`project/decisions.md` |
| 当前进度、阻塞和下一步 | `project/roadmap.md` |
| 系统结构、共同模型、实现范围或评价办法 | `design/` 对应正文 |
| 开发、模型费用、case 用法或会话设置 | `workflow/` 对应正文 |
| 本轮过程与证据 | `logs/worklog/`、`logs/experiments/` 或既有 run README |

一条事实在对应位置维护，其他页引用它。项目记忆同次入仓，本地只留索引；切模型前补齐尚未入文档的事实和用户要求。
旧文件没有继续存在的必要就删除或归档，不为旧路径保留兼容入口。内容按目标归并，不将旧文件一一搬到新目录。历史原稿与 Git 保存可追溯性，历史记录不自动产生待办。

## 统一统筹与开发协作（09-25确认）

用户将 Claude 的开发权限与任务管理交由 Codex 主助手，并指定主助手统一维护项目文档、交接和每轮收工。当前分工为 Codex 继续还原建模，Claude 承接部分推理；主助手可按接口依赖与实际结果调整工作包和合并时机，正常派工与合并不逐次请用户审批。用户仍决定产品目标和明确要求人工验收的结果。

- 派工写清任务目标、基准提交、工作目录/分支、可修改文件、共享接口边界、验证与交付要求。Claude 在范围内自行实现、验证和提交；需要扩展范围或改变公共接口时先交主助手协调，不自行切换主线、合入或推送 main。
- 并行写代码使用独立短期 worktree；共享源 BIM、几何内核、总运行入口及查看器等文件每项改动指定负责人。两边代码按提交集成，未提交修改不会自动同步；避免两个助手同时改同一共享接口。
- Claude 交回基准与成果提交、改动文件、实际验证、结果/证据路径、未完成项及活动进程。主助手审核共享语义与两方向受影响行为，决定合入、返工或保留；公共能力小步集成，再通知 Claude 同步主线，不积累长期分叉。
- 项目目标、设计、操作规则、roadmap 和正式交接由主助手统一维护。Claude 只在获派范围保存任务笔记和实验原始证据，交接材料作为主助手汇总输入；不各写一套全局状态，也不让用户负责搬运合并。
- 这是开发协作安排，不固定产品运行中的 Agent 数量、角色或模型。既有产品模型上限、调用费用授权、GT 隔离与用户验收边界继续适用。

## 版本、环境和并行

用 Git 提交/tag 标识代码，用 run 或工作记录保留输入、命令、关键配置、模型/人工参与、输出和未验证范围；不另造能力版本准入清单。重要证据不只留在临时目录。
main 是持续集成主干，由 Codex 主助手负责合并与推送。短期分支/worktree 明确文件范围，公共模型/内核/出口及时集成；验收合入后由主助手收树，未知改动先保存。共享历史不强推，回退已共享改动优先用 revert 或另开旧版本查看目录。工作树放在已确认持久化的位置，各实验独立输出目录。
使用已配置的 Dev Container 环境。共享 editable 安装可能被另树启动改变；怀疑串树时检查模块 `__file__`。不要反复自动同步依赖或为普通文件改动新装环境，确需不同依赖时再隔离环境。

## 用户说“收工”时

由 Codex 主助手统一执行。先让所有执行助手保存并交回当前成果、未提交改动、验证和运行状态；结束或安全停止本轮活动任务，保留未完成内容，不把 Claude 的局部交付当作全项目已收工。

1. 更新当前状态、具体卡点和下一次入口；本轮过程移入工作记录，目标/设计变化同步对应正文。把最新一份收工/交接记录链接放在 `project/roadmap.md` 的“当前交接”，保持 Agent.md → 当前任务 → 最新交接的阅读路径；不在 Agent.md 累加历次日志链接。
2. 核对全部助手项目记忆和会话内容是否已落文档，移走过期状态。
3. 检查完整 diff/status、验证结果及未验证范围，只提交本轮改动。收工不触发额外全量。
4. commit 并正常 push，核对远端一致，按需增加里程碑标签；收回完成的临时树，未完内容保存并交接。
5. 总结本轮会话的全部工作及其影响，同时汇报提交、验证、遗留和下一次入口。出现失败如实说明，不声称已收工。
