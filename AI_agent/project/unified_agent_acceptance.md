## 阶段 0：接口与验收样例

**状态：10-02 通过（Opus 验收），8 个跟进项在阶段 1 处理。** 用户“开工吧，开始开发”，Opus 派 Astra 实施，[派工单](../logs/experiments/2026-10-02_harness_stage0/brief.md)，[Astra 交付报告](../logs/experiments/2026-10-02_harness_stage0/delivery_report.md)。

### 要交什么

1. **接口说明**：放在 `AI_agent/design/`，白话中文。每个接口写用途、字段、约束，以及与现有代码的关系（沿用、替换或新增）。
2. **可机器校验的接口定义**：写成代码（项目已用 pydantic）。底座核心与建筑共用层分开放；底座核心不引用建筑模块，不出现建筑概念。这些定义就是阶段 1 要用的正式定义，不是一次性草图。
3. **样例**：三类主样例加三个专项样例（见下表）。尽量取自已有真实产物，写明来源路径和哈希；用代替品的地方明确标注。样例可以是节选（例如一层、几个房间），只要每个接口都被实际用到。
4. **检查**：全部样例通过校验；关键约束各有反例，反例必须被拒。
5. **验收材料**：接口 × 样例覆盖表、历史记录映射表、未决技术问题、需用户拍板的产品取舍、阶段 1–3 细化估算、开发记录（含子代理型号与用途、用量）。

### 样例

| 样例 | 输入与来源 | 至少要演示 |
|---|---|---|
| 还原 | 有明确尺寸的图纸。sm25 或 sm21（含两层），取自 10-01 开发产出或 run99/run100 | 标注加像素双证据；尺寸链换算进保存值；一处规整（建议 sm25 一、二层之间 6 cm 的跨层细条）；一次局部观察派工（证据包与返回）；覆盖清单 |
| 部分推理 | 缺资料、含跨层空间。Voimatalo 已验收的精细档（修订 02），以及 6.1 Sol／6 Sol 两次测试记录 | 同一对象上观测与推断并存；跨层空间；重复加例外的声明；“精细档偏好 → 方案选择 → 对象 → 检查”的覆盖链，以 Sol 测试中偏好未落实为反例 |
| 完全推理 | 只有楼的少量照片，可附少量文字 | 照片观察（层数、窗列等）；功能需求作为用户要求；方案选择与推断依据；覆盖清单；没有图纸和网格时接口不缺字段。仓库暂无真实照片样例时可用代替品（如贴图模型渲染的街景），须标明，并把“需要真实照片样例”列为待用户决定事项 |
| 混合输入 | 例如局部平面＋体量网格＋文字，或照片＋一张平面 | 不同部位分别靠观测或推断；不同来源指向同一对象 |
| 证据冲突 | 例如标注与像素量测不一致、平面与立面不一致、用户说明与图纸不一致 | 冲突双方及各自依据都留下；写明处理结果或列为未决 |
| 同输入不同简化 | 同一栋楼的精细档与粗档 | 依据共用，要求不同，声明和覆盖不同；粗档的合并是合法交付，不判漏房 |

### 通过条件

**A. 三线共用，不只服务还原。** 每个共用接口至少被一个还原样例和一个推理样例（部分或完全）实际用到，覆盖表能看出来。推理专属的设计标为待验证假设。

**B. 事件记录够阶段 1 使用。** 能表达并区分：
- 实际发出的请求（适配器转换后的最终请求体），以及每段自动加入内容的来源；
- 模型返回的可见文字和工具调用；思考信息分五种情况：服务公开的内容、摘要、服务报告的 token 数、签名、无法获得。不把签名当内容，不把估算当计费数，不把缺失记成零；
- 采样与推理参数：请求值、服务报告值、未核实是否生效，三者分开；
- 工具的完整参数、原始返回、模型实际看到的返回（截断或转换之后）；图片的原始文件哈希、实际发送哈希及引用；
- 原始用量对象，缺失就标缺失；
- 各层版本：代码提交、依赖锁、提示、工具定义、推理参数、模型路由；远端别名不能证明固定时如实标注；
- 重试、取消、超时、恢复、失败阶段，以及停止时已有的产物；
- 父子任务；预算的预留与结算；上下文压缩、图片移出与取回及其原因（格式在本阶段定，实现在阶段 2）；
- 一期外层协调（命令行里的开发模型）经 MCP 发来的派工、操作和返回进同一份记录；拿不到的请求内容标“未获取”。

**C. 历史记录能映射进来。** 至少各取一段真实历史记录映射成新格式并通过校验：一段 Claude CLI 工作模型运行（如 run99 或 run100），一段开发模型桥接记录（如 6.1 Sol）。旧记录没有的字段列为缺失，不补造。

**D. 依据与需求。**
- 观测、推断、简化、假设可以同时作用于同一对象，不互斥；
- 用户要求（含简化与档位偏好）单独记录，不混进建筑事实；
- 计算链：原值 → 换算 → 规整 → 保存值，每步写原因；
- 依据可从模板或对象组继承，由代码补齐，不要求模型逐字段填写；
- 复用 view_id、claim、record_inference，写清与现有字段的对应关系，不另造并行编号；跨运行引用补上运行身份、原图哈希和坐标关系；
- 依据变动后能查到受影响的声明和模型版本，样例里实际演示一次。

**E. 声明边界。**
- 写明哪些由模型声明，哪些由代码展开和计算；
- 声明单位可以是一层、一翼、一组房间或跨层空间；重复允许例外；
- 完全推理能表达功能需求、空间关系和方案选择；
- 从现有 build_plan_bim、build_parametric_bim、revise_bim 等输入逐步演进，写出对应关系；不另起一门包办一切的大语言。目标是模型不需要临场写脚本。

**F. 角色与证据包。**
- 角色定义（职责、工具白名单、输入材料、返回要求、预算）与模型绑定分开；每个角色有默认模型、推荐模型和已验证范围；推荐列表不是失败后的换模列表（有反例）；
- 证据包包括问题、已知事实、图片或 view_id、裁剪范围、坐标换算、源模型版本、返回格式和预算；
- 子任务返回带定位的观察或建议、依据引用和不确定项，并把“直接看到的”“解释”“不确定的”分开；
- 协调侧应用前核对源模型版本，基于旧版本的修改被拒（反例）；
- 只读由工具白名单落实（反例：只读角色调用写工具被拒）；
- 首批角色是协调和只读局部观察；单层起草写出契约草案即可。

**G. 检查、规整与覆盖。**
- 检查结果写明类别（几何、拓扑、覆盖）、涉及对象、依据、建议动作（只改尺寸的规整，或列出交模型裁决）、容差来自哪一层（工具默认、档位上限、模型裁决及理由）和前后数值；
- “规整只改尺寸、不改实质”可以表达并检查：规整删墙、并房、动门窗或改连通要被拒或被标出（反例）；
- 覆盖清单一行串起“用户要求 → 方案选择 → 实际对象 → 检查结果 → 未完成项”；只有推断理由、没核对保存结果的不算覆盖通过（反例）；还原侧允许用户明确授权的简化；
- 规整不抹掉真实的错层、退台和窄空间：至少一个样例说明怎样区分该对齐的偏差和该保留的真实窄空间。

**H. 恢复与预算。**
- 工具按能否安全重复分类；写操作结果不明时先查实际状态，不重复修改源模型；
- 恢复时先核对已保存的状态；
- 总预算包含子任务、摘要和重试，先预留后结算；用量没有报告时，金额上限注明是估算。

**I. 范围。**
- 冻结基准 `5bb10538` 的工具、两套说明和几何内核行为不变：`scripts/tool_scripts/`、`src/agent/geometry/`、`src/agent/correction/` 和现有 `src/agent/execution/` 模块不改（可以新增文件），用 diff 文件名单证明；
- 不实现阶段 1 以后的运行功能，校验样例所需的最少代码除外；
- 本阶段不调用工作模型或付费 API；为定格式确需 Paratera 接口小测时在交付中提出，由 Opus 安排并报用量。不用 DeepSeek，不用 GLM 订阅接自有底座；
- 新增的产品取舍单列交用户，不在接口里悄悄定下。

**J. 验证。**
- 新增检查全部通过（`python -m pytest`，显式少量 worker）；
- 改了现有共享模块（如 `src/agent/model_routes.py`）时，相关旧测试通过；
- 依赖方向检查：底座核心不 import `src/agent` 下的建筑模块，也不 import `scripts/tool_scripts`。

阶段 1 开工时先处理的跟进项：
1. **名词对齐**：用户确认[名词规范](terminology.md)后，在阶段 1 用到这些类型之前统一命名，例如 `EvidenceItem` 实指“依据”；`normalized`／`NormalizationProposal` 统一为规整（regularisation）；`BuildingDeclaration` 对应“建模声明”；`InferenceHypothesis` 在还原里也用于解释，改为中性名称（如“模型判断”）。
2. **工具分类与真实角色**：现有 42 个工具逐个分为只读、可安全重复的写、不可重复的写；据此写出协调和局部观察两个角色的真实白名单。样例里的 `inspect_region`、`save_declaration` 只是占位名。
3. **语义快照由代码生成**：规整前后快照必须由代码从保存的源 BIM 生成，边界移动后重算开口端点、宿主和连通，不能由调用方填写。这是规整保护是否真正有效的前提。
4. **多层装配纳入声明**：`assemble_plan_bim` 的楼层与标高是模型的建筑判断，多层还原（sm21、sm25）需要，补进声明封装。
5. **证据包预算只引用底座总账**：证据包里的预算改为引用底座总账中的一笔预留，不另存一份数字。
6. **底座核心严格类型**：建筑层已严格校验，底座核心是否同样严格，定一个口径并写明理由。
7. **样例体积**：两份主样例因内联整图达 0.6–1.1 MB，保留一份内联示例用来校验位置，其余改为哈希引用（可选）。
8. **角色 ID 写法**：`local-observer`、`local_observer` 两种写法并存，统一为一种。

对 Astra 所提技术项的答复：快照与几何联动按第 3 项；预算按第 5 项；`InferenceHypothesis` 按第 1 项；大请求落盘前由适配器核对注入位置与图片字节，同意；历史重放分“原始附件完整、确定性重放一致、跨版本建筑差异解释”三项分别验收，同意；只读白名单在阶段 1 的执行器里就按工具分类落实，阶段 3 接入真实分发，不只靠提示词。

交用户的产品事项：完全推理用哪栋楼的真实照片；建模细度的档名、默认简化程度和全局容差（与名词规范一并定）；整案实测方案另报。

用量：Astra 主线程 75 分钟，输入 13,080,271（缓存 12,663,296）、输出 67,398（思考 19,379）；三个开发子代理（`gpt-5.6-sol` high ×2、`gpt-5.6-terra` high ×1）用量协作接口未提供。现有 ChatGPT 订阅；工作模型与付费 API 调用 0。

## 阶段 1：冻结工具的单角色闭环

**状态：10-02 通过（Opus 验收）。** 阶段 0 通过后派 Astra，[派工单](../logs/experiments/2026-10-02_harness_stage1/brief.md)，[Astra 交付报告](../logs/experiments/2026-10-02_harness_stage1/delivery_report.md)。

### 通过条件

**A. 只换底座。** 经新底座发出的工具集合（名称与说明）、两套系统提示和参考资料，与冻结基准 `5bb10538` 逐字节一致，用哈希证明。协议上必须做的转换（例如工具返回的图片改放到随后的用户消息里）写明理由，并在事件里记录转换前后。

**B. 端到端离线闭环。** 用脚本化的模型桩加真实冻结工具跑通一次单角色建模，过程中至少有一次带图返回、一次写操作、一次工具报错。产出的事件日志符合阶段 0 契约（完整新日志，不含历史缺口类型），`record.py` 能从它生成行为报告。

**C. 真实接口小测。** 至少一个目标档候选（建议 Qwen3.8-27B）经新底座完成“看图 → 调工具 → 收到带图返回 → 作答”。最终请求、服务公开的思考内容（有就记）、用量完整进入事件日志，事后报用量。累计不超过 20 次请求，不跑整案。

**D. 历史重放三项。**
- 原始记录与附件完整入档，有哈希；
- 同一版本、过程确定的工具重放与保存结果一致，不一致或不确定的字段逐个列出原因；
- 跨版本比较对象、几何、宿主与连通，解释差异。

旧记录拿不到的部分写明缺口，不补造。

**E. 停止与恢复。** 调用次数、工具次数、时间、token 任一上限触发时干净停止，记录原因和已有产物。写工具结果不明时按阶段 0 规则先查状态再决定，至少一个用例；全面故障注入留到阶段 2。

**F. 跟进项。** 阶段 0 跟进项 1–8 逐项处理，或写明移到后续阶段的理由。第 1 项按用户确认后的名词规范执行。

**G. 范围。** 冻结基准的工具、两套指引和几何内核行为不变，用 diff 文件名单证明。改动现有共享模块（如 `chat_mcp.py`、`model_routes.py`）时，相关旧测试通过。不改 `AI_agent/project/` 与 `Agent.md`。

**H. 验证。** 新增检查全部通过；阶段 0 的 86 项照样通过；涉及的旧测试通过。
