# 统一 Agent 底座与建筑共用层开发计划

10-02 由 Opus 与 Astra 讨论定稿，交用户。各阶段验收标准与结论见[验收记录](unified_agent_acceptance.md)。依据：[调研报告](../logs/experiments/2026-10-02_harness_research/astra_report.md)、两轮讨论（[第一轮](../logs/experiments/2026-10-02_harness_research/discussion_01_astra.md)、[第二轮](../logs/experiments/2026-10-02_harness_research/discussion_02_astra.md)）、[讨论记录](../logs/worklog/2026-10-02_reconstruction_discussion.md)。

用户已确定的前提：
- 工作模型现在就换，不再等 Sonnet 恢复；
- 自建一个轻量、本项目专用的底座，以后可开源；
- 支持多个子代理，按角色分、不按模型分，角色可以接不同模型；
- 首版按阶段开做，实测走 Paratera；
- 最终是一个统一的 Agent，三条线协同设计，不能只服务还原建模。

## 一、目标与边界

- **一个统一 Agent。** 还原、部分推理、完全推理只描述输入信息有多充分，并用于组织评价，不建三套长期管线。三者没有明确边界，只是目前的说法：部分推理也可能带图纸，并需要相对细致的建模；完全推理指信息很少，典型输入是楼的单张或多张照片（10-02 用户纠正：不是只有文字）。同一任务可以混用图纸、三维网格、照片和文字，同一栋楼的不同部位也可以分别靠观测或推断。
- **首版验收：** 形成可追踪、可恢复的建模闭环，并完成带图委派。初期由开发模型在命令行外层协调，工作角色在自有底座里运行；外层拿不到的请求内容如实标注。工作档模型自主协调放到后续阶段。
- **底座本身不承诺提升建模质量。** 换底座能去掉看不见的变量、方便排错。工作模型的建模质量在底座之后单独推进。
- **推理侧还在探索。** 部分推理只做过开发模型的测试，还没有工作模型完成的案例，架构没有定型；完全推理尚未开始。推理专属的设计都标为待验证的假设，包括方案推断角色、由需求生成方案参数、推断语义，并单列探索线（见第四节）。共同件只做已确认需要的部分，探索结果出来后再回头修订。

## 二、共用结构

- **底座核心（不含建筑概念）：** 模型接口、工具执行、角色调度、上下文管理、事件记录、预算与恢复。首版只接 OpenAI 兼容的 Chat Completions，其他接口按获准服务再加。
- **建筑共用层（三条线共用）：**
  - 同一套源模型、对象身份和修改规则。
  - **依据与需求记录：** 观测、推断、简化、假设可以同时作用于同一对象，不互斥。用户要求和计算过程单独记，例如标注值经换算、规整落入模型时，保留原值和变化原因。依据可以从模板或对象组继承，由代码补齐派生关系，不要求模型逐字段手填。复用现有的 view_id、claim、record_inference。依据变动后，能找到受影响的声明和模型版本。
  - **建筑声明：** 在现有建模、参数化和修改接口上逐步统一，不另起一门包办一切的大语言。一次声明的单位可以是一层、一翼、一组房间或跨层空间，重复允许例外。完全推理还需要表达功能需求、空间关系和方案选择。代码负责展开和计算，建筑上的取舍由模型做。目标是不需要模型临场写脚本。
  - **检查与规整：** 包括几何（细条、细缝、上下层对齐）、拓扑（门窗挂墙、连通）和覆盖三类。按 10-02 定的原则，规整只改尺寸、不改实质；也不能抹掉真实的错层、退台和窄空间，不能把精细档机械理解成每个空间都细分。
  - **覆盖清单：** 串起“用户要求 → 方案选择 → 实际对象 → 检查结果 → 未完成项”。只写了推断理由不算覆盖通过，要核对实际保存的结果。还原侧允许用户明确授权的简化。
  - **角色目录与证据包：** 角色按功能划分，按需调用，不是流水线。交给子任务的证据包包括问题、已知事实、图片或 view_id、裁剪范围和坐标换算；子任务交回带定位的观察或建议，由协调侧核对当前模型版本后再应用。每个角色配默认模型和推荐模型，注明已验证的范围；型号可以替换，推荐列表也不自动变成失败后的换模列表。
- **方法模块：** 按当前问题组合图纸、网格、照片、文字方法，不按路线固定选择。现有两套说明（图纸用 09-30 版，三维用 10-01 版）逐步统一为“共用核心＋方法模块＋角色提示”。

## 三、阶段（每阶段离线验收，不承诺周数）

**阶段 0：接口与验收样例。** 定下角色输入输出、图片与坐标引用、依据与需求的关系、声明边界、事件格式和恢复规则。接口同时用三类离线样例检验：
- 有明确尺寸的还原；
- 资料缺失、含跨层空间的部分推理；
- 信息很少的完全推理：只有楼的单张或多张照片，可附少量文字。

另外还要检验混合输入、证据冲突，以及同一输入下不同的简化偏好。技术细节由双方定稿，新增的产品取舍交用户决定。

**阶段 1：冻结工具的单角色闭环。**
- 工具和两套原始说明以主线 `5bb10538` 为基准，只换运行底座，保留比较基础。
- 统一的事件日志保存这些内容：实际请求与响应，工具参数与原始返回，模型实际看到的返回，图片及其引用，服务返回的思考内容，用量，采样参数，各层版本。没有返回的信息标为缺失，不补造。
- record.py 改为读统一日志，同时保留对历史格式的读取。
- 历史重放用 run99、run100、Opus 三例和两次 Sol 测试的记录。验收分三条：
  - 原始记录和附件完整保存；
  - 同一版本、过程确定的工具重放结果一致，不确定的字段明确列出；
  - 跨版本的历史结果比较对象、几何、挂墙和连通，并解释差异。
- 重放通过不代表模型能力通过。
- 按需做 Paratera 接口小测（工具调用、图片、思考字段），事后报用量。

**阶段 2：长任务与恢复。**
- 支持上下文压缩，图片可以移出当前请求，需要时按原引用取回。压缩后保留用户约束、依据引用、当前模型版本、未决项和待办；原始记录始终保留。
- 设 token、金额、时间和调用次数预算，子角色、摘要和重试都计入总账。
- 用 60–120 步的长记录做故障注入检查：中断前后、图片取回、压缩后恢复、预算停止、写操作结果不明。恢复时先核查已保存的状态，避免重复修改源模型。

**阶段 3：带图委派与首版验收。**
- 开发模型在外层协调，通过 MCP 使用建模工具和委派工具；底座内先只运行只读的“局部观察”角色。
- 记录父子任务关系和各模型实际做了什么，验证子角色确实收到了图片，协调侧能回看核对。
- 角色小测试覆盖：图纸、网格、照片，以及只有少量照片、信息不足的情况。输入种类和推理程度在验收表里分别列出。
- 随后提交首批整案方案：至少还原、部分推理各一例，写明模型、次数、预算和评价口径，由用户批准后执行。
- 首版要演示“建模 → 检查 → 针对问题修改 → 保存可查看的结果”，以及中断恢复和带图委派。

**阶段 4：建筑共用层增强。** 阶段 0 定稿后即可并行离线开发，按包分别启用，每包各自确定回归范围，不与底座迁移混在一起，也不合成一次大变化：
1. 依据继承、从需求到对象的追踪、建筑声明补充（包括按标注值落位、读图记录检查）；
2. 全楼几何、拓扑和覆盖检查，以及确定性规整（含上下层对齐、细条检查）；
3. 命名修正（同一排房间分排编号、楼层 F# 与体量命名）和统一说明层。

每包先离线验收，需要整案回归时另报方案。检查既要能发现缺漏，也要保护真实的开敞空间、跨层体量和用户明确授权的简化。

**阶段 5：工作档自主协调。** 把协调角色移进底座，沿用相同的对象、声明、工具和评价规则，逐步加入起草、方案推断和复核角色。强模型辅助的结果和工作档自主的结果分别报告。完全推理的首个真实探索案例在本阶段前另拟方案，交用户确认。单个代表案例成功只算探索结果，不据此宣称稳定。

## 四、部分推理探索线（与阶段 3–5 并行，Astra 牵头）

目标是做出部分推理第一个由工作模型完成的案例，并据此弄清推理侧真正需要哪些角色、声明和检查。
- 先由开发模型调度 27B 做一例（辅助模式），以用户已验收的 Voimatalo 精细档为评价参照，看哪些环节 27B 能做、哪些需要工具或协调补位。
- 再逐步减少开发模型的介入。
- 结果用来修订共同设计：角色目录、声明语义、覆盖清单。

前期推理侧的验收只用站得住的内容：两次 Sol 测试记录的重放，以及网格局部观察小测。不用推理侧的整案质量当底座的验收标准。

## 五、分工与交付方式（10-02 用户调整）

用户：“主体开发工作交给 GPT 那边，至于那边具体的分工，让 Astra 自己决定吧；你这边更多做总主导、验收和质量负责；因为我的 gpt 是 20x，你是 plus，需要合理规划。”

- **GPT 侧（Astra 牵头）：** 承担主体开发，即第二、三节的全部实现，包括底座核心、建筑共用层、各方法模块和部分推理探索线。内部如何分工、选派哪些子代理由 Astra 决定。主线集成和开发记录也由 Astra 负责。
- **Opus：** 总主导、验收和质量负责。具体包括：
  - 把握方向和优先级；
  - 各阶段的验收标准和验收结论；
  - 共享接口的质量审查；
  - 回归与实测方案的提请；
  - 维护本计划和验收记录。
  
  Claude 是 Plus 额度，所以集中用在阶段验收、关键设计审查和质量判断上，不承担大段实现，也不做长时间的探索运行。
- **共同：** 共用接口必须同时经过还原和推理样例检查，不能一侧定型后另一侧再补。每阶段由 Astra 交付离线验收材料，Opus 验收通过后进入下一阶段；验收不通过就写明问题，退回修改。
- **协作方式：** 共享文件指定主要实现者，短分支开发；阶段结论和需要用户拍板的事项由 Opus 汇总后报告用户。

## 六、实测与批准

- **接口小测：** 开发中按需调用 Paratera，事后报实际用量。
- **整案实测与节点回归：** 先报方案（案例、模型、次数、预算、评价口径），用户批准后执行。
- **新旧底座的严格对照：** 需要同一服务、同样参数配对，另行批准。09-30 的 GLM 结果只作历史参照。10-03 用户决定新底座直接接 GLM 订阅（覆盖此前按智谱条款不接的口径），严格对照由此可以在同一订阅上做。DeepSeek 专项许可不变。

## 七、进度预估（10-02，粗估，非承诺）

第一轮验收是阶段 3 结束时的首版验收。按每天一到两轮开发会话估算，大约需要 1–2 周、累计 4–8 轮会话：

- 阶段 0：约 1 轮；
- 阶段 1：1–2 轮；
- 阶段 2：1–2 轮；
- 阶段 3：1–2 轮，另加整案实测的报批与执行。

第一个可看的中间节点是阶段 1 结束，也就是用历史记录重放验收，大约开工后 2–3 轮。Astra 在阶段 0 定稿后细化估算。最大的不确定性在长任务、委派与真实模型的联调，以及实测批次的节奏。Astra 调研给出的人工开发量是 13–22 人日，只作为范围参考，不直接换算成日历时间。

## 七之二、主体迁到新底座的时机（10-03 用户同意“按这个推进”）

阶段 0–3 已验收并合入。现在建模 Agent 有两条测试线：Claude Code＋GLM 订阅（旧运行器，单个工作模型，订阅免逐批批准）和新底座＋Paratera（按量计费，整案逐批批准）。10-03 下午起，新底座也接 GLM 订阅：Paratera 上三次迁移对照显示，同一型号经 Paratera 每轮思考量是订阅线路的 3–5 倍，用户随即决定“直接接”。之后迁移对照改为同一订阅、只换底座的同条件对照，Paratera 的结果保留，作为服务商差异的证据。

**迁移条件（两条都满足即迁）：**
1. 阶段 3 已合入主线（10-03 完成），“输出格式错误回给子角色改一次”的补救已做；
2. **迁移对照实测**通过：同一个 GLM-5.3-Flash 经 Paratera 在新底座上单独跑 sm24（冻结工具、同任务同限额），结果不比 Claude Code 上的 10-02 基线差，记录完整，没有底座本身引起的失败。这也是新底座第一次用真模型跑整案。

**迁移前后的分工（用户 10-03 定）：** “新基座开发过程中，你继续在Claude code基座上开发+测试，不等；等基座差不多了，我们主线迁移到新基座，在新基座上继续开发，5.3flash稳定后再切模型到27B档，然后持续开发agent和改进基座；Claude code作为对照继续存在（最好保持agent是一致的，才好对照差异）；所以我建议开发包后续改进直接等迁移后在新基座上做，更直接。”
- **迁移前：** 新底座由 Astra 开发；Opus 在 Claude Code＋GLM 订阅上继续开发和测试已派的工具改进包 T1（独立分支，边测边改）。T1 之后的改进不再在 Claude Code 上开新包，等迁移后在新底座上做。10-03 用户再定“以迁移为界”，手上的工作做完收口再转：T1 以 sm25（10-03 在跑）为 Claude Code 上最后一次测试，sm21 改到新底座上测。
- **迁移时：** T1 经 GLM 测试证明有用的部分合入主线，两个底座用同一版 Agent（工具、指引、任务说明一致）；底座里“工具与冻结基准逐字节一致”的检查改为“与登记的 Agent 版本一致”，冻结基准标签保留作历史对照。
- **迁移后：** 先用 GLM-5.3-Flash（经 Paratera）在新底座上开发和测试，稳定后切到 27B 档，再持续开发 Agent、改进底座。Claude Code 保留作对照，跑同一版 Agent，比较两个底座的差异；以后的 Agent 改动不能让 Claude Code 这条线跑不起来。整案测试走按量计费：10-03 用户批准开发期额度 50 元，额度内由 Opus 按需跑、事后报（单价与记账口径见[模型与费用](../workflow/models.md)）。
- **首批整案后移（10-03 用户与 Opus 商定）：** 原定迁移前跑的首批整案（sm24、Voimatalo）整批后移。sm24 一例原用冻结旧工具，改为工具改进落进新底座后，作为“开发模型调度 27B”的第一步；Voimatalo 等部分推理框架定了再安排。切 27B 的路径按用户意思：先开发模型调度 27B，再由工作模型替换开发模型的调度（即阶段 5），具体做法届时再商量。
- **迁移后的改进待办**（10-01 亲做三例与 10-02 讨论攒下）：平面差异检查补双线墙漏报、写明“0 条差异”的范围；检查墙是否按标注尺寸落位；工具参数可选值写全、剖面查不到时给提示；上下层对齐与细条检查（阶段 4 全楼检查包）；命名两处缺口（阶段 4 命名包）；评价侧约定差分类与规整前后两份报告。T1 的逐扇核对、逐面清点届时并入阶段 4 全楼检查包。

**顺序（10-03 更新）：** 格式补救与同时派发、立面并发小实验已完成 → 迁移对照（10-03 获批并启动）与 T1 的 sm25 收口测试同时进行 → 迁移对照通过后，T1 有用部分合入主线、两底座同一版 Agent，即迁移完成 → 首次独立审查（两边旗舰各自，用户定在迁移成功后） → 在新底座上用 GLM-5.3-Flash 做改进待办（含 Opus 亲做三例攒下的各项）、sm21 等测试、阶段 4 三包、提速（并发从立面扩到逐层起草，加代码预处理，提速测试后定正式时间规则） → 切 27B：先开发模型调度 27B（后移的首批 sm24 为第一步），再由工作模型替换开发模型调度（阶段 5）。

## 八、主要风险

- 接口兼容的细节：工具调用编号、图片格式、思考字段，各家部署不同。
- 图片缩放、压缩丢掉证据；摘要改变事实。
- 子任务把错误和费用放大。
- 远端模型无法完全冻结：锁住客户端版本和模型名字，不等于锁住远端模型。
- 推理侧架构尚未定型，探索结果可能要求回头修改共同设计。阶段 0 只定已确认需要的接口，为此留出空间。
