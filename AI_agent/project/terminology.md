# 名词规范

**状态：10-02 草案，待用户确认。** 确认后，新写的文档、代码、报告和对话都按本表取名；旧文档不集中改写，改到哪里顺手统一。BIM 里各构件怎么起名（F1、房间名、逆时针编号）是另一回事，见 [BIM 命名](../design/bim_naming.md)。

用法：一个概念只用一个中文称呼和一个英文名。新代码用英文名；已有的旧标识符写在“说明”里，不为改名去改旧代码。“不再用”一栏是容易混的旧说法。

## 一、四条总规则

1. **单说“模型”只指 AI 模型。** 建筑模型一律说 BIM（源 BIM、轻量 BIM），不说“源模型”。
2. **“档”必须带前缀：** 模型档（主力档／Flash 档）、细度档（精细档／粗档）、思考档（low 到 max）。
3. **“声明”拆成三个词，单说“声明”不再用：** 建筑概况（用户填的结构化信息）、定位观测（claim，模型记的带位置的观测）、建模声明（模型写给代码展开的结构化描述）。
4. **“主线”只指 Git 的 `main` 分支。** 还原、部分推理、完全推理三个研发方向叫“研发线”；旧流水线的 Stage 0–5 编号停用，“阶段”只指[开发计划](unified_agent_harness_plan.md)的阶段 0–5。

## 二、产品与系统结构

`建模 Agent = 模型 + 工作套件`，工作套件 = 运行底座 + 建筑共用层 + 几何内核 + 工具 + 方法模块 + 指引。

| 中文 | English | 指什么 | 不再用 |
|---|---|---|---|
| 建模 Agent | BIM Agent | 本项目的产品：把一栋楼的各种资料变成轻量 BIM 的那一个 Agent。还原、部分推理、完全推理都由它完成 | 总 Agent、管线；“统一 Agent”只作强调 |
| 工作套件 | harness | Agent 里除模型以外让它完成任务的全部支撑（09-14 所说的“工作 kit／harness”） | 工作 kit、kit |
| 运行底座（简称底座） | runtime | 工作套件中与建筑无关的部分：模型接口、工具执行、角色调度、上下文管理、事件日志、预算与恢复。计划自建，以后可开源 | 基座、底座核心 |
| 建筑共用层 | building layer | 三条研发线共用的建筑部分：源 BIM 的结构和修改规则、依据与需求记录、建模声明、检查与规整、覆盖清单、角色目录与证据包 | 建筑层、BIM 层 |
| 几何内核 | geometry kernel | 确定性的几何计算：编译、装配、挂门窗、规整、切配。主要在 `src/agent/geometry` | 内核（单说） |
| 工具／工具集 | tool / toolset | 模型能调用的单个功能（看图、量测、建模、修改、检查、交付）；全部工具合称工具集，现以 MCP 提供 | 工具箱 |
| 方法模块 | method module | 针对一种输入的做法：图纸、三维网格、照片、文字。各含一段指引和专用工具，按问题组合，不按研发线固定 | 读图方法（泛称时） |
| 指引 | guidance | 写给模型看的全部文字，分五种：系统提示、任务说明、参考资料（`get_bim_reference`）、工具说明、工具反馈 | 指令层、说明层、操作指南、工具说明书 |
| 角色 | role | 按功能定义的一类工作：职责、可用工具、输入、返回、预算。现有协调、局部观察；计划中单层起草、方案推断、复核 | 子模型 |
| 协调角色 | coordinator | 掌管整案、派子代理、应用修改、决定交付的角色 | 主控 |
| 局部观察角色 | local observer | 只读：就一处局部回答带定位的观察，不改源 BIM（现有 `review_detail`） | |
| 子代理 | sub-agent | 运行中由协调角色派出的一个角色实例，有独立上下文 | |
| 证据包 | evidence package | 派给子代理的材料：问题、已知事实、图或 view_id、裁剪与坐标换算、源 BIM 版本、返回格式、预算 | 材料包 |
| 模型路由 | model routing | 把角色绑定到具体服务、型号和参数的配置；每个角色有默认模型、推荐模型和已验证范围 | 选模表 |
| 运行器 | runner | 现有运行入口 `run_bim_agent.py`：准备输入、提供工具、启动客户端、收结果。以后由运行底座接管 | |
| 桥接器 | bridge | `bim_agent_bridge.py`：让开发助手直接调用同一套工具 | |
| 查看页 | viewer | 源 BIM 的 HTML 交互查看页 | |

## 四、任务与输入

| 中文 | English | 指什么 | 不再用 |
|---|---|---|---|
| 信息充分程度 | information sufficiency | 输入能确定多少建筑信息；三种说法没有明确边界，只用于研发分工和评价分类 | |
| 还原建模 | reconstruction | 资料基本齐全，主要是识读、对齐、规整 | |
| 部分推理建模 | partial inference | 有部分可用约束，重要部分要推断；也可能带图纸、要求较细 | |
| 完全推理建模 | full inference | 信息很少，典型输入是楼的一张或几张照片 | 纯文字推理 |
| 研发线 | work line | 按上面三类划的研发分工：还原线、部分推理线、完全推理线；不是三套产品或管线 | 路线（指产品时）、主线 |
| 建模细度 | detail level | 用户要的简化与合并程度：精细档、粗档（档数待定）；与信息充分程度、后端热区合并相互独立 | 简化程度、粒度、档位（单说） |
| 用户要求 | user requirement | 用户对结果的要求，如细度、授权的简化、用途；单独记录，不当建筑事实 | |
| 输入 | input | 一次任务给 Agent 的全部资料 | |
| 图纸 | drawing | 平面（plan）、立面（elevation）、剖面（section）的图片或 PDF | |
| CAD 图 | CAD drawing | DXF 等矢量图纸 | |
| 三维网格 | mesh | 带贴图的三维体量模型，如 Voimatalo 的 GLB | 带贴图体量（可作描述）、贴图模型 |
| 照片 | photo | 楼的实景照片 | |
| 建筑概况 | building brief | 用户填写的结构化基础信息：用途、位置、面积、层数等（`testdata_prompt.json` 这类） | 建筑基础声明（改名） |
| 文字说明 | text notes | 自由文字的描述或需求 | |
| 案例 | case | 一套固定的测试输入，如 sm21、sm24、sm25、Voimatalo | |
| 参照答案 | reference (GT) | 只用于事后评价的独立参照几何，从不给工作模型看 | 答案、真值 |

## 五、BIM 与产物

| 中文 | English | 指什么 | 不再用 |
|---|---|---|---|
| 轻量 BIM | lightweight BIM | 我们产出的建筑模型这一类东西：空间、边界、开口、关系和依据；口语“丐版 BIM”是同一个东西 | 通用 BIM |
| 源 BIM | source BIM | 一次任务的那份权威建筑模型，各后端都从它派生。代码里叫 `source_model` | 源模型 |
| 空间 | space | 源 BIM 的基本单元：逻辑闭合的空间体。精细档一般一间房一个，粗档可代表多间 | 空间块、区块 |
| 房间 | room | 实际建筑里由实体隔墙围成的房间；空间是它在 BIM 里的表达 | |
| 边界 | boundary | 空间的面：实体（墙、楼板、屋顶）、抽象分界、敞开、未知 | 隔断（泛称时） |
| 开口 | opening | 边界上的门（door）、窗（window）、通道（passage，无门的洞口） | 门窗（泛称时） |
| 空间关系 | space relation | 相邻（共用边界）和连通（经开口相通）分开记 | |
| 热区 | thermal zone | EnergyPlus 等后端从源 BIM 派生的计算分区，不属于源 BIM | |
| 候选 | candidate | 一次运行里每次保存下来的源 BIM 版本，共用候选额度 | 保存稿 |
| 起始稿 | seed | 运行开始时给定的已有版本（恢复运行用） | |
| 平面草稿 | plan draft | 单层平面编译后、装配前的中间稿（`draft_id`） | 草稿（单说） |
| 交付稿 | delivered candidate | 运行结束时由 `finish_bim` 选定交付的候选，连同交接报告 | |
| 建模声明 | modeling declaration | 模型写给代码展开成源 BIM 的结构化描述；现有 `plan_json`、`proposal_json`、参数化 plan、修改操作，计划逐步统一 | 建筑声明（改名）、proposal（泛称时） |
| 回叠 | overlay | 把当前源 BIM 画回原图上对照 | 叠图 |

## 六、依据、检查与评价

| 中文 | English | 指什么 | 不再用 |
|---|---|---|---|
| 证据 | evidence | 能翻看的材料：原图、视图、裁剪、量测结果 | |
| 视图 | view（`view_id`） | 一张给模型看过的图（原图、裁剪、回叠），带编号和哈希 | |
| 依据 | provenance | 源 BIM 里一个值从哪来：观测、推断、简化、假设、用户要求、计算，可同时有多种 | 来源（泛称时） |
| 定位观测 | claim | 带图上位置和视图来源的观测记录（`record_claim`），是模型的解读，不是已证事实 | 声明、高度 claim |
| 推断记录 | inference record | 推断依据的记录（`record_inference`；其字段名 `declaration` 是旧叫法） | |
| 规整 | regularisation | 把低于建模精度的偏差对齐到已有的线；只改尺寸不改实质，留记录 | 吸附（泛称时） |
| 容差 | tolerance | 规整允许的范围，分三层：工具默认、细度档上限、模型裁决 | |
| 检查 | check | 代码做的确定性检查：几何、拓扑、覆盖 | 校验（泛称时） |
| 覆盖清单 | coverage list | 用户要求 → 方案选择 → 实际对象 → 检查结果 → 未完成项 | |
| 复核 | review | 模型做的判断性复查（复核角色或建模后自查） | |
| 评价 | evaluation | 运行结束后、工作模型看不到的打分与诊断，可用参照答案 | judge（中文场合）、评分（泛称时） |
| 实质错误 | substantive error | 漏墙、多墙、错拆错并、假楼板、连通改变 | |
| 尺寸差 | dimensional deviation | 位置或尺寸偏差 | |
| 约定差 | convention difference | 规整或表示约定造成、在容差内的差 | |
| 验收 | acceptance | 用户对结果的认可，或 Opus 对开发阶段的通过结论 | |
| 人工查看点 | review stop | 交付前让人查看、修改、确认源 BIM 的环节 | Stage 2 停点 |

## 七、运行与开发流程

| 中文 | English | 指什么 | 不再用 |
|---|---|---|---|
| 运行 | run | Agent 执行一次任务，编号 runNN | |
| 实验 | experiment | `logs/experiments/` 下的一个目录，含准备、一次或多次运行与评价 | |
| 冷启动 | cold start | 只给原始输入，没有已有版本和答案的运行 | |
| 恢复运行 | recovery run | 从已有版本开始的运行 | |
| 续查 | continuation | 同一运行里模型停下后再追加调用 | 续跑 |
| 行为记录 | behaviour record | 一次运行的完整行为：每步工具调用参数与返回、可见文字、思考、用量 | |
| 事件日志 | event log | 运行底座逐条写下的原始记录；行为报告由它生成 | |
| 重放 | replay | 分三种说清：行为回看（只读记录）、确定性重放（重做工具操作）、重新调用（再请模型，不保证同结果） | |
| 接口小测 | interface probe | 检查模型服务接口（工具调用、图片、思考字段）的极小调用 | |
| 角色小测 | role test | 让一个角色做一个局部任务的小测试 | |
| 整案实测 | whole-case test | 用案例跑完整建模；先报方案，用户批准 | 整案、跑 case |
| 节点回归 | milestone regression | 能力包闭合后确认旧能力没退步的整案实测；先报方案，用户批准 | 回归（单说） |
| 工作包 | work package | 派工单位：谁、做什么、在哪个分支、改哪些文件 | |
| 能力包 | capability package | 一起开发、一起评价的一组改动；修复包、工具改进包都是能力包 | |
| 基线 | baseline | 固定的对照状态：代码标签加运行结果 | |
| 冻结基准 | frozen baseline | 底座迁移对照用的工具与指引版本：`5bb10538`（标签 `checkpoint/2026-10-02-harness-baseline`） | |
