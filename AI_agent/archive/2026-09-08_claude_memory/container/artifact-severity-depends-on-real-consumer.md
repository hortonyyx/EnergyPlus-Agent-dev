**2026-08-14 发单前机械核实，把 F-28 的定性【第二次】改写**（08-13 已改过一次：
从「填错值」改成「漏一格导致整行位移」，见 [[whole-stage-redraw-cannot-fix-systematic-field-confusion]]）。

plan.md 当时写的因果链是：
> 4_mep 交的 `hvac_specs` 是 LLM 手写的**位置敏感 IDF 文本** ⇒ 漏一格 ⇒ 整行位移 ⇒
> **若移过去的值恰好合法，所有门全绿 + EnergyPlus 正常算完 + 结果是错的。**

**前半对，后半错。** 那段文本**从不被贴进最终 IDF**：下游 `src/agent/nodes/hvac.py`
把它当**输入文本**喂给一个 ReAct agent，后者只能通过**具名参数的 MCP 工具**建对象
⇒ **位置在那一层结构上不存在**。

**⭐ 活证据（比任何推理都硬）**：08-13 验收 B 的 `hvac_specs` **少写了两格**
（`50` 落进「排风节点名」、`13` 落进「进风节点名」、`0.015` 落进「最高送风温度」）——
**位移比出事那次还狠**；而它的最终 IDF 里最高送风温度就是 50、最低就是 13，**语义完全正确**。
且最终 IDF 里那两类对象**各 0 个**（全被换成 HVACTemplate 系列）。
⇒ **下游 LLM 是按【含义】重新落位的，不是照抄位置。**

⇒ **真实危害 = 段级门按位置读那段文本 ⇒ 读出不存在的引用 ⇒ block ⇒ 重抽用尽 ⇒ 整条链死**（可靠性），
**不是**静默算错物理。这直接改变了新增门该上什么档位（阻塞 vs 只报告）。

## ⭐ 判别问法

**「这份中间产物的真实消费者是谁？它按【位置】读还是按【含义】读？我核过吗，还是从格式长相推的？」**

推论：
- **格式长相 ≠ 契约**。一段文本「长得像 IDF」只说明它借用了 IDF 的语法，
  ⛔ 不说明任何人会把它当 IDF 解析。**契约必须去找消费者，不能从生产者那头看。**
- **同一个缺陷，在生产端、门那端、消费端可以有三种完全不同的严重度** ——
  报危害时必须说清是哪一端。
- ⚠️ 反向也要诚实：「下游按含义重新落位」是**一份产物上的一次观测**，由下游 LLM 的行为决定，
  **不是结构性保证** ⇒ ⛔ 不得据此声称「位移永远无害」。
