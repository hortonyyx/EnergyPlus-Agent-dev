⭐⭐⭐ **2026-09-05 用户原话**：「**GPT-6 能力较强，且不会过度设计，可以把相对大块的工作一气交给它落地。**」

**Why**：本项目此前的派工习惯是**把一件事切成三四个小单**，动机是防「模型跑偏 / 过度设计」
（历史上 terra / Sonnet / GLM 席位都出现过为了满足一条验收而顺手扩范围）。
用户实测判定**这条动机对 `gpt-6-astra` 不成立** ⇒ 切小的收益消失，而**代价一直都在**：
每道接缝 = 一份派工单 + 一轮跨家族审 + 一次合并 + 一次全量（本批实测一程只能收 1–2 条线）。
⭐ 同日的旁证：astra 的**第一单**（刻度认领设计稿复核）交出 `REWORK / 阻断 5`，
五条全是**拿真实数据量出来的**（含「今天就有 6 条边构造不出 `node_ref`」这种硬事实）。

**How to apply**：
- ✅ **一个自洽的施工单 = 一整条线**（例：A-6a 刻度认领 ＋ A-6b 四分类裁决**一起给**；E-a 端到端接线整条给）。
- ⛔ **「大块」不等于「放松验收」** —— 验收项 / 停报分层 / 禁令清单一条都不减。
  块越大，**停报分层越要写清楚**（承重前提错才停 · 外围数值错只记）。
- ⚠️ **额度是它唯一的现实约束**（见 [[gpt-seat-blocked-by-provider-security-filter]] 与家族版图 §1.0）：
  大块作业撞额度 = **一次损失一整条线** ⇒ **派大块前先用一句话探针实测额度**，
  并在单里**写死分段提交**（2026-09-05 GLM 撞额度那次，正是靠分段提交只丢了文档、没丢代码）。
- ⛔ 仍然**不许 astra 审自己施工的东西**（谁写谁不批不变）；它接了整块施工，审就交 Claude 或 GLM。
