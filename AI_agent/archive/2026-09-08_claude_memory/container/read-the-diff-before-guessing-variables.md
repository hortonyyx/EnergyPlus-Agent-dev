**判据（两条，配套使用）**：

**① 排查回归先量 diff 的大小，再决定要不要做实验。**
「跑一轮实验」看起来像在收集证据，其实是**用一小时换一个 bit**（这个变量是不是它）。
如果候选空间是 N 个改动，单变量实验需要 O(N) 轮，而**把 diff 读一遍是 O(1)**。

**② 参照系必须是【几份成功版本的交集】，⛔ 不是【一份成功 vs 今天】的单点 diff。**
单点 diff 必然混入「成功之后才加的」和「加了但无关的」，**只能产生候选**；
只有「在每一份成功里都成立、而今天不成立」的项才配进候选表。

**2026-08-16 实例（EnergyPlus-Agent，reading 质量回归）**：
连查两天、**七轮单变量实验**（各约 1 小时 + 额度）全部 null。
最后一量：读图器真正会读到的改动 `723b0f9..HEAD` = **1221 增 / 46 删 / 14 文件**，
刨掉一个已撤销的大实现只剩 **355 增 / 46 删** —— **一个下午能逐行读完**。
⇒ **我们花七个多小时去猜一个四百行的 diff。**

**②的当场兑现**：orchestrator 用单点 diff 找到三条被删规则，且与失败症状**高度吻合**
（规则是「别把未核实候选写成墙」，而今天每抽都在多画墙 extra=8–12、成功那次 extra=0）。
**多版本一查即倒**：三份成功里**有两份根本没有这三条规则**，照样满分。
⇒ **「时间吻合 + 症状吻合」仍不足以立论。** 同一形状本仓已犯两次。

**⇒ 怎么用**：
- 先跑 `git diff --stat <上次好的> ..HEAD -- <被测环节真正读到的路径>`。**先看数量级再排工。**
- 找出**所有**成功版本（不止一份），确认它们之间该环节是否稳定
  —— 若稳定，那个稳定态就是参照系；**成功版本之间就不一致的东西，不可能是杠杆**。
- **删除行优先于新增行**：成功窗口内往往是纯增量，之后的删除格外可疑。
- 只有过了交集判据的候选才值得花一轮实验。

**⚠️ 配套的人身教训**：同日 orchestrator 被用户连纠三次，**三次同一形状 = 没查数据就给解释，
而数据就在仓里**（最刺眼的一次：另一个模型家族的满分 run 一直躺在仓库目录里，是用户提醒才去查的）。
⇒ **给「为什么会这样」的解释之前，先问「支持/推翻它的记录在不在仓里，我查了吗」。**
