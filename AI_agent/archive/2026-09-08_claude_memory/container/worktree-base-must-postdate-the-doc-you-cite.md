⭐⭐ **2026-09-04 实犯**：我在派工单里写「**开工第一件事读指南 §十四/§十五**」，
而给席位建 worktree 用的基点 `e9a45226` **早于我当天写那两节的提交** ⇒
**席位树里那两节根本不存在**（`grep -c 十四` = 0）。

**席位做对了**：它按 B 层如实上报「派工单指名的章节实际不存在，已读相关章节替代，
若派工方本意指别处请点名」。⛔ 它没有猜、没有沉默。

**后果差点很贵**：设计稿把「一档」**收窄成「必须是尺寸链的 `cum_mm` 节点」**，
而权威口径当天刚被用户补成「**节点，或由链算出来的值**」（累加 / 分段相减 / 轴线±半厚）。
⇒ 若直接转成施工单，这个收窄会**焊进契约**。

**是什么救的**：把设计稿送**跨家族审**，并在复核单里把「**逐条 delta 核对**」列为第一任务
（⛔ 明确写「不许笼统说『基本一致』」）。复核方一次挖出 **5 条「因未读到而遗漏」**，
含裁决账未进契约、第一步/第二步响应面无类型隔离、两个颗粒度未各自声明各自消费。

⇒ **两条纪律**：
1. ⭐ **建 worktree 前先 `git log --oneline -1` 对一眼**：基点必须**晚于**单里点名要读的每一份文档的最后一次提交。
   最省事的做法 = **基点就用 `HEAD`**，除非有明确理由要旧基点（如避开在飞席位的改动面）。
2. ⭐⭐ **凡「作者没看到某份权威材料」被发现，⛔ 不要立刻重写** —— 先让**跨家族审做一次 delta 核对**，
   它比重写便宜，而且顺带体检了整份稿子。
