**2026-08-04 实际发生（orchestrator 自己犯的）**：GLM 施工席 05:59 撞额度中断，
**r2c-2 的测试改动已写在工作树、未提交**。orchestrator 06:30 收工执行 `git add -A && git commit`
⇒ **把它扫进了那条「管理文档同步」的 wrap-up 提交并推上 origin**
⇒ 提交信息与内容不符，且向用户汇报「三条 MINOR 全没做」**多报了一条**。

**Why**：收工 ritual 要求 commit 本轮全部改动 + push；但「本轮全部改动」在**有并行席位**的场景下
≠「我做的改动」。我当时只核了三项边界（未 push / 未碰 gt / 未动管理文档），
**没核「工作树里有没有别人的半成品」**。

**How to apply**：
- **收工提交前先 `git status` 通读一遍**，逐个确认每个改动属于本次提交；
  ⚠️ 施工席正在跑时别在主仓库跑 `git status`（抢 index 锁），**要等它退出后再看**
  （见 [[codex-mcp-idle-timeout-and-cli-channel]]）；
- 席位**中断/额度耗尽**时尤其要查：它很可能"做完没存"（派工单虽写了「做完一件存一件」，中断点仍会有残留）；
- 真扫进去了：**⛔ 不 force push 改历史**（项目禁令），改为在轻门报告 + 执行日志 + plan.md **如实登记**，
  并核对「已验证的状态」与「推上去的状态」是否一致（本次一致：全量 2096 跑的就是含该改动的工作树）。

## ⭐ 2026-08-07 反向同型：**漏掉**该提交的文件（不是扫多，是扫少）

额度窗中断时 orchestrator 代施工席紧急提交 F-9 成果，**只提交了两个 `src/` 文件，把新增的测试锁文件漏在未跟踪**
⇒ **修法落库但锁没落库**（后由下一席位发现并补 `test_lock_recovery`）。

**为什么漏**：提交前那次 `git status --short` 用了
`grep -vE "^\?\? case_tests/.../run_2026-08-0[45]" | head -12` ——
**过滤器是按 08-04/05 调的，而当时的噪声来自 08-06 的目录**，`head -12` 又把真正要看的新增文件截掉了。

**How to apply**：
- **提交前通读 `git status` 必须是完整通读** —— ⛔ 不许 `head` 截断、⛔ 不许用「按上次噪声调的」过滤器。
- 想降噪就用 `git status --short --untracked-files=all | sort -k1,1`（按状态分组），**看完整输出**。
- **代他人提交时，先问「这次改动应该包含哪几类文件」**（改了 src 就该有锁），再拿清单对 `git status`，
  ⛔ 不要反过来"看到什么提交什么"。

**在飞的席位是【半句话】** —— 提交它等于把一个语法都可能不完整的中间态钉进历史，

**How to apply（硬口径）**：

  逐行确认每个文件都是自己改的。⭐ 本次正是这一步抓住的。
- 派工前就把边界想清楚：**主控推进的并行工作要挑与席位零文件重叠的**（本次挑对了，
  错的只是暂存动作）。
