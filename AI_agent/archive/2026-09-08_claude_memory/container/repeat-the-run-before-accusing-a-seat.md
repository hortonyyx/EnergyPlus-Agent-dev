**⛔ 判据：凡要下「某个席位报的数不对 / 虚报 / 没跑」这类结论，先把那条测试重复跑几次，再开口。**

## 2026-08-20 实犯经过

1. sol（施工席）报「全仓 2918 绿、退出码 0」。
2. GLM（审阅席）实测「2917 绿 + 1 红」，判 **BLOCKER：虚报坐实**，并点名了那条红锁。
3. 我自己跑，也是 2917 + 1 红 ⇒ **当场对用户说「GLM 的指控成立」**。
4. 继续验归因：摘掉 sol 的改动 → 锁绿；还原 → 锁**又绿了**。同一棵树、`cmp` 逐字节确认文件相同。
5. 重复跑 6 次：**1 绿 5 红**。固定 `PYTHONHASHSEED` ⇒ **6/6 稳定** ⇒ 根因 = 哈希序依赖。
6. ⇒ **三方观测全是真的，没有人说谎。** sol 抽到那 1/6 的绿样本、如实报了；
   GLM 连抽三次红（约 58% 概率）。**指控与 GLM 的定性双双被推翻。**

## 为什么第 3 步是错的

那一次实测**与「虚报」和「测试在抽签」两种解释都相容**——它**区分不开**这两者。
真正把它们分开的是第 5 步的**重复跑，只花了 90 秒**。
⇒ 同族 [[one-shot-acceptance-bar-kills-false-claims]]（一次跑出来的绿不是证据）——
**这条是它的反面：一次跑出来的红，同样不是证据。**

## 连带的两条

- **成本极不对称**：重复跑 90 秒；冤枉一个席位则污染协作记录、并可能据此退回一批本来正确的活。
- **⭐ 它还解释了一桩老悬案**：当**基准本身来自一次抽样**时，你会永远在追一个不可复现的数。
  sm24 那个签字 DXF 哈希、以及 07-07 那个卡了六周说不清的 9/9，是同一个毛病。
  见 [[baseline-unauditable-dont-chase-its-number]]。

## 现场留下的第二条判据

**「摘掉改动 → 绿；还原 → 也绿」本身就是不确定性的信号。**
neuter 的正确读法是：还原后**必须**回到还原前的结果；回不去就先怀疑测试，别急着怀疑人或代码。
