# 迁移对照：sm24，GLM-5.3-Flash，新底座对 Claude Code（10-03）

用户 10-03 批准（“这个批”）。目的是看同一个 GLM-5.3-Flash 改经 Paratera、在新底座上单跑 sm24 时，底座本身会不会让结果变差。通过即满足[开发计划](../../../project/unified_agent_harness_plan.md)第七之二节的迁移条件 2。

## 条件

- 启动：`PYTHONPATH=$PWD python -m src.agent.runtime_r1_preparation launch AI_agent/logs/experiments/2026-10-03_runtime_r1/configs/migration_sm24_glm_paratera.json --case sm24_glm_paratera`，11:13 UTC 启动。输出在 [`../2026-10-03_runtime_r1/runs/migration_sm24_glm_paratera/`](../2026-10-03_runtime_r1/runs/migration_sm24_glm_paratera/)。
- 与 10-02 基线（Claude Code＋GLM 订阅，[`2026-10-02_sm24_glm_baseline`](../2026-10-02_sm24_glm_baseline/)）相同的部分：五张原图（哈希逐一相同）、任务正文（SHA-256 `a05ae6d5…`）、冻结绘图指引（`9ca4fdcd…`）、45 个工具实现文件（评分前逐个核对与基线相同）、24 个候选、3000 秒、无委派、无续查、无重试。
- 已知差异：思考档用 high（订阅为 medium，Paratera 不提供 medium）；temperature 1.0（订阅路线未报告）；服务走 Paratera 而不是智谱订阅；硬停为 60 次请求或 400 万 token。

## 判定口径（开跑后、出结果前写定）

这是单次对单次的比较，只判断底座有没有让结果变差，不得出稳定性结论。

1. **底座本身**：运行正常结束或到点交出结果；记录完整（每次请求和响应、工具调用和返回、图片引用都在）；没有底座引起的失败，例如请求格式错误、记账误停、工具结果被截断或改写。
2. **质量**：房间一一对应，没有错拆错并；门窗挂墙和门连通跟基线一样全对；门窗位置和外部高度比基线少不超过 2 项（基线位置 20/21、高度 12/14），每少一项都要查清原因。不过线时先按行为记录找原因：由底座引起的（例如图片被缩放、上下文压缩丢了信息）算不通过；属于模型取样差异的另行记录，必要时在额度内再跑一次同条件对照。
3. **时间与花费**：在 3000 秒内完成。用量报两个数：接口实报的 token，以及按账单单价折算的金额（图片 token 在账单上另计，见[模型与费用](../../../workflow/models.md)）。

## 评分方法

`evaluate_migration.py` 只做评分，不调用模型。新底座把冻结工具服务的运行目录放在 `bim/` 下，而 10-02 的检查读的是 Claude Code 运行器写出的文件。脚本先把 `bim/` 复制到临时目录，只补这些检查需要读取的字段，并标明这些字段由评分适配写入；然后原样调用 09-23 原图平面审计、按 GT 的外部门窗高度诊断和 09-30 跨例评分。运行目录本身不做任何改动。底座方面的事实（模型、请求数、token、图片、耗时、工具报错、记账事件）直接从新底座的事件记录里读取。

## 结果

### 第 1 次（11:13–11:31 UTC）：底座停跑，没有出结果

- 第 12 次请求时，模型思考了 16,377 token，把 16,384 的输出上限全部用完（finish_reason=length）。可见文字只有半句，也没有工具调用。底座把截断当作协议错误处理，直接停掉了整个运行（`incomplete_response`），没有任何补救。
- 停跑之前一切正常：12 次请求、20 次工具调用，其中 2 次剖面工具因参数错误失败，属于模型侧，基线也有同类报错。模型还在读图阶段，没有保存候选稿。接口实报 478,174 token（其中缓存命中 86,144），按账单单价折算约 0.49 元，不含图片。评分记录见 [`evaluation_attempt_01.json`](evaluation_attempt_01.json)；完整运行记录压缩为 [`evidence/attempt_01_run.tar.xz`](evidence/attempt_01_run.tar.xz)（6.1 MB，406 个文件，逐个哈希见 [`attempt_01_manifest.json`](evidence/attempt_01_manifest.json)），被截断的那次回复另存为 [`attempt_01_request_12_truncated_response.json`](evidence/attempt_01_request_12_truncated_response.json)。账单逐行见 [`paratera_bill_2026-10-03.csv`](paratera_bill_2026-10-03.csv)。
- 被截断的思考是连贯的分析，没有原地打转。截断前，模型已经写明下一步要一次发出 5 个工具调用。
- 与基线对比：Claude Code 的单次输出上限是 32,000（基线记录 `maxOutputTokens`）。基线自己也有一轮思考约 1.96 万 token、另一轮约 1.37 万。**停跑是两个底座因素共同造成的：新底座的输出上限只有基线的一半，而且一遇到截断就停。按判定口径第 1 条，记为底座引起的失败，本次不通过。**
- 更正（10-03 下午，看过第 2 次数据后）：起初我拿基线前 12 段思考（约 5.6 万）去比本次前 12 轮（约 5.1 万），据此认为思考档不是问题。这个比较方法不对：基线 44 轮里有将近一半根本不思考，那 12 段其实跨了更多轮。按轮次算，基线整轮总输出约 6.6 万，平均每轮约 1.5k；本次 high 档平均每轮约 4.3k，第 2 次约 7.7k，是基线的 3–5 倍。所以输出上限要对齐，思考档也要按实测对齐，后者见下文校准。

### 第 2 次（11:34 UTC 起）：只改输出上限

配置见 [`configs/migration_sm24_glm_paratera_output32000.json`](configs/migration_sm24_glm_paratera_output32000.json)，和原配置只有两处不同：输出目录，以及输出上限（16,384 → 32,000，与基线一致）。截断补救（截断后提示模型继续，而不是整轮停掉）另交新底座跟进，不在这次对照里改。

**第 2 次结果（11:34–12:24 UTC）：50 分钟时限到被截停，不通过。** 评分见 [`evaluation_attempt_02.json`](evaluation_attempt_02.json)，完整运行记录压缩为 [`evidence/attempt_02_run.tar.xz`](evidence/attempt_02_run.tar.xz)（15.9 MB，987 个文件，哈希见 [`attempt_02_manifest.json`](evidence/attempt_02_manifest.json)）。

- 慢的原因与服务出字速度无关（两边都在每秒 50–56 token 左右），是模型每轮想得多：22 次输出了 15.5 万 token，平均每轮约 7k；基线 44 轮总共约 6.6 万，平均每轮约 1.5k。另外，新底座里模型每轮平均调用约 3 个工具，基线约 1 个。底座自身开销约占总时长的 5%。

### 思考档校准（12:16–12:24 UTC，6 次请求）

[`calibrate_effort.py`](calibrate_effort.py) 把第 2 次的第 5、8 次请求原样重发，只改 reasoning_effort，结果见 [`effort_calibration.json`](effort_calibration.json)：

| 请求 | 原记录（high） | high 重发 | low | 不指定 |
|---|---|---|---|---|
| 第 5 次 | 16,422 | 5,128 | 4,685 | 5,765 |
| 第 8 次 | 12,056 | 19,412 | 12,285 | 17,583 |

三档差别很小，同一档重发两次却能差 3 倍。Paratera 很可能不理会这个参数，换思考档解决不了时间问题。

### 思考回传（待验证）

新底座会把此前每一轮的 `reasoning_content` 原样回传进后续请求：第 2 次的第 8 次请求带着约 10.9 万字符以前的思考，第 17 次带着约 8.4 万。Anthropic 格式的 Claude Code 路线不一定这样处理。[`calibrate_echo.py`](calibrate_echo.py) 把第 8、17 次请求中以前的思考删掉、其余不变，各重发两次，看思考量是否明显下降。
