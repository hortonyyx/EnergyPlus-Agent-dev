## B. 修改：在原有一次高度写入前补齐可追溯的定位

新增 `src/agent/runtime_roles/height_evidence.py`，只由分工专用 `height_writes.py` 调用。现有原子依据事务保持，一次批写仍只产生一个高度候选。

1. 以不可变读图交付的横向标定为准。竖向优先采用两条分离的、带图像依据的水平标高带；排除假设、竖向尺寸链整块框及过厚的区域。带中心确定标定，带厚度给出定位不确定范围。
2. 若只有一条可用标高带，按横纵等比例像素估计竖向尺度，且至少两处独立门窗原框必须同时支持读到的上下沿高度，否则不写定位标定。这是有条件、明确记录的估计，不是新读图观测。run6 东面及 run3 北面使用该分支，其余安全匹配面使用两条标高带。
3. 只为安全匹配的图像读数制作原图上下文框。水平边距来自原匹配器的位置和宽度容差（默认 `0.35 + 0.25/2 = 0.475 m`），竖向边距来自标高带的不确定范围。函数不接收 BIM 顶点，不按候选位置倒算“恰好通过”的框。整图框、包住另一份完整读图门窗框的区域、原框不支持其像素/高度读数的对象不补定位。
4. 将原图哈希、任务及交付哈希、原框、上下文框、边距、标高带和推导方法一起保存到原覆盖检查已有的 `elevation_reviews/review_*.json` 标定入口及高度操作收据。记录明确写出没有新增视觉观察。相同输入使用相同标定身份，重复调用复用；后来的显式人工标定仍可按原规则覆盖它。

图像字节需同时与输入清单和读图任务一致。不能定位的读数仍保留原依据，覆盖表继续如实报告。没有改覆盖判定、没有填西面缺失证据、没有改原图或读图交付。上述边界与“无引用的后续改高会失去覆盖”有定向行为检查。
