# 冻结试验后暴露的问题与离线修复

两组开发模型都使用 `frozen_runtime.tar.gz` 中的首版公共代码。下列改动发生在测试开始后，**没有送入运行中的模型，也没有改变其候选**；离线验证不计作开发模型或工作模型成功。

## 跨层空间的楼层归属

6 Sol 用参数化模板生成独立连续交通核，物理实体和逐层门连接存在，但公共参数展开器没有把 `spanning_space_ids` 传入楼层。模型从普通层总轮廓扣除了核心，导致分层平面漏显示核心，普通层的声明成员也不完整。

公共源协议本来已支持跨层成员；6.1 Sol 的直接方案使用了该字段。修复只为参数化 `instances[]` 增加可选 `spanning_space_ids`，接受已展开全局 ID，例如 `CORE:core`，原样交给源内核校验。不推断归属、不克隆或拆分空间，不自动改轮廓。说明同步区分：核心在楼层总轮廓内，在局部普通房间多边形外。

两层加一个连续核心的合成源验证通过，二层平面真实包含核心，未知／重复／高度不覆盖的引用被拒绝。参数展开与源导出相关16项检查通过。

## 门位摘要没有揭示批量居中

6 Sol 已读到不要机械居中的说明，也调用了实际源审计，但最终184个普通门中176个精确居中。首版完整审计有每门两端净距，摘要只有范围，容易掩盖重复模式。

现在完整审计增加门中点在宿主线上的归一化位置和距宿主中点偏移；摘要直接给出已测数量、数值居中数量及最多6个示例ID。`1e-6 m` 仅用于判断坐标数值相等，不是建筑尺度、规范或验收阈值，工具不自动挪门。合成居中／偏置／宿主倒向的4项审计测试通过。是否能让模型实际返工尚待新的独立试验。

## 精细档的房间粒度需要落实到解释

首版只说窗节奏是线索，不能普遍一窗一房，未充分传达已校准的精细偏好。6 Sol 由此选了普遍两窗的普通办公室带。通用方法段现替换为：在精细档、重复独立办公室的合理解释下，从可用尺度的一窗组／开间一房开始；多窗大房间保留功能或空间理由，合并应声明，已知开敞空间仍保持完整。没有写入此楼坐标、固定房间数或所有建筑一窗一房的规则。

## 未建成窗无法通过局部接口撤回

6.1 Sol 首稿两扇推断窗落在附楼相接的墙上，源内核正确报告无外墙宿主。模型按正确 ID 使用 `remove_opening` 撤回，却得到 `found 0`：该操作只搜索 `geometry.openings`，两个声明仍在 `geometry.windows`。模型随后重新提交完整方案自行绕过缺口。

最小修复针对提案中的全局唯一开口 ID，同时支持窗、门和通道，保留删除前记录及理由后正常重建；不直接编辑派生 `unbuilt_openings`，不把删窗当作宿主报错的默认解法。已实现窗口／门／通道联合唯一定位，记录实际集合，修订范围审计也正确识别 window 与 opening 删除。提案编辑及范围审计52项、源导出7项通过；两扇真实失败窗的纯内存重放也得到源检查通过、未建开口为0。没有改写模型原始候选。
