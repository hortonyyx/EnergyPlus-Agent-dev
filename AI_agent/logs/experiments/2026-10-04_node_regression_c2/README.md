用户 10-04 批准：“ok，批准，跑吧”。范围按提请：新底座经 GLM 订阅（medium）跑当前版 sm24、sm25 各一次；同版 Claude Code 跑 sm24 一次作同期对照。Agent 版本 `t1-20261003-c2.1`（主线 `101d39c0`）。

## 条件

- **新底座**：配置 [`configs/runtime_subscription.json`](configs/runtime_subscription.json)。任务正文取 10-02 基线原文，只把预算句改为 6000 秒，与 Claude Code 线逐字相同；`reasoning_effort: medium`；上下文只追加、估算 15 万 token 压缩；临时故障最多重试 2 次；输出上限 32,000；24 个候选；楼层图显式声明。硬停（请求 150、工具 300、token 1,500 万）只是保护线。
- **Claude Code**：[`claude_code.py`](claude_code.py) 原样复用 T1 启动器（同原图、同任务、medium、24 候选、无委派与续查、6000 秒），只把预备记录和运行目录换到本目录，T1 的旧运行不覆盖。预备时探测到的 42 个工具是完整目录；实际启动带 `--enabled-only`，模型看到 40 个，与新底座相同。
- **已知差异**：Claude Code 走智谱 Anthropic 兼容端点、自适应思考；新底座走 OpenAI 兼容端点、无自适应开关。
- **顺序**：sm24 两条线同时开跑（同一时段、同一订阅，服务状况相同）；两者结束并核过回执后，再单独跑新底座 sm25。遇到额度用尽即停，不补跑。

## 判定口径（开跑前写定）

1. **底座本身**：正常交付或到点交出最近完整稿；记录完整；没有底座引起的失败。临时故障被重试救回的次数单列。
2. **模型每轮看到的量是否接近 Claude Code**（本次的主要问题）：每次请求平均输入 token、缓存命中占比、每轮平均用时、每轮平均输出。新底座缓存命中与 Claude Code 相差在 20 个百分点以内、每轮用时在 1.5 倍以内，记为“接近”；否则写明差在哪里。
3. **质量**：sm24 看房间一一对应、挂墙、门连通、门窗位置、外部高度，对照 10-02 基线（20/21、12/14）、T1 sm24（19/21、14/14）与同期 Claude Code；sm25 对照 T1 sm25（Claude Code，一层 14/14，二层多拆一间，位置 41/61，高度 25/34）。每次单次样本，只判有没有明显变差，变差的要按行为记录找原因。
4. **时间**：6000 秒内交出完整全楼稿。

- **按判定口径第 2 条：** 缓存差 26 个百分点、每轮用时 2.3 倍，**仍未达到“接近”**，但比清理前明显缩小（缓存从约 10% 到 66%，每轮用时减半）。相邻请求的消息序列核对过：每次都以上一次为前缀，只有末尾的状态消息不同，所以剩余的缓存未命中不是我方前缀造成的；新底座请求间隔 1.5–3 分钟，Claude Code 约 26 秒，智谱这条端点的缓存在长间隔下多次没命中。剩下的主要差距是思考量：medium 下每轮仍有 4–11k 的大轮，Claude Code 有自适应思考，将近一半轮次不思考。下一步提速首选：让新底座走智谱的 Anthropic 兼容端点（与 Claude Code 同协议，可用自适应思考）。

- 两条线都没有遇到服务端临时故障，重试路径这次没有被触发。
