# run04 源 BIM 与局部委派复核

## 结论

`candidate_01` 正常完成并交付了可查看源模型（8 空间、52 条边界、11 门、11 窗、11 连接）。本轮把走廊两侧的纵向边界从 `x=3.767/5.843m` 改为 `x=4.180/5.820m`；这项物理修改确实改善了源分区。独立 GT 中，内边界缺失/多出长度由 `40.086/40.065m` 降到 `15.560/16.494m`，左侧 MeetingDining、Office2、Office1 三个空间由 severe 变为容差内一致。

整案仍为 **severe**。东侧三个空间的横向分隔及走廊折转沿用了 seed；BottomRightOffice、Corridor、MeetingRoomBig、TopRightRoom 仍超出分区容差。自洽检查通过只说明修改后的空间和开口可装配，不代表图纸还原已经通过。

## Haiku 是否读对、是否被正确采纳

本次子问题有界，但不是独立数字转录：父问题已经给出上下两组尺寸链数字，并指定询问下链两个内部分界 tick。因此 Haiku 只能复核 tick 位置和其上方图线，不能作为链数字或链身份的独立证据。

Haiku 的关键量测没有读对。原图下链两处内部分界约在 `x=400px` 和 `x=460px`；它回答 `x=385–390px`、`x=505–510px`，第二处偏差尤其明显。它只做了两次 1 倍、带网格查看，没有按 system prompt 使用高倍率干净裁图，也没有返回标签框、同一尺寸线及相邻延长线端点；“两处上方都是墙、不是洞”的结论也建立在错误 x 位置上，不能作为可靠图证。

Sonnet 后续采用的是自己从原图得到的约 `x=399/460px`，没有采用 Haiku 的坐标，所以最终正确移动不应归功于子观察。操作 reason 和终答却称 Haiku “independently confirmed”并与父读数一致，这一表述过度：两组像素并不一致，子回答也没有独立核验已预填的尺寸链。此次说明 Sonnet 自主选题和主读图有效，Haiku 没有提供可靠的增量证据。

## 实际物理变化

- 七个走廊侧门随宿主墙只平移 x，平面宽和高度保持：左侧四门从 `x=3.767` 移到 `4.180m`，右侧三门从 `5.843` 移到 `5.820m`。其中 `D_Corridor_Office1` 的旧宽 `0.74m` 也原样保留，本轮没有重新证明这个宽度。
- `D_Rec_Corridor` 是明确例外：端点从 `[3.90,4.80]` 改为 `[4.37,5.64]m`，宽度由 `0.90m` 增至 `1.27m`，高度保持 `2.10m`。Sonnet 在修改前实际查看了该门的 4 倍局部；原图可见双扇门弧支持“seed 过窄、应加宽”的方向，但独立 GT 不评价室内门坐标，故 `1.27m` 仍是图像支持的局部读数，不是完整评分通过。终答“preserving all door widths/heights”遗漏了这一例外。
- 11 个窗的全部序列化字段未变；11 条连接也完全未变。门、窗和连接 ID 均保留，没有静默删项。所有门高未变，仍沿用既有假设；本轮没有立面或门高复核。
- 七个平移门的原 `door arc` source ref 被统一替换成 `corrected corridor wall face`。物理宽高虽保留，但直接门弧来源的追溯信息变弱，后续局部编辑应避免覆盖未修改属性的已有证据。

## Sonnet 是否查看新源

实际工具顺序为：`revise_bim(candidate_01)` 后约 3 秒调用 `view_candidate(candidate_01, F1)`，再约 3 秒调用 `finish_bim(candidate_01)`。因此它确实打开了修改后由源 BIM 渲染的平面，而非只看修改前原图。此次没有运行 `check_openings`、没有注册或查看原图回叠，也没有查看立面；新源查看能发现明显重叠和宿主脱落，但不足以证明八个受影响门的位置、宽高及全图门窗均已复核。

## 评价边界

`evaluate.py` 在 `summary.json` 落盘后才读取 human-verified typed GT，GT 没有进入父模型或 Haiku 输入。窗与外门坐标结果仍只是等数量、同立面顺序配对的诊断；室内门没有 typed GT 坐标评分。本文没有修改 seed、候选、原图或生产代码。
