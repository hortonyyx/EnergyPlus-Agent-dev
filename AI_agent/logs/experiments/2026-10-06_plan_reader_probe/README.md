# 平面读图员单独实测（10-06，Opus）

**目的：** 路线第 ② 步。D1b 合入后（Agent `t1-20261006-d1b.2`），只让平面读图员读 sm24 一层，看它能否自己交付、交付的稿质量如何；不过关就专门改进一轮。

**条件：** 脚本 [run_probe.py](run_probe.py)。一个读图任务，无调度员模型、无立面读图员、不跑整案；任务正文与 D1、D1b 小测相同，只把请求上限从 24 提到 30。GLM 订阅智谱 Anthropic 兼容线路，`glm-5.3-flash`，medium，输出上限 32768。凭据只读主树 `.env`。Paratera 0，DeepSeek 0。运行前后 Agent 版本核对一致。

## 结果：没有交付

30 次请求用完，约 41.6 分钟（2,495.8 秒），停止原因 `child_model_budget_exhausted`。没有一次试建通过，因此没有可打分的稿。用量：供应商报告输入 642,890、缓存读取 721,024、输出 158,239，合计 1,522,153 token；另有图片估算 178,337 只进保护账本。

前 11 次请求在看图、放大、用像素剖面量墙线，第 12 次请求才第一次试建。之后 17 次试建（逐次分类见 [probe_trials.json](probe_trials.json)）：

| 类别 | 次数 | 内容 |
|---|---:|---|
| 返工申报手续拒收 | 8 | “改动清单与实际改动不一致”或“缺上一稿哈希”。第一份稿字段名全错，改对格式后整份都算“改动”，被要求逐项申报 33–45 项 |
| 格式错误 | 6 | 依次错在 `walls`（应为 `partitions`）、隔墙 `p1/p2`（应为 `points`）、房间种子字段、门窗多余字段 `room`/`space_id`/`facade`，每次只报一处 |
| 几何错误 | 3 | 窗没落在外轮廓线上被当成内窗；把外墙也声明成隔墙 |
| 通过 | 0 | |

**对照：** D1 版本（还没有返工申报手续）同一任务第 4 次试建通过，共 13 次请求，几何很好（之后因交付格式被拒）。

## 判断

1. **D1b 的返工手续在读图员自己起草时是净负担。** 设计本意是“有了一份好稿后，返工只改被指出的项”（D1-A 发现整层重建会冲掉已对的项）。但现在第一份稿只要格式不对，就成了“返工基准”，之后每改一次格式都要逐项申报，申报不准就整次拒收。17 次试建里将近一半耗在这里。
2. **读图员不知道平面稿的确切格式。** 完整格式样例在参考资料 `plan_partition` 一节，读图员指引没有指向它；本次读图员查了另外四节，没查这一节，只能靠报错一个字段一个字段地学。立面读图员的指引自带完整样例，D1b 小测里立面首交 3/3 通过。
3. **墙线取法的说法前后不一。** 指引第 3 步说外轮廓取外皮、隔墙取中线；交付时的 `wall_reference` 却要求全层一种取法。外墙上的窗也没说清必须落在声明的外轮廓线上。

以上转为改进包 D1c 的验收条件，见[验收记录](../../../project/unified_agent_acceptance.md)。

## 同时发现：本机内存

本轮定向检查与实测同时跑时，2 项涉及真实工具服务进程的检查失败；实测还在跑时单独重跑，3 项离线贯通都报 `OpenBLAS ... Memory allocation still failed`。原因是每个导入数值库的进程默认按 16 线程预留数值库线程池：实测单个进程约 535 MB，把 `OPENBLAS_NUM_THREADS` 设为 1 后约 53 MB。分工模式下调度员、试建、各读图员各有工具服务进程，整案时会更多。已改：工具服务子进程默认 `OPENBLAS_NUM_THREADS=1`（`src/agent_runtime/mcp_tools.py`，显式设置仍优先），本机激活脚本同样设置。工具服务只做小规模几何计算，不受影响。
