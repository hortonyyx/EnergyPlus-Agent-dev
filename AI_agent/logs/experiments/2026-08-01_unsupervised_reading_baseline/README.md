## 3. ⭐⭐⭐ 结果三：两臂都没有去测量 —— 「给了工具就会去量」再次被证伪，且这次零监督

| 臂 | 实际跑的探针 | 自述 |
|---|---|---|
| A | **0 个**（`out/` 下无任何探针产物目录） | *"No px_per_m scale established yet (CV toolbox deferred); coordinates estimated from **visual inspection**"* |
| B | 2 批（自己跑了一次 prescan + 一次 wall 探测） | *"Interior wall coordinates **estimated from visual layout** rather than explicit dimensions"* |

**A 臂唯一一次尝试标定就被守卫按语法拒了，之后再没试过**：

```
[Bash] probe arguments must be paired --key value; unexpected bare argument: px_m_calibrator
```

它把工具名当位置参数传（`--tool` 漏了），被拒一次，**就整个放弃了标定**，改成目测。

B 臂在探针语法上被拒 6 次（含 `--help` 被拒 ——**它想查接口，被守卫挡住**），
磕出 2 批之后也回到目测。

**⇒ 这是本轮最重要的机制发现，且它与监督无关**：
07-30 时主控还怀疑「不去量」是 directive 措辞或守卫摩擦造成的。
**本轮零 directive、守卫已按参数角色重建、散文误伤已清零 —— 它还是不量。**
⇒ **「量而非看」这条方法论没错，错的是它的落地方式**：
把工具交给模型、指望它自己去量，**不成立**。
这直接支持 plan.md 已登记的**债 #2「B 档：把测量整个移进代码，识图降为在确定性候选上分类 + 查漏」**——
本轮 A vs B（35.8 % vs 0 %）正是该路线的强证据：**确定性给的候选越多，成绩越好。**

### 附带的真实产品缺陷（非监督问题，待修）
- **探针 wrapper 的参数契约对 Haiku 级模型过难**：一次语法失败即导致整个测量环节被放弃。
- **`--help` 被守卫拒绝** ⇒ 模型无法自助发现接口，只能猜。
- `mkdir` / `find` 不在白名单（各 1–2 次拒绝），属可用性摩擦。
