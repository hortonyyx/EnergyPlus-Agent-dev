方向同意。统一 Agent 要落实到**共用建筑对象、依据、声明和检查规则**，不能只共用运行器，再分别长出三套建模流程。

**一、对四条调整的意见**

1. **依据作为一等数据：同意，但要补“用户要求”和计算过程。**  
   用户要求不是建筑事实；计算结果也不是新的观测。例如标注尺寸经过坐标换算、容差规整后落入模型，应保留原值和变化原因。观测、推断与简化可以同时作用于同一对象，不宜做成互斥标签。每个参数最终应能追溯，但可继承模板、对象组的依据，由代码补齐派生关系，不要求 27B 逐字段手填。继续复用 `view_id`、claim 和 `record_inference`；依据修改后，要能找出受影响的声明和模型版本。

2. **建筑层声明语言：同意，但不能把部分推理等同于模板复制。**  
   应在现有建模、参数化和修改接口上统一表达，逐步增加能力，不另起一个包办所有建筑问题的大语言。声明单位可以是一层、一翼、局部房间组，也可以是跨层空间；重复必须允许例外。完全推理还需要表达功能需求、空间关系和方案选择。代码负责展开与计算，建筑取舍仍由模型作出。

3. **共用角色目录：同意，但目录不是固定流水线。**  
   局部观察与转录可以由同一角色完成，精确换算交工具；“复核”还要检查方案是否合理、是否满足用户要求，不能只有叠图。各角色按需调用，不要求每案经过全部角色。首版仍只启用协调和只读局部观察，避免同时验证太多新分工。

4. **全楼检查与覆盖：同意，但“有理由”不能代表“已落实”。**  
   应串起“用户要求→方案选择→实际对象→检查结果→未完成项”。[两次 Sol 验证](/workspaces/EnergyPlus-Agent-dev/AI_agent/logs/experiments/2026-10-01_partial_inference_developer_tests/README.md:3)已经说明：有说明、有检查，仍可能没有落实精细偏好。推理结果还需核对建筑合理性；还原侧则应允许用户明确授权的简化。规整不能抹掉真实错层、退台或窄空间，也不能把精细档机械解释成所有空间都细分。

**二、共同提交用户的开发计划（修订稿，3000 字以内）**

### 目标与边界

建设一个统一 Agent。还原、部分推理、完全推理用于描述信息充分程度和组织评价，不设三套长期管线。同一任务可混用图纸、网格、照片、文字需求，并在不同部位采用观测或推断。

首版验收是：**形成可追踪、可恢复的建模闭环，并完成带图委派。** 初期允许开发模型在 CLI 外层协调，工作角色在自有底座运行；外层请求不可完全控制的部分如实标注。自主工作档协调放到后续阶段。

### 共用结构

- **底座核心**：模型接口、工具执行、角色调度、上下文、事件记录、预算与恢复，不含 BIM 概念。先接 OpenAI 兼容 Chat Completions。
- **BIM 共用层**：同一套源模型、对象身份和修改规则；依据与需求记录、建筑声明、检查与规整、覆盖清单、角色和证据包。
- **方法模块**：按当前问题组合图纸、网格、照片、文字方法，不按路线固定选择。保留已有工具，逐步统一说明为“共用核心＋方法模块＋角色提示”。

依据复用现有引用体系，支持组级继承、计算来源、冲突和未决项。声明支持重复与例外、跨层空间、局部修改；子角色交回建议或声明，由协调侧核对当前模型版本后应用。

### 阶段 0：共同确定接口与验收样例

明确角色输入输出、图片及坐标引用、依据与需求关系、声明边界、事件格式和恢复规则。角色配置包含默认模型、推荐模型及已验证范围，型号可替换。

接口同时用三类离线样例检验：有明确尺寸的还原、资料缺失且含跨层空间的部分推理、只有文字需求的完全推理。另检验混合输入、证据冲突，以及同一输入下不同简化偏好。技术细节双方定稿；新增产品取舍交用户决定。

### 阶段 1：冻结工具的单角色闭环

工具与两套原始说明以 `5bb10538` 为基准；先改变运行底座，保留建模行为的比较基础。

统一事件日志保存实际请求与响应、工具参数与返回、图片内容及引用、服务返回的思考字段、用量、采样参数和各层版本。没有返回的信息明确标缺失。`record.py` 改为读取统一日志，并保留历史格式适配。

历史样本采用 run99/100、Opus 三例及两次 Sol 桥接记录。验收分开：

- 原始记录和附件完整保存；
- 同版本确定性工具重放结果一致，非确定字段明确列出；
- 跨版本历史结果比较对象、几何、宿主和连通，解释差异。

历史日志缺失的内容不补造；重放通过不代表模型能力通过。按需做 Paratera 工具、图片、思考字段接口小测，事后报告用量。

### 阶段 2：长任务与恢复

支持上下文压缩、图片移出当前请求及按原引用取回。压缩后保留用户约束、依据引用、当前模型版本、未决项和待办，原始记录始终保留。

设置 token、金额、时间和调用次数预算；子角色、摘要及重试计入总账。用 60–120 步长记录和故障注入检查：中断前后、图片取回、压缩恢复、预算停止、写操作结果不明。恢复时先核查已保存状态，避免重复修改源模型。

### 阶段 3：带图委派与首版验收

开发模型在外层协调，通过 MCP 使用 BIM 工具和委派工具；底座内先运行只读局部观察角色。

证据包包含问题、已有事实、可用图片或 `view_id`、必要裁剪及坐标换算；输出带定位的观察、依据和不确定项。记录父子任务关系及各模型实际工作，验证子角色确实收到图片，协调侧能够回看并核对。

小测试覆盖图纸、网格、照片，也覆盖无图需求和信息不足；输入种类与推理程度分别列入验收表。

随后提交首批整案方案，建议至少包含还原和部分推理各一例，明确模型、次数、预算及评价口径，由用户批准后执行。首版须展示“建模→检查→针对问题修改→保存可查看结果”，并演示中断恢复和带图委派。

### 阶段 4：增强 BIM 共用能力

阶段 0 定稿后可并行离线开发，完成后分包启用：

1. 依据继承、需求到对象的追踪，以及建筑声明补充；
2. 全楼几何、拓扑和覆盖检查，确定性规整；
3. 命名修正与统一说明层。

不把这些变化与底座迁移一次混入。每包先离线验收，需要整案回归时另报方案。检查既要发现缺失，也要保护真实开敞空间、跨层体量和明确授权的简化。

### 阶段 5：工作档自主协调

把协调角色移入底座，沿用相同对象、声明、工具和评价规则，逐步加入起草、方案推断与复核角色。分别报告强模型辅助结果和工作档自主结果。

完全推理的无图接口在阶段 0 就检验；首个真实探索案例在本阶段前另拟方案，交用户确认。代表案例单次成功只作为探索结果，不据此宣称稳定。

### 分工与交付方式

- **Astra**：底座核心、记录与恢复、三维及部分推理方法；同时负责共同声明中的体量、跨层与推断语义，以及用户偏好落实的验收。
- **Opus**：依据层、声明展开、全楼检查与覆盖的主要实现；图纸方法、还原验收和相关角色题目。
- **共同**：角色、证据包、记录格式、建筑声明和统一说明；完全推理最小接口。共用接口必须同时经还原与推理样例检查，不能由一侧定型后再补另一侧。

共享文件指定主要实现者，短分支开发，共享接口互审；Astra 负责主线集成和统一交接。按阶段交付，不承诺周数。接口小测按已获授权执行并报告用量；整案实测及节点回归先报方案、获批后执行。

**三、明确的分歧**

- **不同意把历史源文件逐字一致作为统一重放标准。** 只有满足同版本、同依赖和确定性条件时才适用。
- **不同意用图纸、网格、照片三种题目代表三条建模路线。** 完全推理的无实测资料接口必须现在就检验，真实探索可以后置。
- **不同意用“推断有理由”作为推理覆盖通过条件。** 必须检查实际保存结果及未满足的需求。
- **共同件应分包启用、分别判断回归范围。** 不建议全部合成一次大变化，再用一次回归解释所有差异。

其余选型、首批角色、辅助模式和按阶段交付的方向同意。本轮仅做只读核对与计划修订，未改代码、未调用模型。
