# Agent 运行底座调研报告

2026-10-02，供 Opus 讨论及用户决策。

本次完成了项目资料、五份源码快照及官方文档的只读核查；没有修改仓库、运行克隆项目、派子代理或调用其他模型/API。以下区分**源码核实、官方说明、设计建议、未核实事项**；没有把功能存在写成实际建模效果已验证。

## 一、一页结论

**建议以现有 Python 原型为起点，建设专供本项目使用的轻量底座；pi 的低层库作为备选。** 优先补齐完整记录、图片与上下文管理，再增加角色委派。三类建模共用底座、工具和源 BIM，通过任务说明、输入和角色配置适应信息充分程度。

底座负责模型请求、工具执行、上下文、子任务、预算和记录；建筑判断仍由模型承担，几何计算和规整仍在工具层。换底座能够减少不可见变量、改善排错条件，**目前没有证据证明它本身会恢复建模质量**。

| 方案 | 一句话定位及对我们的价值 |
|---|---|
| **pi** | 最值得考虑的库级备选：模型适配、循环和上下文接口较清楚；可取低层库，整套 coding-agent 仍需裁剪和补充项目机制。 |
| **DeepSeek Harness** | 最有价值的记录与可恢复执行参考：借鉴事件记录、上下文投影、图片移出记录和子代理契约；当前预览版及插件体系不适合直接作为我们的首版依赖。 |
| **Codex** | 完整工程实现参考：借鉴子代理生命周期、共享预算、历史完整性和图片保留；体量、接口限制与 Python 衔接成本较高。 |
| **Qwen Code** | 多服务和图片处理的参考，也可作为后续对照候选；同属 Qwen 家族不构成更适合 BIM 的证据，整套产品明显偏重。 |
| **mini-swe-agent** | 极简 Python 循环参考：便于理解控制流、停止和轨迹保存；需要另补 MCP、图片证据管理、压缩和子代理。 |
| **Claude Code／Agent SDK** | 现成运行能力与历史对照入口；可定制提示、工具和子代理，但运行器仍会添加系统提示之外的内容，逐字控制受到限制。[官方说明](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts) |
| **我们的原型** | 与现有工具和评价链最贴近、改造边界最小；已经具备基本闭环，尚不具备长任务、多角色与完整行为记录能力。 |

这次快照比派工背景更新：**pi 为 1.0.0，DeepSeek Harness 为 0.2.0-rc.2**。Codex 是主线源码快照，工作区版本字段为 `0.0.0`，不能拿它代替实际发行版号。各快照、许可证和代码规模见附表。

“模型看到的每个字由我们掌控”应分两层落实：客户端发出的消息、工具说明、补充提醒和图片转换全部由我们构造并保存；托管服务内部的聊天模板、隐藏处理及权重更新，需要服务方另行保证。**锁住客户端版本和模型名字，不等于锁住远端模型。**

## 二、对选型有实质影响的发现

### 1. 可改系统提示，不等于可控制整次请求

pi 的底层循环允许自行转换上下文，coding-agent 也有完整覆盖系统提示的入口；但普通自定义提示仍可能与项目上下文、技能等组合。DeepSeek Harness 可以注册完整提示，并单独关闭运行时上下文。Qwen Code 替换基础提示后，外层仍可叠加项目文件、媒体说明和记忆。Codex 也分别管理基础指令、开发者指令、环境与权限等内容。

Claude 官方明确说明：普通 SDK 消息流不包含全部系统提醒；可以通过原始请求日志或受控网关观察实际发送内容。因此，闭源运行器并非完全不可观察，但**普通会话记录不足以证明模型实际收到了什么**。[提示与请求日志说明](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts)

### 2. 图片支持与带图委派，是两个不同能力

几套较大的方案均有工具图片处理，但默认子任务入口往往仍是文字：

- pi 的示例扩展及实验性 durable 子代理，默认都是文字任务、文字回报。
- DeepSeek Harness 的底层委派接口接受多模态内容块，默认派工工具却把参数包装成单个文字块。
- Codex 当前 v2 派工消息是文字，可通过历史继承或工具重读获得其他材料。
- Qwen Code 普通派工参数也是文字；完整图证据能否随不同派工路径保留，仍需专项验证。

对我们而言，需要交付的是“这张原图、这个裁剪区域、这组坐标、这些对象”，并让上层核对实际结果。不能仅凭“支持视觉模型＋支持子代理”认定已经满足要求。

### 3. “OpenAI 兼容”不足以证明可接入

本次 Codex 源码已经移除 `wire_api="chat"`，保留 Responses 接口。因此，只提供 Chat Completions 的本地服务不能直接按旧配置接入；需要相应接口或适配，并核查工具、图片和思考字段。[源码](https://github.com/openai/codex/blob/ca466061d64f0b44f416135c7fd06aa7af850bbc/codex-rs/model-provider-info/src/lib.rs#L97)

pi、DeepSeek Harness、Qwen Code 的服务适配更广，但跨模型续接同样涉及思考签名、工具调用编号、图片格式和上下文长度。Claude 官方也明确不支持通过网关将 Claude Code 路由到非 Claude 模型；现有 GLM 路径可作为项目实践记录，不能视为官方兼容承诺。[网关说明](https://code.claude.com/docs/en/llm-gateway)

### 4. 自有原型已有基础，记录缺口却很具体

现有 `chat_mcp.py` 为 218 行，角色路由为 81 行。它已经实现明确工具集合、图片回传、调用编号检查、模型与工具次数预算、总超时、原始 usage 保存，以及禁用 SDK 自动重试。

历史上的 35 项离线检查还包含真实 SDK 序列化、真实 MCP 服务及合成两房间建模；**模型回复是测试桩，未证明真实模型整案成功**。[验证说明](/workspaces/EnergyPlus-Agent-dev/AI_agent/design/model_configuration.md:42)

当前记录回调没有保存完整请求、中间助手文字和工具文字返回；部分思考字段只是放回内存历史。完整行为记录、持久化、恢复、压缩和子代理都需要继续实现。[请求记录](/workspaces/EnergyPlus-Agent-dev/src/agent/execution/chat_mcp.py:128)、[工具返回记录](/workspaces/EnergyPlus-Agent-dev/src/agent/execution/chat_mcp.py:195)

## 三、自有底座设计建议

以下均为设计建议，尚未实现。

### 1. 保持六个清楚的组件边界

| 组件 | 负责什么 | 主要借鉴 |
|---|---|---|
| 请求组装与模型适配 | 按配置组装消息、工具和参数，处理各服务协议；保存最终发出的请求 | pi；Qwen Code 在服务转换后捕获请求 |
| 工具执行器 | 调用现有 Python MCP，记录完整参数、原始返回和实际模型可见返回 | 现有原型；pi、Codex 的工具执行边界 |
| 上下文管理 | 从完整历史选择本轮材料，压缩旧文字，保留或重新取回图片 | pi 的可替换转换；DeepSeek 的历史投影 |
| 角色与任务调度 | 创建、等待、取消子任务，分配模型、工具和预算 | DeepSeek、Codex、pi durable |
| 记录与文件存储 | 追加事件，按哈希保存图片及大结果，生成现有行为报告 | DeepSeek；现有 `record.py` |
| 运行控制 | 管理总预算、重试、检查点、停止及续接 | mini 的显式循环；Codex 共享预算 |

首版不用实现通用插件市场、复杂分布式调度或完整终端产品。使用普通 Python 模块和明确接口即可；只有出现实际替换需求时再增加扩展层。

几何对齐、容差、切配、拓扑与装配继续放在 BIM 工具层。工具返回计算结果、候选操作和影响范围，模型裁决有建筑含义的歧义。底座记录依据和最终操作，不重新实现几何规则。

### 2. 角色与模型分开，委派围绕证据组织

每个角色定义职责、可用工具、输入材料、返回要求和预算；另由路由配置把角色绑定到服务、模型及推理参数。沿用现有“服务—模型配置—角色”三层关系，未知能力不能因模型名字被默认为支持。

初期可以有协调、局部观察／建模、复核等角色，但不要求每次运行都调用全部角色。协调角色可以先接开发模型，工作角色接 27B；以后换协调模型无需改角色协议。

子任务默认使用独立上下文，收到一个明确材料包：

- 任务目标、相关建筑对象和源 BIM 版本；
- 原图或裁剪图引用、坐标转换、必要工具结果；
- 已知事实、推断、待解决问题；
- 返回格式与本次预算。

返回内容包含结论、证据引用、候选修改、未解决项及产物位置。上层要能打开子任务实际使用的图，并检查保存后的几何，不能把子代理“完成”当作验收。

首版建议让只读观察并行，源 BIM 修改由协调侧统一应用；子任务可以产生独立候选。应用修改时检查基准版本，避免两个子任务覆盖彼此成果。并发和嵌套深度设为可配置的小值，先验证协作有效，再扩大。

**开发模型辅助与工作模型独立完成必须分别统计。** 若开发 CLI 暂时在外层指挥，应标记为辅助模式；要验证整个产品的输入控制能力，协调角色也应进入同一自有底座。

### 3. 长上下文采用“完整历史＋当前状态＋活动窗口”

完整记录永久保留，送给模型的内容可以缩减，两者分开维护：

1. **完整历史**：模型请求、响应、工具结果和图片。
2. **当前状态**：用户约束、源 BIM 版本、关键决定、证据索引和未决问题。
3. **活动窗口**：当前任务附近的消息、完整工具调用／返回对，以及所需图片。

先用确定性方法去除重复大结果、旧版本模型摘要和重复图片，再考虑模型摘要。摘要模型也走同一记录与预算机制；摘要不能把推断改写成事实，不能成为尺寸、对象编号和源几何的唯一保存位置。

图片按任务保留：当前楼层、正在判断的立面、未决问题证据可以固定保留；其他图片变为可重新读取的引用。每次移出或恢复都记录原因。DeepSeek 的图片移出机制很值得借鉴，但其当前策略是收到预算错误后移出，且不会自动恢复；我们应在请求前检查，并支持按证据重新取图。

图片与来源标签、裁剪范围、坐标转换一起处理。保留原始文件与实际发送文件两个哈希；缩放或压缩后，模型读错究竟来自图片处理还是判断，才有条件区分。

跨模型续接优先传任务状态和证据。供应商专有的思考签名保留在原始记录中，由适配器判断能否回送，不能直接交给另一模型当作通用历史。

### 4. 完整行为记录从请求边界开始

推荐一个运行清单、一份追加式事件日志和一个按哈希存放的大文件目录。日志至少覆盖：

| 类别 | 必须保存的内容 |
|---|---|
| 身份与版本 | 运行、角色、父子任务、模型请求和工具调用编号；代码、配置、提示及工具定义版本 |
| 模型请求 | 最终请求体、实际附图、推理参数；每段自动加入内容的来源 |
| 模型响应 | 可见文字、工具调用、可获得的思考信息、结束原因和原始用量 |
| 工具执行 | 完整参数、原始返回、图片文件；截断或转换后实际交给模型的返回 |
| 上下文变化 | 压缩前后引用、摘要请求、移出／恢复的图片及原因 |
| 生命周期 | 重试、取消、超时、恢复、失败阶段及停止时已有产物 |
| 建模结果 | 输入与源 BIM 版本、候选变更、保存结果、质量评价对应对象 |

Qwen Code 已在服务参数转换完成后捕获请求，这个位置值得借鉴：只保存调用适配器之前的抽象消息，会漏掉最终加入或删除的字段。[源码](https://github.com/QwenLM/qwen-code/blob/b3dda468f2e48a9733ab390d42a2bdef62418310/packages/core/src/core/openaiContentGenerator/pipeline.ts#L1605)

思考记录必须区分内容、摘要、服务报告的 token 数、估算值、签名和不可获得。不能把签名当内容，把估算当计费数量，或把缺失用量记为零。5 小时／7 天额度仅在服务提供时记录，其他服务标记不适用或未提供。

保留现有行为报告的首稿、立面核对、高度依据等指标，让 `record.py` 逐步读取统一事件格式。无需另造一套与现有评价脱节的报告体系。

“重放”也要分清：离线还原行为、在隔离目录重做确定性工具操作、重新调用模型，是三种不同操作。最后一种不保证生成同样结果。

### 5. 预算、停止和版本冻结落实到执行器

根任务统一计入所有子任务、摘要和重试的用量；子任务预算不能独立叠加突破总额。请求前预留，完成后结算，同时控制时间、模型请求数、工具次数和输出上限。存在未报告用量时，费用上限只能注明其估算性质。

重试由一处管理，并记录每次尝试；只自动重试明确可安全重复的操作。停止时保存可查看草稿和未完成状态。对已经发出的写操作，超时不代表操作一定没有发生，恢复前应查询实际结果。

冻结内容包括底座提交、依赖锁文件、提示、工具定义、推理参数及模型路由。自部署还应记录权重版本、量化、分词器、聊天模板、推理服务及启动参数；远端别名无法证明固定时如实标注。固定条件提高可复现性，不承诺逐字一致。

### 6. 与现有运行器逐步衔接

继续使用 `run_bim_agent.py serve` 暴露的 BIM 工具、输入准备、候选目录和评价链。把 Claude CLI 启动部分与自有循环作为不同执行入口；旧入口保留为历史对照。

`bim_agent_bridge.py` 继续服务开发模型的直接工具调用。完整记录应在读取原始 MCP 返回时建立，再生成桥接文件或模型消息，避免某个出口提前省略内容。

首轮迁移尽量固定已有提示和工具，只改变执行底座；之后再调整角色、指引和上下文策略。这样才能解释行为变化来自哪里。待合并分支中的说明层与行为脚本应由 Opus、Astra 先确定基准，再接入，避免迁移时混入另一组指引变化。

## 四、实施顺序、工作量与决策点

### 分阶段实施粗估

按一名熟悉项目的开发者估算，**首版约 13–22 个开发人日，约 3–5 周**。这是设计判断，包含集成及离线验证，不包含把 27B 调到稳定建模质量所需的时间。

| 阶段 | 交付及验收范围 | 粗估 |
|---|---|---:|
| 设计定稿 | 请求、事件、图片与子任务契约；确定迁移基准 | 1–2 日 |
| 单角色闭环 | 接现有工具；完整记录、版本清单、预算和失败停止 | 4–6 日 |
| 长任务支持 | 图片存取、活动窗口、压缩与恢复；模拟 60–120 次工具调用 | 3–5 日 |
| 角色委派 | 独立路由、带图材料包、回传核对、共享预算、修改串行应用 | 3–5 日 |
| 获批后的实测 | 接口小任务，再到既有案例；区分底座变化与模型变化 | 2–4 日 |

离线验证重点是实际请求内容、图片字节与坐标、完整调用对、压缩后证据可取回、子任务归属和异常恢复。已有 35 项有效检查可以继承，本次没有重跑。

真实测试应先固定模型比较执行路径，再固定底座比较模型；只有具备同一模型服务的条件，才能称为底座对照。整案回归与付费调用继续按项目约定另批，本报告不启动实验。

### 需要与 Opus 讨论

1. **Python 自有循环还是 pi 低层库。** 我倾向 Python；若多服务协议维护迅速成为主要负担，再评估引入 pi-ai 的独立适配进程。
2. **第一批角色和图证据契约。** 建议先验证“协调＋一个局部工作角色”，把结果核对做好，再扩展角色数量。
3. **强模型调度的接入方式。** 开发 CLI 外层调度可以帮助开发；完整可控实验需要协调器也走自有请求路径。
4. **迁移基准。** 确定使用哪个工具和说明层版本，以及现有行为报告如何接入统一日志。

### 需要用户拍板

- 是否按上述范围开始首版实施；
- 首次实测的模型、服务、强模型辅助范围及调用批次；
- 首版验收是否以“可追踪、可恢复的建模闭环＋带图委派”为目标，随后单独推进工作模型质量。

主要风险是协议兼容细节、图片压缩损失证据、摘要改变事实、子任务扩大错误及费用，以及远端模型不可完全冻结。**发布频次、跨版本兼容稳定性、各方案在本项目的实际质量和性能，本次均未实测。**
