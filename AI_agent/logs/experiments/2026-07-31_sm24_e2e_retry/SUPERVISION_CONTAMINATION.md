> 记录人：主控 Opus 5。**用户判断：这个问题比较大，值得单独全面仔细地检查并重新设计 reading；
> 意味着之前在 sm21 和 sm24 上拿到的高分很可能是虚假的。明天优先解决，具体方案届时再议。**

## 1. 用户给出的两条硬口径（原话）

1. **reading 的时间要算总的。** 不能说主控把一些工作提前做了、再给 Haiku 读，就算 reading 时间变少了 ——
   那毫无意义。要的是**真正的 reading 过程提速，而不是拆出来的一个所谓 reading 环节提速、总量不变**。
2. **dev 阶段有主控，上线版本没有主控。** 因此：
   - 通过 judge 校验**整体打回**是可以的（不过就整个 reading 被打回重抽一次）；
   - **⚠️ 不可以主控告诉 reading agent 哪些地方没做对、要怎么做，也不可以某个子部分没做对就打回**
     —— 那等于在监督 Haiku 把任务做好。
   - **要实现的是：Haiku 等级的模型可以独立完整地完成 reading 并保证质量，
     且实现 reading 的过程中不可以收到其他更强力 agent 的信息。**

## 2. 为什么说历史高分可能是虚的（证据）

### 2.1 07-07 的 8/8 是带监督拿到的

北极星实验（[2026-07-07_haiku_cv_retest](../2026-07-07_haiku_cv_retest/README.md)）过程记录原文：

> **pilot r1（1f 平面）：工具箱调用链正常，但流程不合格打回** —— 标定错锚（用墙线端点非尺寸链 tick，
> Y 残差 0.90m、外框量成 14.52×8.90 vs testdata 15×8）、内墙 19 道（候选未经 crop_zoom 逐条核验
> ＝头号失败模式复现）、windows/dimensions/ocr/provenance 全空。已按 SOP pilot 审查点发返工指令。
>
> **pilot r2（返工后，orchestrator 亲核盘上产物 + 亲跑 gate①）：达标才放批量。**

⇒ **主控明确告诉了 Haiku「标定锚点错了」「候选没有逐条核验」「这些字段是空的」，然后它才做对。**
这正是用户禁止的那类信息注入。**该轮 9/9 · 7/7 · 15/15 的成绩不能作为无监督基线。**

### 2.2 同一模式在 sm21 系列同样存在

`new_case_guide` 的 SOP 本身就把「pilot → 主控审 → 反馈 → 返工」写成标准动作
（本文件 §5「Order of work」：*Do the pilot first, then stop and wait for review feedback*），
`isolation.py` 更有专门的 `write_feedback()` / `check_feedback_text()` 反馈通道与
`feedback.md` 注入点（`spawn_command` 会把它并进 prompt 并提示 *read it FIRST*）。
⇒ **反馈通道是机制化的、不是偶发的**，凡走标准 SOP 的 run 都可能带监督。

### 2.3 本轮（2026-07-31）实测：无监督时它会停在半路

复验轮 pilot r2（Haiku 4.5，长线视图 + 新标定门齐备）自己停下并输出：

> *Per the directive §5: I should stop and wait for review before proceeding to elevations.
> **Would you like me to continue with the complete pilot reading, or would you prefer to review
> the calibration approach first?***

⇒ 它把「等主控回答」当成流程的一部分。**上线没有人回答，它就停在那里。**
这不是模型的问题，是**流程围绕「主控在场」设计的**。

## 3. 当前形态里违规的三条通道（主控自查）

| # | 通道 | 是否违规 | 说明 |
|---|---|---|---|
| ① | **per-run directive** | **违规** | 由主控看着上一轮失败现调、随轮投喂。合法形态 = 沉淀进 standing 文档（guide / pen_library / cv_toolbox），随产品发布。本轮 directive 的三处修订（provenance 反转 / 缺席必证 / 长线优先且禁从尺寸链标定）都是有效内容，但**载体错了**。 |
| ② | **pilot → 主控反馈 → 返工** | **违规** | 07-07 的 8/8 即由此而来；`feedback.md` 是机制化注入点。上线无此环节。 |
| ③ | **主控跑预扫** | **不违规（但参数选择违规）** | 预扫是确定性代码，上线时由管线自动跑，不含更强 agent 的判断。**但**收窄阈值 / `--no-cc` 若由主控看着结果临时挑，就越界 —— 必须是固定的、随产品发布的默认档。本轮 `--no-cc` 是主控当场加的，如实登记。 |

## 4. 时间口径的更正（对应用户第 1 条）

主控此前只报 reader 会话墙钟，**从未计入会话之外的前置工作**。本轮实测补上：

| 环节 | 耗时 | 性质 |
|---|---|---|
| 五图预扫 | **23.6 s** | 确定性代码，无 LLM |
| 工作区构建 | **7.1 s** | 确定性代码，无 LLM |
| **主控侧前置合计** | **30.7 s** | |
| reader 会话（07-31 pilot r1） | 447 s | LLM |
| **总量** | **≈ 478 s** | 前置占 6.4% |

**结论**：把工作从 LLM 移到确定性代码，**总量是真降的**（代码秒级 vs 同样信息要 LLM 几十个 round trip），
不是把时间挪位置。**但以后一律报总量**，不再单报会话墙钟。

## 5. 明日重新设计时要回答的问题（不在此预设答案）

1. **standing 与 per-run 的边界**：哪些内容属于随产品发布的 standing 脚手架，哪些是 dev 期的编排噪音？
   现 `feedback.md` 通道是否整个下线，还是保留为「judge 判定后的整轮盲重抽」的载体？
2. **重抽机制**：judge 不过 ⇒ 整轮盲重抽（零提示）？还是把「质量自检」做进 standing 文档让模型自救？
   两者的成本与可达质量各是多少？
3. **无监督真实基线是多少**：sm21 / sm24 的历史成绩需要在**无监督条件下重测**才有参照价值。
   在拿到该基线之前，任何「质量恢复了」的判断都没有依据。
4. **pilot 这个概念本身是否成立**：上线没有 review 点，"pilot 先做一张停下等 review" 的两段式
   是否应当整个取消，改为一次性读完全部视图？
5. **judge 侧的自动化程度**：用户提到「目前是一个 agent 在做，之后可能直接通过代码跟 gt 核就行」
   —— 代码化判卷与本轮建成的 v3 类型化投影层如何衔接。

## 6. 本轮仍然有效的成果（与监督问题无关）

以下是**确定性机制**的改进，不依赖任何监督，明日重设计时可直接继承：

- v3 判卷层对识图阶段的生产投影 + 能力守卫（原 BLOCKER 已消）

  （上一轮 40.22 / 9%）—— 这条是**无监督也成立**的真实改进
