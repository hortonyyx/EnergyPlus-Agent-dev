## 结算与反例

服务实报超出单次预留时，全额计入根账和子账，保留原 usage，另写
`budget_overrun`（模型、预留、实报、超额、请求时档案余量、是否在余量内、根/子
是否不足）。只要相应总额度足够就继续；子额度不足只停该子任务，兄弟仍按根账
余额申请。根额度不足时仍记录已发生的实际值、余额记 0，拒绝后续请求。配置
上限不增加，超额不截断、不少记、不记零。

[离线反例结果](counterexamples.json) 与 [完整事件/附件](counterexamples.tar.xz)
直接复用 R1 首条 GLM 原请求/原响应：输入 31、输出 24（思考 22）、合计 55，
旧预留 46＋8＝54。全部是离线运行，没有伪造为新的服务实测。

| 情况 | 结果 |
| --- | --- |
| 根额度 100，预留 54，实报 55 | 全额结算 55，余量 45，可继续 |
| 根额度 54，预留 54，实报 55 | 全额结算 55，余量 0，停止并保留超额事件 |
| 子额度 54，根额度 200，实报 55 | 子任务停止，根账计 55、余量 145，兄弟可再预留 54 |
| token 实报 55 且耗时 11 秒超过所留 10 秒 | 仍按时间规则停止；token 全额结算，时间保留原 hold，完整 11 秒写入违规证据 |
| 重开并重复结算同一响应 | 仍计 55，结算与超额事件各一条，时间停止原因也保留 |

旧档案余量 0 时，completion 多出的 16 标为不在余量内。另以余量 32 配旧
54 预留做明确的离线故障注入，验证记录“在余量内”且不改变实报；这不是新
预留公式的正常输出。正常 GLM 首条请求现预留为 86。
