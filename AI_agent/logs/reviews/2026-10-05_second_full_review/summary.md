## 二、分歧与取舍

1. **依据事务的接线缺陷（只有 Astra 发现）。** `claim_transaction` 成功存出新稿后，单模型底座的“当前稿”与开发调度用的 `CoordinatorSession.source_bim` 都还停在旧稿：`runtime_context.py:102` 的写工具名单里没有它，且只读 `candidate`（事务起点）不读 `result_candidate` ✔；`runtime_coordinator.py:242` 同样 ✔。另外调度在 `:331,347` 只凭“没有调用报错”就把局部观察记为已应用，事务领域失败、什么都没改时观察也被消费 ✔。Astra 用真实夹具两条都离线复现。Opus 没有发现。
   **取舍：采纳，分界前必须修。** 新默认入口已替代三个旧单步工具，下一步“开发模型调度 27B”走的正是调度这条路径，不能带着走。
2. **底座开销的原因与优先级。** Opus：约八成贴着检查点，每个检查点都把整个运行目录 `rglob` 并逐文件算哈希（`runtime_tools.py:356-372` ✔，`loop.py:899` ✔），工作区又在 Windows 9p 挂载上（`mount` ✔）；sm25 94 分钟里约 17 分钟；列为分界前必须。Astra：列了事件追加全前缀校验、每次工具后重扫视图与依据等候选热点，主张先分阶段计时，放到以后。
   **取舍：采纳 Opus，列入分界前；同时采纳 Astra 的做法，先计时再改。** 理由：产品按时间上限管理，这是不改模型行为就能拿回的 10–20%；且回归的速度数字要可信，底座不能自己拖慢。运行入口只许写在工作树内（`runtime_entry.py:89-90` ✔），所以要加显式的运行根目录配置，让整案运行能放在本机盘。
3. **历史思考回传（只有 Opus 发现）。** Paratera 走 OpenAI 兼容线路，底座把每条历史 `reasoning_content` 原样回传（`adapter.py:197` 默认 `echo_fields` ✔）；27B 第二次运行后段请求里约 41% 是旧思考。GLM 的 Anthropic 线路不受影响。
   **取舍：采纳，做成按线路配置、27B 默认只保留当前一串工具调用里的思考。** 对连贯性的影响未知，所以节点回归里 27B 用新设置跑，与之前两次（全回传）比；变差就改回配置，不改代码。
4. **按实际额度收尾。** Astra 列为分界前必须：把 token／金额／调用的保守剩余额度做成一句短提示，替换只按时间的提示。Opus 侧重回归里 27B 改用按金额封顶、不设 token 硬停。
   **取舍：两条都采纳，互不冲突。** 提示替换原句，不新增一套催办规则；不自动放大额度。
5. **旧检查。** Opus 更正前提：250 个旧检查文件在本机原生盘的提交副本上 `-n 2` 跑 10 分 51 秒全部跑完、没有卡住，与 Git 和环境无关的真实失败 11 项（9 项钉实现哈希或旧产物、2 项旧约定）；主张分界前全量跑通。Astra 做了全目录静态依赖盘点，主张分层放以后。
   **取舍：全量在本机盘跑通并处理那 11 项，放进清理包；分层（L4）放以后。** 理由：分界条件里有“完成测试”，而全量在本机盘只要约 25 分钟，成本不高；以后每次合并后的核对改为在本机盘跑全量。11 项失败要先在主线上确认，重签哈希必须写明原因，不能为变绿放宽保护性断言。
6. **节点回归的范围。** Astra 建议直接用“开发模型调度 27B”跑 sm24，加 sm25 抽查；Opus 建议沿用原计划（GLM 新底座 sm24、sm25，Claude Code sm24 同期，27B sm24 按金额封顶）。
   **取舍：沿用 Opus 的范围。** 分界回归要和 10-04 同条件可比；开发模型调度 27B 是过分界后的第一步，不混进同一次回归。
7. **Opus 另有两项小发现，采纳：** `geometry_feedback`／`geometry_changes` 捕获 `KeyError` 后只给模型 `"'z'"`（`run_bim_agent.py:1094,1169` ✔），与首次审查的“只看到 0”同类，放进 C3-T；`src/agent/__init__.py` 让工具服务加载旧 LangGraph 与 EnergyPlus 侧 256 个模块，放以后（L5）。
