## 结论

1. **新底座最大的问题出在“模型每次看到什么”，而这一项不在“两底座同一版 Agent”的核对范围内。**（核实）R3 只逐字节核对了指引、工具目录和任务正文。可新底座默认只保留最近 16 条消息：从第 5–7 次请求起，模型自己早先的观察和整张原图就被移出上下文，原位置只剩一条列哈希值的系统消息。此外每次请求还附一条“当前运行状态”，最长约 5 万字符，大部分是哈希和文件路径；带结构化内容的工具结果则原样发两遍。在较长的 4 次运行里，三项合计约占提示 token 的 16–31%。缓存命中只有 8–18%，Claude Code 是 87–92%。同样这 4 次，新底座每次请求平均输入 6.3–8.8 万 token，Claude Code 每轮 3.4–5.5 万。对质量的影响没有做过对照（判断），但行为上已经有迹象：新底座 20 次读参考资料里有 7 次是重读，Claude Code 47 次里只有 1 次。
2. **T1 改指令时“替换”没有替换干净，留下两处互相矛盾的要求。**（核实）系统提示第 6 步说“整图引用不算定位，依据框必须盖住那扇洞口”；可 `claims` 参考里仍写着“拿不准坐标就引整图，窄框从来不是必需的”。几乎每次运行都会读这份参考（21 次里有 19 次）。当前版 Agent 的 sm25 中，20 条几何依据全部引的是整图，北立面用一条尺寸链套了同面 4 个洞口，两层都这样。外部高度 34 个里对上 25 个，没对上的 9 个中有 6 扇北窗就是这样读错的，另外 3 扇门是已定为容差的地坪基准差。另一处：总则让模型“交付前再看一遍”，收尾规则却规定“剩余不足 15% 就停止读图”。
3. **工具：42 个里有 17 个在 21 次图纸运行中一次都没被调用**（核实）。它们的说明和参数结构共 13,347 字符，占目录的 39%。其中 7 个属于别的输入模式，或在新底座里已被禁用（`review_detail`、推断 3 个、参数化 2 个、续查 1 个）。T1 的报错反馈有个 bug：`operations_json` 写成对象时，模型只能看到一个 “0”。
4. **运行：当前版 Agent 只跑过两次，都在 Claude Code 上**（sm24 44 分钟，sm25 78 分钟）。新底座的 5 次运行用的全是旧版 `5bb10538`（核实）。sm25 的首稿出得晚（65 分钟），其中 22.7 分钟耗在平面 JSON 连续 18 次失败上：10 次是格式或字段写错，8 次是端点不重合之类的拓扑问题。这些失败大多以 `status:error` 返回，现行统计口径只数 `isError`，所以记录上 sm25 只有“4 次报错”，实际是 19 次。
5. **底座自身耗时占 2.7–8.3%**（每次请求 4–9 秒，随着运行变长越来越慢）。事件里 64% 是上下文事件，绝大多数是图片去留记录，同一张早已移出的图最多被重复记了 29 次。一次运行的目录有 43–102 MB，Claude Code 只有约 10 MB。另外，启动器把重试次数写死为 0，空回复也不在可重试之列：3 次订阅对照里有 2 次都死在服务端的临时故障上（核实）。
6. **审查自己用的量具有坏字段，下次审查前必须先修。**（核实）T1 每次工具返回末尾都追加一行时间提示，导致行为记录脚本解析失败，T1 两次运行的看图统计全部归零；新底座行为报告里的依据提取全部为空；两套脚本的字段名也对不上。

**建议（判断）：** 在吸收包和 27B 摸底之前先插一个小清理包，内容就是下文“建议马上做”的 6 条（M1–M6）。其中 M1–M3 决定了此后在新底座上测到的任何数字是否可信，也决定了它能不能作为 Claude Code 的同条件对照。

### 1.4 过时规则（核实）

- `review_detail` 的说明还写着 “local image model (Haiku)” 和 “At most two local reviews are available in this experiment”（`run_bim_agent.py:2822-2828`）。21 次运行调用 0 次。
- TOOLS 段的 “a continuation does not reset it”（`:394`）以及 FINISHING 注释里的“与续查共用”：现在的运行都不开续查，新底座也没有续查这种轮次。

### 1.5 “替换不追加”执行得怎样

形式上做到了：每段都有注释写明针对的失败，旧句子也删了。问题出在只在一处替换：同一条规则在参考或总则里的另一份旧写法没有跟着改（见 1.3）。另外，T1 还在工具返回里加了一层反馈：每次返回都附时间行；每次保存、开口检查和交付都附 `located_height_coverage`、`facade_counts`、`floor_completeness`。`finish_bim` 的返回从 8.6k 字符涨到 15.5k，`check_openings` 从 13.4k 涨到 18.6k（核实，sm24 基线对 T1）。现在一次开口检查里同时出现两种不同口径的“高度覆盖”（`height_coverage` 和 `located_height_coverage`，`run_bim_agent.py:2724-2745`）。这正是 09-27–29 那次回退的同一类风险：一层层往反馈里加东西（判断）。

- 底座自身的耗时会越跑越长：Paratera 第 3 次，从工具做完到发出下一次请求，这段间隔从开头的约 1 秒涨到后段的 5–15 秒。原因是每次请求都要对全部历史图片重新判定去留并逐一记事件（`context.py:993-1040`），已经移出的图也会再记一次。全程 861 条上下文事件占全部事件的 64%，同一张早已移出的图最多被记了 29 次。照这个趋势，100 分钟、150 次请求的运行会更明显（判断）。

### 5.2 每次请求附加的内容（核实；token 份额按每次请求“实报输入 ÷ 发送字符”的比例折算，是估计值）

| 运行 | 状态消息＋哈希清单＋重复发送的结构化结果（占提示） | 回传的旧思考（占提示） |
|---|---:|---:|
| Paratera 第 2 次 | 约 24.5 万 token（16%） | 约 54.5 万（36%） |
| Paratera 第 3 次 | 约 96.8 万（31%） | 约 48.3 万（15%） |
| 订阅第 1 次 | 约 20.1 万（17%） | 约 44.0 万（37%） |
| 订阅第 2 次 | 约 45.5 万（27%） | 约 32.5 万（19%） |

1. **按条数裁剪的活动窗口**（`context.py:66-74`，默认 16 条；`runtime_entry.py:263`；启动器 `runtime_r1_preparation.py:105-109` 不传这个参数）。它不看 token 数，到第 5–7 次请求就开始裁剪，而此时整个请求只有约 4–5 万 token，配置的上限却是 90 万。以 Paratera 第 3 次为例（核实）：从第 8 次请求起，整张平面图已经不在上下文里，到第 11 次，4 张立面整图也全部移出；第 12 次请求写出整层的 `build_plan_bim` 声明时，模型只看得到 3 张局部裁图和 2 张剖面图，此前 11 轮只保留了 6 轮；到第 36 次请求，只剩最近 7 轮。移出的部分换成一条系统消息，列出每条被移出记录的 `history_id` 和 sha256（`context.py:1042-1087`）。模型没有任何工具能按这些编号读回内容。作对比：Claude Code 在 sm24 基线里只压缩过一次，发生在第 39/42 次工具调用之后，当时上下文已到 178,264 token（从流记录 `compact_boundary` 查到）。
2. **“当前运行状态”消息**（`context.py:708-734`）：每次请求都放在末尾，声明自己是“机器生成、认识状态权威”。最长的一次 51 条，其中 38 条是每个视图、每条依据各一条带哈希和 `blobs/` 路径的引用（约 3.9 万字符），外加整段任务原文的副本；同一句未决项因为挂在 3 条依据上而重复 3 次。真正对模型有用的只有当前和选定候选的编号，以及约 2.5k 字符的未决项和待办。
3. **结构化结果重复发送**（`adapter.py:272-297`）：`content` 里的文本和 `structuredContent` 一起塞进 tool 消息。实例：Paratera 第 3 次第 23 次请求里的一条工具消息有 186,732 字符，其中 92,026 字符的 `structuredContent` 与文本逐字相同。整段 JSON 再被包进一个 JSON 字符串，转义又多出 1.4–2.5%。
4. **缓存几乎命中不了**：大多数请求恰好命中 10,496 token，也就是工具、指引、任务这段固定前缀。窗口每次往前滑，后面的内容就都变了。
5. **思考回传**：Claude Code 也保留旧思考（10-03 抓包），这一项本身不算两底座的差异；但它占提示的 15–37%。

### 5.3 没用上的功能（核实）

模型摘要（默认关闭）、重试（被关闭）、`--pin-tag`、`--keep-view-id`、`--retrieve-image`、`--attach-image`（5 次运行都没用，启动器也不支持传入）、订阅线路上的金额预算；外层协调与局部委派（`runtime_coordinator.py` 591 行、`runtime_delegation.py` 346 行）只在 R1 立面小实验里真跑过，整案一次都没用过，按计划要到“开发模型调度 27B”时才会用上。

### 5.4 接口复杂度（核实）

入口有 42 个命令行参数，外层协调另有 23 个；事件类型 15 种；底座契约类 62 个，建筑契约类 47 个；每次请求产生 20–41 条事件。重试没开，失败时也只记异常类名（`loop.py:1093-1101`），HTTP 状态码和服务返回的正文都不记（`adapter.py:158` 直接 `raise_for_status`）；空回复属于协议错误，直接停跑（`loop.py:397`）。订阅凭据路径写死为主工作树的 `.env`（`runtime_r1_preparation.py:75`），R2c 验收时已经记下。

### 5.5 做得好的地方

记录完整、可复核：5 次运行 4,240 个文件全部对得上哈希。Agent 版本登记和两底座的一致性核对都已经建起来了。T1 的时间上限和到点交稿两边共用同一份代码，没有另写一套。

## 删、并、简化清单

### 建议马上做（插在吸收包和 27B 摸底之前）

**M1 新底座上下文默认改成“只追加、到阈值才压缩”，与 Claude Code 对齐**
- **改什么**：不再按 16 条消息裁剪，改为按 token 阈值触发压缩。阈值先保守取约 15 万：Claude Code 实测在 17.8 万时压缩；订阅端点的真实上限还没核实。启动器显式写入这个参数。触发压缩时，删掉那条只列哈希的系统消息，改成一句模型看得懂的说明（例如“更早的 N 轮已移出；原图可以重新查看”）。图片上限一并改成按体量控制。“两底座同一版 Agent”的核对加上一项：上下文策略相同。
- **为什么**：第五节第 1、4 条；结论第 1 条。这是迄今两底座之间最大的未登记差异。
- **预计影响**：对工作模型，它能看到自己读过的尺寸和整图，重读和重复推理会减少（判断，需对照确认）。对速度和花费，缓存可以命中，每次请求的输入有望降到 Claude Code 的量级。对维护，主要是改默认值，按阈值压缩的逻辑已有。
- **风险**：sm21 那样的两层、100 分钟长跑可能逼近端点上限，所以保留按阈值压缩作兜底；图片一多请求体会变大，Claude Code 也一样。改完要跑一次同条件对照（订阅，sm24 和 sm25 当前版各一次），属于节点回归，需要报批。

**M2 “当前运行状态”消息：删掉，或只留模型用得上的部分**
- **改什么**：`context.py:708-734`。如果保留，只放当前和选定候选的编号、已保存的未决项和待办原文；去掉哈希、`blobs/` 路径、每个视图一条的引用、任务原文副本，以及重复的未决句。
- **为什么**：第五节第 2 条；R3 验收已经把它列进审查清单。
- **预计影响**：后段每次请求少约 1–1.5 万 token；去掉一条自称“权威”的噪声；`runtime_context.py` 也能大幅简化。
- **风险**：这条消息原本是为了在裁剪窗口后保住关键事实；M1 之后不再裁剪，这个用途基本没了。将来如果又要裁剪，再按需加回可读的摘要。

**M3 同一内容在一次工具返回里只出现一次**
- **改什么**：(a) 底座：`adapter.py:272-297` 不再同时发文本和 `structuredContent`，只发文本，与 Claude Code 一致；外层 JSON 包装也可以去掉，免得转义。(b) 工具：`revise_bim` 返回给模型时，`provenance.claim_application` 只保留文件路径，不再复制一份 26k 字符的依据（`run_bim_agent.py:700`、`:1349`）。
- **为什么**：第五节第 3 条；第四节最后一条（依据在一条工具消息里出现 4 次；10/16 次 Claude Code 运行的工具返回被截断）。

- **风险**：低。`runtime_context` 读的是原始结果，不受影响；需要改相关测试对 tool 消息格式的断言；工具改动要登记新的 Agent 版本。

**M4 服务端临时故障有限重试，并记下错误内容**
- **改什么**：启动器不再写死 `--model-retries 0`，默认改为 1–2 次；用量为 0 的空回复、429、5xx、网络超时都走这条有限重试；失败事件记 HTTP 状态码和返回正文的前 2 KB。
