## 二、分歧与取舍

1. **按条数裁剪的上下文窗口是不是头号问题。** Opus 列为第一：默认只留最近 16 条消息（`context.py:69` ✔，启动器不改），从第 5–7 次请求起就裁，Paratera 第 3 次写整层平面时整张平面图已不在上下文；缓存命中 8–18%，Claude Code 87–92%。Astra 承认窗口在移动、缓存低，但认为因果要受控验证，没列进“马上做”。
   **取舍：采纳 Opus，列入马上做。** 理由：这是两底座之间最大的未登记差异，“同一版 Agent”不只看指引和工具，还要看模型每轮实际收到什么；不先对齐，以后新底座上测的任何数字都难以和 Claude Code 对照。Astra 的顾虑也采纳：改完必须跑同条件对照才算数，压缩时必须保住阶段 2 那次退回所保护的关键状态。
2. **依据定位的指引冲突。** Opus 发现 `claims` 参考仍写“拿不准就引整图，窄框不是必需”，与系统提示“整图引用不算定位”相反（`:116-119` 对 `:1055-1059` ✔），而 T1 sm25 的 20 条几何依据全部引整图。Astra 没列。**采纳，马上做。**
3. **工具目录减多少。** Opus 主张图纸运行马上拿掉 7 个不属于本条件的工具，另 10 个从没调用过的以后再减；Astra 强调“没用过不等于没用”，主张按能力过滤。**取舍：两者并不矛盾，但马上做的范围比 Opus 建议的窄。** 马上做的只是按运行实际开启的能力过滤：没开委派就不挂 `review_detail`，没开续查就不挂 `record_work_review`，相应的指引句一起移出。推理和参数化工具先不从图纸运行里拿掉：产品是统一入口，不完整的图纸同样需要推断，按输入类型摘掉会和这个目标冲突。按使用次数删工具，等 27B 摸底的行为记录出来再定。
4. **依据手续太重。** Astra 发现 T1 sm25 有 41.5% 的调用花在登记、采纳、确认依据上，一次修订让未应用的依据整体过期，又重登记 9 条。Opus 没列。**采纳，列为以后做里的第一梯队**，风险中到高，要单独做反例。
5. **重试的边界。** Astra 提醒：额度用完、权限错误要和临时限流分开，批次规则“遇 429 或额度限制即停”不能被通用重试悄悄改掉。**采纳**：只对临时故障做有限次重试，额度类错误照旧停。

## 三、清理包（插在吸收包和 27B 摸底之前）

按文件边界分两包，可以并行（都由 Astra 实现）：

1. 上下文改为只追加、按 token 阈值压缩；压缩时给模型一句看得懂的说明，并保住关键状态。
2. “当前运行状态”只留模型用得上的：当前与选定候选、未决项与待办原文、取回入口；哈希清单和来源元数据留在日志。
3. 工具结果在模型消息里只出现一次；原始返回照旧完整存档。
4. 失败分类与有限补救：记状态码、服务错误类型、正文摘要、请求 ID；超时、临时 429、5xx、用量为 0 的空回复有限重试，计入预算与截止时间；额度、权限错误停；未知写不重试。

6. 凭据路径改为显式配置。

**C2 Agent 与量具**（`scripts/tool_scripts/`、`src/agent/runtime_tools.py`、行为记录脚本；改完登记新 Agent 版本，两底座同步）
