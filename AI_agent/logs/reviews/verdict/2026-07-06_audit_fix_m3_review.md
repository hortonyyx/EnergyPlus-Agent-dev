## Review questions

1. Top-level `baseline.provenance` is additive and should not trip strict schema validation. There is no local `Baseline` pydantic/jsonschema model; consumers use ordinary dict/json access. `record_baseline` writes JSON at `scripts/tool_scripts/record_baseline.py:436`-`scripts/tool_scripts/record_baseline.py:437`, then passes an in-memory dict to report assembly at `scripts/tool_scripts/record_baseline.py:430`-`scripts/tool_scripts/record_baseline.py:450`. Tests read with `json.loads` and assert selected keys only, e.g. `tests/test_orchestrate_baseline.py:194`-`tests/test_orchestrate_baseline.py:197` and `tests/test_orchestrate_baseline.py:219`-`tests/test_orchestrate_baseline.py:221`.
2. Yes, include `src/agent/correction/`, and also hash the active correction tolerance config. The correction core materially changes reading-to-downstream behavior: `src/agent/correction/deterministic.py:18`-`src/agent/correction/deterministic.py:32` describes cross-floor reconcile, snapping, sliver merge, and tolerance loading; it imports correction config/envelope/schema/validator at `src/agent/correction/deterministic.py:40`-`src/agent/correction/deterministic.py:43`. The config loader explicitly allows per-run overrides via `EP_AGENT_CORRECTION_CONFIG` at `src/agent/correction/config.py:1`-`src/agent/correction/config.py:9` and resolves that env override at `src/agent/correction/config.py:21`-`src/agent/correction/config.py:38`. Fix: add `correction_src_hash` for `src/agent/correction/` and `correction_config_hash` for `resolve_correction_config_path()`; record the config path/source too.
3. Deleting `reading_runner_ladder` is locally compatible with stored artifacts. Old orchestration states contain stage/status/attempt/message/gate data, e.g. `case_tests/e2e_tests/sm21_anchor/run_2026-07-02_sonnet_flow_e2e/_run/orchestration_state.json:1`-`case_tests/e2e_tests/sm21_anchor/run_2026-07-02_sonnet_flow_e2e/_run/orchestration_state.json:80`, not serialized `RunPolicy`. Existing baselines likewise have top-level run/model/gate data, e.g. `case_tests/e2e_tests/sm21_anchor/run_2026-06-23_gpt54mini_reading/_run/baseline.json:1`-`case_tests/e2e_tests/sm21_anchor/run_2026-06-23_gpt54mini_reading/_run/baseline.json:80`. Caveat: because `RunPolicy` is `extra="forbid"` at `src/agent/execution/policy.py:37`-`src/agent/execution/policy.py:38`, any external serialized policy payload containing the field would fail after deletion; I found no such local payload.
4. Anchor git calls to the repo root, not `run_dir` and not ambient cwd. Existing tests exercise `record_baseline` against tmp runs: `_minimal_run` creates `tmp_path/synthetic_case/run_audit` at `tests/test_orchestrate_baseline.py:38`-`tests/test_orchestrate_baseline.py:41`, real cases are copied under tmp at `tests/test_orchestrate_baseline.py:215`-`tests/test_orchestrate_baseline.py:218`, and `record_baseline` is called there at `tests/test_orchestrate_baseline.py:250`-`tests/test_orchestrate_baseline.py:252`. `git -C run_dir ...` would hit non-git tmp dirs and only test degradation. Use a module-level `PROJECT_ROOT = Path(__file__).resolve().parents[2]` from `scripts/tool_scripts/record_baseline.py`, then `git -C PROJECT_ROOT rev-parse HEAD` and `git -C PROJECT_ROOT status --porcelain --untracked-files=all`. If that fails, soft-degrade to null/error.

## Findings

1. HIGH - `collected_at` must not make `record_baseline` non-idempotent. The proposal's wall-clock `collected_at` conflicts with the existing "no Date.now in tooling here" contract in `scripts/tool_scripts/record_baseline.py:9`-`scripts/tool_scripts/record_baseline.py:11` and the idempotence test that records twice and expects the exact same `REPORT.md` at `tests/test_orchestrate_baseline.py:635`-`tests/test_orchestrate_baseline.py:641`. `REPORT.md` GEN model config is rebuilt from the baseline dict at `scripts/tool_scripts/report_assembly.py:731`-`scripts/tool_scripts/report_assembly.py:745` and wrapped at `scripts/tool_scripts/report_assembly.py:799`, so a live timestamp would churn both baseline and report. Fix: make `collected_at` deterministic from the existing `date` arg, omit it, or inject/freeze it in tests and exclude/normalize it in any future exact re-record diff.
2. MEDIUM - The hash scope is too narrow if it excludes correction code/config. See review question 2. Fix: add `correction_src_hash` plus active correction config path/hash. Without this, two runs with identical reading skill/source hashes can still diverge through deterministic correction behavior.
3. MEDIUM - Git provenance must be explicitly repo-root anchored for tmp-path record tests and copied runs. See review question 4. Fix: collect repo state with `git -C <project_root>`, not `git -C run_dir` or bare `git` dependent on process cwd; keep subprocess failures best-effort with null fields plus `collection_error`.
4. LOW - Future exact golden re-record comparisons need a normalization rule for environment-dependent provenance. Current xfail re-record tests do not compare whole baseline JSON (`tests/test_orchestrate_baseline.py:181`-`tests/test_orchestrate_baseline.py:199` checks selected keys; validation xfails at `tests/test_validation_run_baseline.py:41`-`tests/test_validation_run_baseline.py:96` validate gates/policy paths). When the pending re-record lands, compare stable fields normally, but exclude or normalize `provenance.collected_at`, `git_dirty`, `git_dirty_paths`, and `collection_error` unless the test explicitly controls the worktree.
