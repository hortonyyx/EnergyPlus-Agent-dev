## 1. 方案主张

**别再用代码在开考前替读图器把候选算好；改用两样"读图器自己必须亲手生产"的确定性痕迹做账——
（a）它自己调用验证工具（crop_zoom 等）留下的会话内证据，（b）它自己抄下来的尺寸链数字做闭合运算——
两者都不是预扫给的，都不能靠自评，都不需要人/更强 agent 在场。做了这项工作，账才平；账平不平，机器看得见。**

## 2. 机制怎么工作

### 2.1 Q1：没人盯着的前提下，靠什么让弱模型真的把逐条测量的工作量做完？

**关键结构性事实（本版新增，直接来自本次修正给的数据 + 一次现场验证）**：
`cv_toolbox.md` 已经写明——每次调用 `crop_zoom`/`wall_line_profiler`/`px_m_calibrator`/`window_cc_detector`
（不含 `prescan-*`）都会在 `cv_evidence/<image_stem>/NNN_<tool>.json` 留下一个**编号侧车文件**，
记录工具名 + bbox/anchor 几何。**这是读图器自己每做一次"去看/去量"就会自动留下的、不需要预扫、
不需要模型主动上报的确定性痕迹。** 我核实了本轮崩溃的 d1/d2：`cv_evidence/{1f_view,South_view}/` 下**除
`prescan/` 子目录外，没有任何编号侧车文件**——即两次崩溃里读图器自己一次手动验证工具都没调用过，
所有 CV 痕迹都只是开考前代码自动跑的预扫留下的。**这与"做对时在枚举、崩时在目测"的判断完全对得上，
且不需要相信模型自述，是可以直接从磁盘上数出来的。**

**机制（Verification-Trace Ledger，工作量痕迹核账）**：

- **输入**：`cv_evidence/<image_stem>/` 下**非 `prescan/`** 的编号侧车文件（工具名 + bbox/anchor）+
  `output.json` 的 `strokes[]`。
- **输出**（新增 gate① CROSS_CHECK，每张图各出）：
  ```
  reading.verification_density   # 手动验证类调用数（crop_zoom/profiler/calibrator）÷ 非周长墙笔画数
  reading.verification_coverage  # 所有手动验证调用 bbox 的并集范围 ÷ 图纸有效区域
  reading.stroke_verification_anchor  # 每条非周长墙笔画,是否有一次手动验证调用的bbox在容差内覆盖它的坐标
  ```
- **谁判**：纯计数 + 几何覆盖运算，代码，不是模型也不是人。
- **判什么**：三个数值是否达到门槛（门槛来自 07-07/07-30 这类有真实调用痕迹的历史样本实测分布，
  §4 第一步先观察不阻断；07-02 的 112 次因为走的是自建 CV、不产生 `cv_evidence` 侧车，**不能直接拿来标定
  门槛数值，只能当"下限该多高"的背景参照**——它告诉我们"读懂一张复杂图纸值这个量级的验证工作量"，
  但不能提供可比的侧车计数）。
- **判不过怎么办**：与既有机制一致——**盲重抽，零信息，≤3 次**，复用 `judge_rubric.md` 已经写好的
  冷启动子代理重读机制，不新增任何"告诉它哪里错"的通道。

**这条机制不靠"劝"**：它不写进 skill 文档要求模型多调用工具（那是已经三连败的路，见 §3 第 5 条约束的
讨论）；它只是**在事后，对着磁盘上已经存在（或不存在）的痕迹算账**——模型做没做验证工作，不取决于它
说了什么、也不取决于文档写得多清楚，取决于 `cv_evidence/` 目录下有没有那些编号文件。**这是本条机制回答
"什么样的结构让不做就走不下去/做没做机器看得见"的核心**：结构不是"劝它做"，是"它不做，痕迹就不存在，
账目就不平，不平就重抽"——重抽的成本已经算进预算（≤3 次），比"漏判一次坏产物一路淌到 EP"便宜得多。

### 2.2 Q2：完成度的分母，唯一主线 = 尺寸链闭合（不再是预扫替补）

**这条不是新发明，是把 gate① 已经实现、目前只当"内部自洽参考"的 `_chain_closure` 检查，提升为分母的
唯一来源，并接上下游的认领判定**：

- **谁产生分母**：**读图器自己**——它在 `dimensions[]` 里转录的每一个 `chain_id`/`axis`/`role`/`order`
  条目。这是纯 OCR 任务（抄图纸上印刷的数字），是弱模型相对最强的能力，且图纸本身（问题书 §1 已述）
  带完整尺寸链标注。**分母完全不依赖预扫，也不依赖代码替它猜——是它自己老实抄数字的直接产物。**
- **谁核对闭合**：既有代码 `_chain_closure`（Σ segments == overall，`DIMCHAIN_CLOSE_TOL_M` 门限）——
  已经是确定性代码，不需要新写。
- **账不平机器怎么知道**：现状已经能知道——链条只写了总长没写分段（`incomplete`）或分段总和对不上
  总长（`mismatch`）都已经在 `results` 里显式 `fail`。**本版要做的两处提升**：
  1. 把这个检查从"仅供参考的 CROSS_CHECK"提升为影响下游信任的**分母生成前置条件**——只有闭合的链条
     才拿去生成"预期隔墙位置"；
  2. 新增一步（纯算术，代码）：把每条**已闭合**链条的累加坐标序列，转成该图"预期内部隔墙可能落点"的
     列表；每个落点必须有（a）一条墙笔画落在容差内认领、或（b）`uncaptured[]` 里一条显式说明
     （例如"这个位置是窗垛不是隔墙"）。两者都没有 = 该落点"未认领"，计入不完整。
- **对 §2.1 的互补**：尺寸链闭合给出的是"数字上该有一道墙的位置"，工作量痕迹给出的是"有没有真的去验证
  这道墙"——两者独立，互不依赖预扫，合起来堵住"多画"：**任何非周长墙笔画，必须落在（a）一个闭合链条的
  累加位置容差内、或（b）一次真实发生的手动验证调用的 bbox 容差内，两条都没有 = "无锚笔画"，直接计入
  不完整/低可信**。这一条对"多画 60–80m 虚构墙"直接命中——编造一条墙,如果既不落在任何闭合尺寸链位置上、
  也没有一次真实的验证调用去看过那里，就是无锚笔画,不需要判断"它是不是真的墙"这种语义问题，
  只需要问"这个位置有没有账"。
- **已知局限（gate① 代码注释自己写明的）**："a self-consistent wrong read still closes"——
  一组自洽但抄错的分段数字一样能闭合。这个局限本版没有解决，见 §5 反对意见。

### 2.3 Q3：同一张图独立读两遍、代码比对——正面评估

**先给一个现成数据能立刻算出的结果**：d1、d2 本身就是同一张图的两次独立冷启动读法（W5 实验的原始设计
目的不是为了互相 diff，但数据现成，可以马上拿来做这个检验，**零新增识图成本**）。我用最简单的
"墙笔画中点最近邻匹配"（0.5m 容差，比 GT 的 0.30m 更宽松）跑了一次：

| | d1→d2 匹配率 | d2→d1 匹配率 |
|---|---|---|
| 数值 | 4/13 = 30.8% | 4/17 = 23.5% |

**更关键的是匹配的分布形状，不是聚合数字本身**：唯一匹配上的 4 条，中点距离**精确为 0.00m**——
这 4 条几乎可以肯定就是周长墙（两次读法都对外轮廓读得很准，这和 GT 判卷"外轮廓 60/60m 两次都 pass"
完全对得上）；**其余全部内部墙（S5–S13，9 条）在 d2 里找不到任何 0.5m 内的对应**（最近距离 0.60–2.58m）。
**⇒ 不需要 GT，只用两次独立读法互相 diff，就已经能看出"内部墙不可信、周长墙可信"这个和真实判卷完全一致
的结构**——这是本版新证据，支持"双读 diff 有实质分辨力"这个判断，而不是空对空的猜测。

**正面回答四个子问题**：
1. **能不能当完成度/可信度判据**：能当**信号**，建议定位为**第二级、按需触发的复核**，不建议当第一级
   默认机制（原因见下）。
2. **不一致率与真实分数相关吗**：这次事后验证支持"相关"这个方向（两个已知差的分数 9.0%/24.8%，
   对应的互相一致率也很低、且失守的具体位置〔内部墙〕和判卷失守的位置完全一致）；但样本只有一对，
   **相关性本身仍然是待实测**（见 §7），不能从一对数据下因果结论。
3. **两遍都以同样方式错（系统性偏差）会不会一起瞎**：**会，这是本机制真实存在的盲区，我没有干净解法**。
   双读 diff 只能抓"不同错法"（两次结果彼此不一致 ⇒ 至少一个错），抓不住"两次用同一套系统性偏差错成
   一样"（比如某种图纸画法让任何一次冷启动都把窗垛认成隔墙——问题书 §4.2 里北立面尺寸链累加位置被
   画成纵向内墙就是这类具体先例）。d1/d2 这次的分歧看起来是"各自随意发挥"而非"同一种系统偏差"，
   所以这次的验证只能证明"能抓不同错法"，**不能**证明"能抓同错法"——因为这两份数据本身就不是同错的例子。
4. **代价**：两次冷启动 = 时间翻倍（约 400s → 800s），且不产生额外污染（复用既有零信息盲重抽基础设施，
   两次都保留而非"失败了才触发第二次"）。

**⇒ 建议定位**：不作为默认的第一级机制（太贵、且对系统性偏差无效），而是**当 §2.1/§2.2 的确定性检查
结果处于临界/矛盾（比如 verification_density 达标但 stroke_verification_anchor 很低）时的第二级复核**——
先用便宜的确定性检查筛，贵的双读诊断只在看不清的时候才启用。

### 2.4 Q4：07-02 的差距是"工作量没发生"还是"能力不够"？

**对 Haiku 今天这批崩溃案例，压倒性证据指向"工作量没发生"，不是"能力不够"**：07-07 同样是 Haiku、
同样的现成工具箱，只是把 crop_zoom 等验证调用做够了（记录里是"平面图 33/24 次工具调用、其中 crop_zoom
17/16 次"），就拿到 8/8。同一模型层级、同一工具箱，唯一对得上今天差距的变量是工作量有没有发生。

**07-02 不能直接拿来类比**：那是 Sonnet 5，且当时**没有现成工具箱**——它是自己发明的一套 CV 流程
（调试 numpy/scipy 连通域参数）。这里确实可能有一段真实的能力差距：**发明一套能用的图像处理调参流程本身
需要更强的编程/调试判断力**，Haiku 不一定能同等质量地"发明"工具。**但这段能力差距，现在基本已经被
"工具箱已经是现成产品"这件事绕开了**——Haiku 不需要发明 CV，只需要用现成的，07-07 证明它用到位时能拿
满分。

**机制怎么区分两者**：§2.1/§2.2 的机制本身只能**强制"工作量有没有发生"这一层**（不做验证/不闭合尺寸链，
账就不平，就重抽），**不直接测"模型看得准不准"**。**分界信号写进 §4 第一步**：如果把工作量拉到 07-07
的量级之后（verification_density/coverage 都达标、尺寸链闭合率也高），分数仍然上不去（笔画背书率低、
判卷分数仍差）——那才是能力信号真正浮出水面的时候，需要重新评估、可能需要把更多算术进一步移交代码。

**该由代码补掉的部分（已经补了一部分，不需要模型有"发明 CV"那种能力）**：`px_m_calibrator` 已经把
"像素→米换算"这段算术从模型手里拿走；尺寸链 Σ 闭合的算术也是代码干的。**真正留给模型的能力要求，
收窄成"看一眼 crop_zoom 结果，能不能正确分类这是不是墙"**——这是一个分类判断，不是发明流程，
07-07 的数据说明 Haiku 在"做了工作量"的前提下这件事能做对。

## 3. 为什么不违反 §3 的五条硬约束

1. **环节内部禁止人/更强 agent 在环**：§2.1/§2.2 全程确定性代码（数侧车文件、比坐标、算闭合），
   不是 agent；判不过的唯一出口复用既有的零信息盲重抽（§2.3 若被启用，也是两次都走同样的零信息冷启动，
   不是"失败了才由人推一把"）。**未新增任何人工/更强 agent 判断点，也没有重犯"停等审阅"这条已知死路。**
2. **不许把主控/人的临场判断当输入**：门槛数值、验证密度/覆盖率的具体阈值、触发 §2.3 二级复核的临界区间
   ——都是**随产品发布、写死在配置里的固定档参数**，来源必须是"历史样本实测分布"而非主控当场拍，
   本版 §4/§7 明确要求先做观察期再定阈值。
3. **确定性代码不算监督**：整个机制的核心卖点——把"完成度判定"从任何主体手里拿走，变成"数侧车文件、
   查闭合"这类纯算术——是这条约束**最大自由度**的直接兑现。
4. **标准向前看，不为历史让步**：本稿明确承认——07-02（无 `cv_evidence` 侧车、走自建 CV）和 07-07
   （有侧车、但因反馈机制不算无监督基线）**能不能通过新门槛，本版没有验证过**（§7 待实测）；
   如果验证后发现某个历史高分过不了新账本,不应该为了保住它去调松门槛。
5. **建筑复杂度可扩展**：尺寸链闭合是形状无关的 1D 区间算术；验证痕迹核账（数侧车文件+算覆盖面积）
   本身也和户型形状无关，只是复杂户型大概率需要更多验证调用——**门槛应该按图纸复杂度自适应，
   这点本版明确标为未来待做，不是当前矩形+走廊布局烤死的假设**。

## 4. 落地分期

**第一步（低成本、可逆、纯观察，不需要重新识图）**：
- 对已有历史样本计算 §2.1 的三个数值：**07-07**（有 `cv_evidence` 侧车、无预扫，作为"高工作量"参照，
  即便它的达标资格因反馈机制被撤销，侧车计数事实依然可以拿来看数值范围）、**今天的 d1/d2**（有预扫、
  零手动侧车，已核实）。**07-02 因为没有 `cv_evidence` 侧车（走自建 CV），无法用这套计数法参与比较，
  只能当背景参照，不能当验证样本**——这一点在 §7 里必须明确标注，不能含糊处理。
- 同步跑一次 §2.3 的事后 diff（用现成的 d1/d2 数据，本稿已经算过一版，见 §2.3 表格）。

**能拿到的信号**：`verification_density`/`coverage` 在"07-07（高工作量）"vs"d1/d2（零工作量）"两组之间
是否有明显 gap（预期：会有，因为 07-07 侧车数十条、d1/d2 侧车为零，这不是渐变分布而是有/无的差异，
分辨力预期比原版基于预扫候选的比例更干净）。

**什么信号说明这条路走错了**：
- 如果扩大样本后（不只 d1/d2 这一对崩溃产物，还要找更多历史崩溃/达标样本）verification_density 在
  "好"与"差"之间**仍然区分不开**——说明这套代理指标同样没有分辨力，是 §4.4（原问题书数据）那次
  "阻断层对 8/8 与 1/8 结论逐字相同"的翻版，必须停下重新设计，不能强行拿来当阻断门。
- 如果工作量强制拉高后（未来批次做到），分数仍然上不去——见 §2.4，这是能力信号，需要跳出本机制
  重新评估。

**第二步**：验证 §2.2 尺寸链闭合机制在历史样本上的表现（闭合率、认领率），同样先观察不阻断。

**第三步**：两抽纪律下的门槛校准（§6），升级为 golden/regression profile 下的阻断项。

**第四步**：正式实现 §2.3 的二级复核触发条件（先用便宜检查筛,贵的双读诊断按需启用）。

**第五步**：门槛达标后若分数仍上不去,回头评估 §2.4 提出的能力缺口分界,决定要不要把更多算术移交代码。

## 5. ⭐ 我自己的反对意见

从最脆弱到次脆弱：

1. **最脆弱的假设——相关不等于因果**：07-07（高验证工作量）拿到 8/8、d1/d2（零验证工作量）拿到
   9.0%/24.8%，这是我论证的核心证据，但**我没有做受控实验把"工作量"和"当天模型/prompt 状态本身更好"
   这两个可能同源的因分离**。如果真正的因是某种我没识别出的状态变量（比如那次会话恰好在某个更有利的
   点上），工作量只是伴随的副产品而非原因,那么"强制它多调用验证工具"本身不会带来分数提升——
   它完全可以敷衍地多调用几次 crop_zoom（bbox 覆盖了对的区域）但并不真正观察结果就写数据。
   **这条风险和上一版的 Goodhart 风险同构，换了证据来源没有消除它，只是让作弊成本变高了一点**
   （现在至少要真的调用工具、bbox 要覆盖 claim 区域，而不是凭空编一个候选 id）。
2. **尺寸链闭合的局限是继承的、没解决**：gate① 代码注释自己写明"a self-consistent wrong read still
   closes"——一组编造但自洽的分段数字一样能通过闭合检查。算术自洽不等于数字真的是从图上抄的。
3. **验证密度门槛怎么定，本身有隐藏的人工判断**：§4 说"先观察、看数值能不能区分好坏"，但样本目前只有
   一对崩溃数据（d1/d2）和一份因反馈机制作废的参照（07-07），**样本量严重不足以支撑一个稳健的阈值**，
   门槛定得早了会重复"S-0 分辨力=0"的老问题,定得晚了又拖慢整个机制上线——这个平衡点本身没有干净答案。
4. **07-02 数据不可比这件事,本身削弱了"能力已经被工具箱抹平"这个乐观判断的证据力度**：我在 §2.4
   论证"Haiku 现在只差工作量不差能力"，主要证据是"07-07 证明 Haiku+工具箱能拿满分"——但 07-07 这份
   数据因为主控按子部分打回，**本身已经不算合规的无监督基线**，我引用它做能力论证时用的是"侧车计数
   这个事实部分"而非"8/8 这个成绩部分"，这个切割是否站得住,需要更谨慎对待，不能把"侧车多"直接等同于
   "能力够"。
5. **Q3 双读机制的触发条件本身可能形同虚设**：定位成"二级、临界时才触发"是为了控制成本，但如果没有人
   （或者说没有确定性代码）真的去执行这个"临界判断→触发第二次"的调度逻辑，它就会重演 `self_check` 的
   命运——写在纸面上但从来没被真正打开过。这条需要在实现时给出明确的、默认开启的触发规则，而不是留成
   可选项。

## 6. 验证方案

1. **两抽纪律不变**：任何验证 §2.1/§2.2 机制有没有分辨力的实验，必须对同一套配置独立跑至少两次，
   报告数值时同时报两抽结果和差值，不接受单抽结论。
2. **第一个要看的数字**：扩大样本后，`verification_density`/`coverage` 在"07-07 类（有侧车高工作量，
   即便资格作废，侧车事实仍可用）"与"d1/d2 类（零侧车）"两组间是否有清晰 gap——这一步需要**更多样本**，
   目前只有一对崩溃数据，不足以下结论，需要项目组补充跑几轮才能验证。
3. **第二个要看的数字**（**本稿已经做过、可以立刻复核的部分**）：d1/d2 互相 diff 的一致率——本稿算出
   周长墙 4/4 完全一致（0.00m）、内部墙 0/9 一致（最近 0.6–2.6m），**建议项目组独立复算这个数字确认
   我的计算没有错**（脚本很简单：墙笔画中点最近邻匹配，见 §2.3）。
4. **第三个要看的数字**：尺寸链闭合率在历史样本上的分布（用既有 `_chain_closure` 直接跑，不需要新代码）。
5. **不接受的证明方式**：只跑一次就下结论；用 GT 分数反推调整门槛（违反"标准答案只有判卷和人可读"）；
   只在 sm24 一个 case 上验证复杂度可扩展性（至少要设想一个非矩形 case 的行为，即便不真的跑）。

## 7. 假设 vs 待实测（明确区分）

**我的假设（本稿论证依赖，未经充分实测）**：
- 验证工作量痕迹（crop_zoom 等手动调用的数量+覆盖度）与真实完成度正相关——目前只有 d1/d2（零工作量、
  零侧车）和 07-07（高工作量、有侧车但资格作废）两个参照点，**样本量不足以下结论**，需要更多历史/新跑
  样本才能验证 gap 是否稳健存在。
- Haiku 现在的能力已经被"工具箱已产品化"这件事基本抹平了 07-02 那种"发明 CV 流程"的能力缺口——
  这是从 07-07 侧车数据推出的判断，**没有找到"Haiku+工具箱+高工作量但仍读错"的反例去证伪它**，
  需要项目组专门找/构造这样一个反例来测试这个假设的边界。
- 07-02 的 112 次调用量级可以当"复杂图纸值多少验证工作量"的背景参照——这是我的直觉判断，

**需要项目组去实测确认的（不是我能在这轮点射里做的）**：

  需要工程侧结合更多样本标定。
- 一个专门设计的反例实验：Haiq+工具箱+被强制拉高工作量之后，是否仍然读不准——这是判断"工作量 vs
