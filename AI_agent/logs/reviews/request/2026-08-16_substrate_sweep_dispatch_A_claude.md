## 1. 背景（为什么有这一单）

reading 环节的读图器跑在一个**隔离沙箱**里。它调用 CV 工具的唯一入口是 staging 根下的
`tools/run_cv_probe.py`（wrapper），wrapper 再去调真正的 `cv_probe`。这套 wrapper 地基 2026-07-08 落地。

**2026-08-16 一天之内，在这层地基上串行撞出三个缺陷**：

1. **F-45**：随产品发出的文档示例，命令形态在沙箱里逐条被 DENY；
2. **F-49**：`anchors_json` 被当成路径参数 ⇒ **像素→米的唯一那把尺子**，文档与 wrapper 自带 usage
   写的两种形态**全都跑不通**，唯一可用形态没有任何文档写过。自 07-08 起，隔离形态下这把尺子
   **一次都没被成功调用过**；
3. **F-51**：读图器自报的像素坐标在**降采样帧**里，而工具读**原分辨率文件** ⇒ 标定自洽但整体错约 54%。

**三者串行遮挡**：示例被 DENY ⇒ 看不见参数语义错 ⇒ 看不见坐标系错位。每揭一层烧一次真实跑测。
**根子**：这套地基上线时，**全仓没有任何一把测试会因为「工具链算出来的数是错的」而变红**，潜伏了五周多。

⇒ 本单的目的**不是**再撞一个，是**一次把基座逐格过完**，并把结论变成测试的属性。

## 3. 格子表规格

### 3.1 三种调用形态（每个工具都要走完这三种）

| 代号 | 形态 | 命令 |
|---|---|---|
| **B** | 直接参数 | `python tools/run_cv_probe.py --tool <T> --image case_data/<X>.png --out-dir out/cv [--k v ...]` |
| **A** | 请求文件 | `python tools/run_cv_probe.py --request requests/<r>.json`，文件内容 `{"tool":"<T>","args":{...}}` |
| **C** | 批量文件 | `python tools/run_cv_probe.py --batch requests/<b>.json`，内容 `{"requests":[{"id":"<id>","tool":"<T>","args":{...}}]}` |

### 3.2 六个授权工具（⚠️前提：`ALLOWED_TOOLS` 就这六个，prescan 两个已于 08-15 撤除——请核）

`crop_zoom` · `wall_line_profiler` · `storey_line_profiler` · `px_m_calibrator` ·
`window_cc_detector` · `overlay_logger`

**S-1 主表 = 6 × 3 = 18 格**，每格用该工具的最小可用参数集，判「跑通 + 数对」。

### 3.3 参数形态表（S-2）

**⚠️前提（请核）**：授权工具的参数面 = 6 个公共参数 + 15 个专属，共 51 格（有重复）。
公共 = `image` `out_dir` `recipe` `bbox` `scale` `sidecar_name`；
专属 = `axis`(wall_line_profiler) · `anchors_json` `residual_warn_px` `residual_warn_m`(px_m_calibrator) ·
10 个过滤参数(window_cc_detector) · `candidates_json`(overlay_logger)。

**每个参数至少测下面这几种写法**（B 形态下一切都是字符串；A/C 形态下 JSON 值可以是原生类型）：

| 参数 | B 形态 | A/C 形态·自然 JSON 写法 | A/C 形态·字符串写法 |
|---|---|---|---|
| `image` / `out_dir` | 相对路径 | 同左（字符串） | — |
| `recipe` | `--recipe clean_vector_v1` | `"recipe":"clean_vector_v1"` | — |
| **`bbox`** | `--bbox 100,80,700,460` | **`"bbox":[100,80,700,460]`** ⚠️ | `"bbox":"100,80,700,460"` |
| `scale` | `--scale 2` | `"scale":2` 与 `"scale":2.0` | `"scale":"2"` |
| `sidecar_name` | `--sidecar-name mycrop` | 同左 | — |
| `axis` | `--axis col` / `row` | `"axis":"col"` | — |
| **`anchors_json`** | 内联 JSON 字符串 | **原生数组** | 文件路径字符串 |
| **`candidates_json`** | 内联 JSON 字符串 | **原生数组** | 文件路径字符串 |
| `residual_warn_px` / `_m` | `--residual-warn-px 1` | `"residual_warn_px":1` | `"1"` |
| window 的 10 个过滤参数 | 字符串数字 | 原生 int / float | 字符串数字 |

**⚠️ 我读代码看到的一个候选缺陷（未实跑，⛔ 不是结论，请你验）**：
A/C 形态下 `"bbox":[100,80,700,460]` 会被 wrapper `json.dumps` 成 `--bbox [100,80,700,460]`，
而 `cv_probe` 的 `_bbox` 按逗号切后拿到 `"[100"` ⇒ 可能直接报错。**这与 F-49 是同一族**
（参数在 JSON 形态下的自然写法跑不通）。如果成立，登记为新缺陷；如果不成立，**明确写「证伪」**。

## 4. 合成夹具（本单的判据来源）

**为什么要合成图**：真实图纸上没有「已知正确答案」，只能判「跑没跑通」；
而本单要判的恰恰是**「跑通了但数是错的」**。所以每格的期望值必须来自一张**由构造决定真值**的图。

**照抄现成形态**：`tests/test_f51_source_frame_roundtrip.py` 已经做过一份
（1200×600、两条竖线在 x=100/700、真值 40 px/m），并且是**经真实 staging + 真实 CLI 子进程**跑的。
**沿用它的骨架**（`build_isolation_workspace` 建真 staging → 把合成图写进 `case_data/` →
`subprocess` 跑 `python tools/run_cv_probe.py ...`），把图扩成能覆盖六个工具：

建议构造（可调整，但**每一处真值必须由构造决定并写进文档**）：

- **2 条整高竖线**（灰度 128，宽 4）在 x=100、x=700 → `wall_line_profiler --axis col` 的期望位置；
  配 `value_m=15.0` 给 `px_m_calibrator` ⇒ 真值 **40.0 px/m**。
- **2 条整宽横线** 在 y=150、y=450 → `wall_line_profiler --axis row` 与 `storey_line_profiler` 的期望位置。
- **2 个实心矩形**（灰度 128），bbox 由你定且写死 → `window_cc_detector` 的期望框与面积。
- `overlay_logger` 的期望 = 传进去的候选**全部出现在决策记录里**、overlay PNG 真的产出。

**⚠️ 灰度必须落在 `clean_vector_v1` 的灰带内**（现有夹具用 128，注释说灰带是 60–230）——请核。

**⚠️ 期望值可能有歧义时怎么办**：例如矩形也会在投影里产生峰值，profiler 可能返回多于 2 个候选。
这时**不要硬凑**：把期望写成可判定的形式（如「最强的两个候选在 x=100±1 与 700±1」），
或者**如实记录实际值并标 `需裁决`**，由主控判。⛔ 不许为了让格子变绿去改期望值。

## 5. 锁的规格（`tests/test_substrate_sweep_tools.py`）

1. **走真实入口**：每把锁都必须经 **真 staging + `subprocess` 跑 staged wrapper**。
   ⛔ **不许直接 import 工具函数来测** —— 本仓已明确吃过这个亏（主树里直接调库**不迁移**到沙箱 wrapper 形态，
   F-49 潜伏五周正是因为库层测试全绿）。
2. **通过的格子 → 正锁**（断言那个**数值**，不只是退出码）。
3. **失败的格子 → `@pytest.mark.xfail(strict=True, reason="F-52 …")` 锁**。
   `strict=True` 的意义：缺陷修好后这把锁会**变红提醒摘掉**，不会静默漂过去。
   ⛔ **绝对不许把失败行为写成正向预期** —— 本仓吃过这个亏
   （`test_neuter_restoring_stamp_flips_judge_back_to_accept` 把一个 bug 锁成了正确语义，
   判据是「锁越完备，越会把错误的语义固化下来」）。
4. **锁必须自证有分辨力**：至少挑 3 把正锁做一次 **neuter**（临时把被测实现改坏 ⇒ 确认锁真的变红 ⇒ 还原）。
   ⛔ 还原后必须 `git diff` 确认零残留，并把 neuter 过程写进 grid_A.md。
   （判据：**变红才算接线，形状匹配 / 代码审查不算**。）
