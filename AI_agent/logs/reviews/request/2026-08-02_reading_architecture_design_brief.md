## 0. 背景（冷启动自包含）

### 0.1 项目与 reading 在其中的位置

建筑图纸 → EnergyPlus 能耗模型的多模态管线，分 0–5 段：

```
0_reading 识图（VLM 读图纸 → 结构化 JSON）
  → 1_correction 校正（LLM，image-blind 纯文本）
  → 2_modelling + 3_split_pairing 几何内核（确定性代码）
  → 4_mep 物理（LLM）→ 5_intakeoutput 装配（代码）
  → 下游 9 个 subagent → IDF → EnergyPlus 仿真
```

**分工铁律（项目不变量 #1）**：LLM 只做感知 + 校正判断 + 物理语义；**所有几何由代码做**。
`0_reading` 的产物是**图像局部（image-local）的观测**：墙的笔画 strokes、窗、尺寸标注转录 `ocr_texts`、
标定信息、以及每条观测的来源 `provenance`。世界坐标落位是下一段（`1_correction`）的活，
**读图器明令不许做世界落位声明**。

每段有两道门：**gate①** 确定性自检（代码，产出 `*_checks.json`，按 `run_profile` 分档决定 fail 是否阻断）
+ **gate②** judge（结构化清单，dev 期）。判卷把识图产物与人工签字的标准答案 GT 逐元素对账。

### 0.2 现在为什么单独攻 reading

用户拍板：**先把 reading 解决，再回归主线**（主线 = sm24 端到端跑通 → sm25-L → C2 收官）。
过去一个多月，识图质量的成绩在 9 % 到 100 % 之间剧烈摆动，且**归因一直不干净** ——
每次以为找到原因，下一轮就被推翻。本轮要求把它彻底收口。

### 0.3 ⭐ 用户已拍板的方法论（**不许推翻，是本设计的前提**）

> **先保证质量，从高档模型往低档模型上降，而不是先降模型、拿到很低的分数再想办法提分数。**
> 既然已经有 Sonnet 几乎全对、Haiku 加轻量介入也基本全对，
> **不应该容忍分数掉到 40–70 % 再想办法提升。**
> **「之前的成绩是假象」= 指「Haiku 纯自己做到全对」是假象**，不是指那个 100 % 是作弊 ——
> **100 % 是真的**，只是不是低档模型的单一功劳。
> **应该思考的是怎么把这条已经存在的正确路径让 Haiku 也掌握**，
> 而不是为 Haiku、或为这两个 case 定制一套方案然后迭代。

⇒ 正确形态 = **降档阶梯**：① 高档零介入确认路径存在 → ② 把走对的路径提成工序 →
③ 换低档模型跑同一条工序、看在哪一步断 → ④ 断哪补哪（**能代码化的就代码化**）。
**每一档都要求接近全对**；掉到 40 % 是「这一档不合格、回去补工序」，不是「这一档的新基线」。

⇒ **降档的真实动因**：reading 后续要转**本地开源 VLM 部署**。Haiku 4.5 是那个档位的**代理基准**，
不是为了省实验费用。这决定了方案不能依赖只有顶级闭源模型才有的能力。

### 0.4 ⭐⭐ 本批次到底要做成什么（**2026-08-02 用户当面更正，是本文最重要的一节**）

**「完全自主（零 `reading-agent`）拿到好 reading」是北极星长期目标，不是本批次的目标。**
用户原话：**目前看来长期还是依赖有 `reading-agent` 的形态**；等这条路先拿到好 reading 之后，
**再尝试把 `reading-agent` 撤掉，看能不能行。**

**⇒ 本批次的验收 = 在 sm21 和 sm24 两个 case 上，在 `reading-agent` 在场的情况下，都拿到接近满分。**

**本质是「先恢复到 Haiku 做 sm21 / sm24 满分的那个状态」** ——
因为那个时候**本来就有高档模型部分介入**。这批要做的是把当时那个介入**换一种形态**：

| | 当时（07-07） | 本批要做成的 |
|---|---|---|
| 谁在介入 | orchestrator **临场**看着失败现调 | **固化成 `reading-agent`** |
| 与 orchestrator 的关系 | 就是 orchestrator 本人 | **与 orchestrator 彻底隔离** |
| 介入者的智力档位 | 最高档 | **降档**（Flash 级或以下） |
| 读图的那个 | Haiku（`reading-worker-agent`） | Haiku，不变 |

⇒ **本批不是「提高分数」，是「把已经达到过的分数，用合规的形态重新达到一次」。**
⇒ 因此**方案的核心问题不是「要不要 `reading-agent`」，而是「怎么把当时那个临场介入正确地固化下来」。**

### 1.5 单抽是噪声

同配置独立两抽（d1 / d2，考试范围哈希与答案账本哈希均逐字相同，机械证明配置一致）：

### 1.6 ⭐ 「信号产出了、没有消费者」—— 同一个病撞见三次

| 信号 | 现状 |
|---|---|
| `self_check.all_visible_strokes_captured` 等四个**结构化自评字段** | 读图器**诚实填了 `false`**（并附「只描了主要分隔」「窗检测到但没画」），**全仓生产代码零消费者**（`grep`：只出现在 schema 文档与产物里，`src/` 零命中）⇒ gate① 0 阻断放行 |
| `cv_evidence` / `prescan` / `candidate_id` | `src/validator/` 对它们**零引用** |
| 考场守卫写的 `access_log.jsonl`（命令原文 + 放行/拒绝 + 理由，按 attempt 归档、进指纹、**被测者伪造不了**） | **零消费者** |

**⇒ 读图器没有不听话**：它读了自检清单、诚实自评、正确判定自己没做完、写进指定字段、提交。
**没人说过 `false` 不许提交，也没人去看那个字段。**

**⚠️ 但有一盆冷水，决定了方案形态**：另一抽（d2）**四个自检字段全填 `true`，成绩仍只有 24.8 %**。
⇒ **把自评变成阻断项只能抓「诚实的没做完」，抓不住「自信的做错」**，
且最可能的结果是**让 d1 学会变成 d2**。
⇒ **「完成度由谁判定」必须有一个不依赖自评的答案。**

### 1.9 已知的能力缺口与未收口的契约

- **「量了但基准错」会被判成「没量」**：08-02 那 12 段失分的

## 2. ⭐ 用户已拍板的治理口径（**硬约束，方案必须落在里面**）

以下为项目不变量 #7（2026-08-02 用户重订的第三版，与更早两版冲突处以本版为准）。

### 2.1 **orchestrator** 对某个环节内部：**只能启动与接收**

- ✅ 可以：创建 job / 传入**冻结的** case bundle + profile / 等待 /
  接收 `status + output + evidence manifest`；dev 期编排（建工作区 / spawn / merge / 跑确定性工具 /
  决定跑什么）仍合法；**orchestrator 兼任 judge 仍合法**（judge 是 dev 辅助，不属产品环节）。
- ⛔ 不可以：写自由文本 directive / feedback；**看了图之后指导 worker**；替它挑 CV 参数或返工区域；
  操作环节内部会话；**接触 GT 之后把任何结论送回同一个 run**。

### 2.2 ✅ 环节内部**允许**有 `reading-agent`（08-02 新增许可）

`reading` 可以配置属于 reading 环节**内部**的调度 agent 去指挥 `reading-worker-agent`，条件是：

1. 与 orchestrator **彻底解耦**（外部看仍是 reading 自己走完 输入 → 输出）；
2. **档位不高**（DeepSeek v4 Flash 级或以下、thinking off、结构化输出、短上下文）；
3. **有界**：最多「一次任务计划 + 一次局部返工」，不重抽整栋，**不得直接写最终坐标**
   （最终 stroke 必须来自 `reading-worker-agent` + 工具证据）；
4. 它是**权衡方案不是永久架构**，后续要代码化 / 降档 / 撤除。

### 2.3 ⛔ 成绩记账：**两条正式 lane + 一个 dev 期职能**（2026-08-02 用户更正）

⚠️ **此前记成「三条并列 lane」是错的**，tool-invention 不是成绩 lane。正确结构：

**两条正式成绩 lane**（配 `reading_mode` provenance 块：`reading-agent` / `reading-worker-agent` 各自的模型、
`reading-agent` 是否看图、返工轮次、工具箱版本、隔离档）：

- **autonomous**：目标 VLM + 冻结工具箱，**零 `reading-agent`** —— **北极星，长期目标**；
- **controlled**：+ `reading-agent` —— **本批次的验收 lane**（见 §0.4）。

**controlled 完全算真实工程成功**，但**不得记成「弱模型独立满分」**。
**autonomous lane 必须一直保留**，否则不知道离「本地开源 VLM 自主完成」还有多远。

**另有一个 dev 期开发者职能（不是 lane、不产生正式成绩）**：

> 允许一个**最强的模型**去**观察 reading（乃至其他环节）的内部过程**，
> 从中**提炼方法论、搓适配工具、改进流程**，把这些作为**成果资产纳入项目开发本身**。

- **角色归属**：用户**倾向 orchestrator 兼任**（可在细稿里讨论，但要给理由）。
- **⛔ 铁律**：**不能给项目生产本身提供信息**；**可以**提供思路、方法、工具。
- **⛔ 这种模式下的跑测不作为正式成绩。**
- **⛔ 一个 case 的收官验收，必须脱离这个角色完成**
  （即验收时跑的是已固化的工序 + 已冻结的工具箱，该角色不在场）。

### 2.4 ⛔ 隔离原则（08-02 改写）

> **严格限制可见信息与写出边界，不限制在合法输入上采用何种计算方法。**

要防的是**漏题与污染**（GT / baseline / judge 结论 / 其他 run / 历史答案 / 网络外传），
**不是**模型用了哪种算法。**按命令形态封杀通用 CV 编程属于「能力封口」**。

### 2.5 judge 出口不变

判定不过 ⇒ **整轮盲重抽、零信息**（相当于另外做一次）；
judge **不得**告诉执行环节「哪里错了、该怎么改」。
（注意区分：**环节自己的 `reading-agent` 做局部返工是允许的**；受此约束的是**跨环节的评判者**。）

### 2.6 建筑复杂度可扩展性铁律（项目不变量 #6）

**每个决策必须为未来建筑复杂度升级留路**（非方形 / 退台 / 挑空双层高 / 中庭竖井）。
**不得**把「共用 footprint / 每层满铺楼板 / 固定层高」这类当前简化假设**烤死到无法松动**。
**纯只适用当前情况的方案没有意义。**
⇒ 具体到本设计：**不得把方案绑死在 sm24 / sm21 这两栋楼的形态上。**

## 5. 已知的坑（**请在方案里绕开，或明确说明为什么不用绕**）

1. **文档不能验证别人是否遵守它**（§1.7，连败三次）。
2. **自评不能单独当完成度判据**（§1.6 冷水：四字段全 `true` 仍 24.8 %）。
3. **单抽是噪声**（§1.5，2.8 倍）——任何结论至少两抽。
4. **provenance 字段判不出「量没量」**（§1.3 反例）。
5. **预扫召回不足**（§1.9，5 条 vs 16 段）——不能直接拿来当完成度分母。
6. **减卷有害**（§1.4）——不要用「缩小范围」来降低难度或省成本。
7. **按命令形态封能力**（§1.8）——会封掉已知的成功路径。
8. **「探针 ≠ 锁」**：临时跑通一次的探针不具备回归效力，每条守卫要有**摘掉即红**的锁。
9. **「非 None ≠ 成功」**：曾有锁断言 `score_vs_gt is not None`，而判卷器**拒绝**时侧车也不是 None
   ⇒ 锁绿着、判卷其实是拒的，三道审全漏。
10. **「门是真的、锁是缺的」**：守卫逻辑正确但无任何测试绑住它，多批复发。
11. **放水比冤枉危险**（项目既定口径）——fail-safe 的默认值要慎重，
    对未知形态系统性放水正是历史上的实际后果。
12. **不要为两个 case 定制**（§0.3 用户原话）——sm24 / sm21 之外要能长。

## 7. 交付形态

一份**累计式自包含**的设计细稿，逐条覆盖 Q-A … Q-H，每条给：

1. **方案**（做什么、放在哪一层）；
2. **依据**（引到具体文件行 / 实跑证据 / 上面的事实编号）；
3. **你考虑过但否决的替代方案，及否决理由**（这一项是硬要求 ——
   本项目多次因为「机制选对、边界留给施工方猜」而返工，替代方案的否决理由是边界的一部分）；
4. **验收形态**（怎么机械地证明它做到了；每条新守卫的「摘掉即红」的锁断言什么）；
5. **风险与副作用**（尤其：会不会让某类真实缺陷从此检不出来；会不会烤死当前建筑形态的假设）；
6. **施工拆批与顺序**（含哪些可以立刻开工、哪些必须等拍板）。

**无法在不施工前提下判定的，明说无法判定 + 「要判定需要跑什么」，不要用推测填充。**
本项目吃过大亏：一个 judge 的判语被当成事实继承，导致整个归因方向错了好几轮。

**⚠️ 最后**：如果你认为本问题书的问题分解本身有问题（漏了更重要的、或某个问题问错了），
**请直接说并给出你认为对的分解** —— 这比顺着答更有价值。
