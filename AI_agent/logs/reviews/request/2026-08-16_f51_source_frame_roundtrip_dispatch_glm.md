## 1. 背景：这一刀要解决的是什么

**F-51（今日实测坐实）**：读图器（VLM）看到的图是被降采样到约 1.2 MP 的版本
（`1f_view.png` 2133×1345 → 约 1381×871），**它自报的像素坐标在那个帧里**；
而 `cv_probe` 读的是**原分辨率文件**。

单变量实验（haiku，A×3 目测 / B×2 先调一次工具再答，问四面外墙外皮的源图像素）：

| 臂 | west | east | 落在降采样帧内(<1381)？ |
|---|---|---|---|
| A1/A2/A3（目测） | 107 / 294 / 104 | 1254 / 1256 / 1259 | **是**（12 个数字无一例外） |
| B1/B2（先调工具） | 275 | **1888** | **否 ⇒ 源图帧** |

真值 west=426 / east=1816。⇒ **目测坐标被困在降采样帧内、系统性偏小、且不稳定**
（A 臂 `west_x` 三抽 107/294/104，近 3 倍散布；B 臂两抽逐字节相同）。

**后果**：标定自洽却整体错、C1 跨轴门放行（同比例偏移 ⇒ 偏差 0.000%）、
crop 落在错误区域产生**诚实的假阴性**。

**⇒ 本单的目标不是「修好模型的眼睛」（做不到），而是给它一个能自查的锚**：
**让每一份 cv_probe 侧车都回报源图的真实像素尺寸**，并**补一条端到端往返锁**，
使「工具链算不出正确比例」这件事从此会让测试变红。

**元教训（本单存在的理由）**：`run_cv_probe.py` 自 `df6f249`（2026-07-08）落地，
到 2026-08-16 之前，**全仓没有任何测试会因为「标定调不通」而变红** ——
F-45 / F-49 / F-51 三个缺陷因此潜伏了五周多。

## 3. 要做的三件事

### A. `write_sidecar` 回报源图真实尺寸

`src/agent/reading/cv_toolbox/sidecar.py` 的 `write_sidecar()` 目前构造：

```python
"source_image": {"name": ..., "sha256": source_hash},
```

改为**再带两个键**：`"width_px": <int>`, `"height_px": <int>`，取自实际打开的源图。

- **这是唯一收口点** —— 六个工具（`crop_zoom` / `wall_line_profiler` / `storey_line_profiler`
  / `px_m_calibrator` / `window_cc_detector` / `overlay_logger`）全部经它落盘，
  ⛔ **不要在六个工具里各改一遍**。
- 键名就用 `width_px` / `height_px`，⛔ 不要自创别名。
- 尺寸必须是**源图**的，不是 crop 之后的；有 `crop_chain` 时也仍然是源图尺寸。
- 现有键一个都不许删改（`name` / `sha256` 保持原样、位置无所谓，文件本就 `sort_keys=True`）。

### B. 端到端往返锁（新建测试文件）

**三条锁，全部经真实 CLI 入口**，⛔ 不许只调内部函数：

- **L1 往返比例**：用 PIL **在测试内合成**一张已知比例的图（⛔ 不要新增二进制夹具文件），
  例如 1200×600、在已知像素位置画两条竖线，令真实比例为一个整数 px/m；
  经 `python tools/run_cv_probe.py --tool px_m_calibrator --image … --out-dir out/… --anchors-json …`
  跑通，断言侧车里的 `axis_px_per_m`（或该版本实际字段名，**以实跑输出为准**）
  等于真值，容差 ≤0.5%。
- **L2 尺寸回报**：断言侧车 `source_image.width_px` / `height_px` **等于合成图的真实尺寸**。
  至少覆盖 **`px_m_calibrator` 与 `crop_zoom` 两个工具**（后者带 `--bbox`，
  用来证明「crop 之后回报的仍是源图尺寸」）。
- **L3 帧错位可被自查**：构造一个「读图器式」的错误 —— 把 L1 的锚点像素**整体乘以 0.6**
  再跑一次，断言得到的 `px_per_m` 与真值**明显不同**（≥20% 偏差）。
  **这条锁的意义**：把「同比例缩放的锚点会产生一个看似正常、实则整体错的标定」
  钉成一条会说话的测试，⛔ 它**不是**要求工具去拒绝这种输入（那是 C1 的地盘、本单不动）。

**测试运行环境**：必须在**真实 staging** 里跑（`spawn_isolated_reader.py build` 造一个到 `tmp_path`），
理由 = 主树里直接调函数与沙箱里经 wrapper 调用**形态不同、结论不迁移**（本项目已因此栽过）。

### C. 文档：告诉读图器怎么用这个锚

`skills/intake_pipeline/0_reading/cv_toolbox.md` 加一小节（位置自定，简洁即可），
内容须包含这三点，措辞你自己组织：

1. 每份侧车的 `source_image.width_px` / `height_px` 是**源图的真实像素尺寸**；
2. **你目测出来的像素坐标可能来自一张被缩放过的图**；把你以为的图宽与侧车回报的宽度对一下，
   不一致就说明你的像素坐标整体带一个比例误差；
3. **凡是要交给工具的像素坐标，优先用工具回读的数字，不要用目测的数字。**

⚠️ 文档里写的任何命令形态**必须实跑验证过**（本项目连续栽过两条：F-45 路径/参数形态错、
F-49 参数语义错，**都是文档里的示例本身跑不通**）。
