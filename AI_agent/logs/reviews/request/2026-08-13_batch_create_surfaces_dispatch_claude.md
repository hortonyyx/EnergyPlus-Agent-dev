## 1. 要解决的结构问题（已实测定死，不是推测）

下游 `surface` 节点确定性/间歇性崩在 DeepSeek 400
（`"An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'"`）。
**两轮诊断把机制收敛到了「历史规模」，且把两条错误解释排除掉了**：

| 探针（GPT 侧活体实测） | 结果 |
|---|---|
| 一条消息 28 个调用 + **全部 28 条回应** | provider **接受** |
| 客户端截断成 1 个调用 + 1 条回应 | provider **接受** |
| **生产里 50 个调用 / 50 条回应、内容非空（104–116 字符）、零未配对/零重复/零孤儿** | **被拒 400**，重发同一历史 **3/3 全拒** |

⇒ ⛔ **那条错误消息是误导性的**：它说配对问题，而配对是好的。
⇒ ⛔ 已被排除：「provider 无视 `parallel_tool_calls=False` 的批量是触发条件」（第一轮结论，**已证伪**）·
「provider 记着它下发过的全部 id、我们丢弃就必然被拒」（第二轮首要假设，**已证伪**）。

**而结构性事实是（orchestrator 核实）**：仓里有 `update_surfaces_batch`（批量更新，`src/mcp/api/envelope.py:1051`）、
有 `create_fenestration_surfaces_batch`（批量建窗），**但没有「批量创建面」** ——
`create_surface` 只有单个版本（`src/mcp/api/envelope.py:784` · `src/agent/tools/surface_tools.py:13`）。
⇒ **100 个面 = 100 次工具调用堆在同一个对话里**，而 50/50 就已经被拒
⇒ **这个节点的工作量结构上就要求一份 provider 会拒掉的历史**。
（之前 08-11 与今日 09:02 能跑通，属运气边缘，⛔ 不是稳定能力。）

## 2. 要做什么

**加一个「批量创建面」工具**，让 surface 节点用**几次调用**建完 100 个面。

- **⭐ 必须照抄仓内既有先例的形态**，⛔ 不要自创风格：
  `create_fenestration_surfaces_batch`（批量创建的先例）+ `update_surfaces_batch`（批量写的先例）——
  **入参形状 / 校验方式 / 逐条错误报告 / 部分失败语义 / 返回结构**都要与它们一致。
  **先读那两个再动手**，并在报告里说明你对齐了哪些约定、哪里不得不不同（以及为什么）。
- **工具要真的接到 surface 节点的工具集上**，并且**提示词要真的会用它** ——
  ⚠️ 只加工具不改提示词 = 这摊活白做（模型不会去用它）。
- ⛔ **不许减少真实工作量**：仍然必须建出 **100 个面**，几何一模一样（见 §4 验收 A5）。
- ⛔ **不许放宽/关闭任何门**来「跑通」。
- ⛔ **不许改 `parallel_tool_calls` 相关逻辑或 `react.py`** —— 那是刚完工的摊 H 的面，本摊别碰。
