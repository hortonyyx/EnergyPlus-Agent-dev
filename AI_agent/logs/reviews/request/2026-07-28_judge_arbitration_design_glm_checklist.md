## 0. 怎么用这份清单

**这是设计稿评审，不是代码审。** 你的任务是逐条判定下列命题**成立 / 不成立 / 无法判定**，每条都写死了「验什么」和「什么算不成立」。

**纪律**：
1. **逐条给独立证据**，不采信设计稿的自述。能用代码/探针验的就去验（仓库在手，可读现码、可在 `/tmp` 跑探针）。
2. **不要改任何生产码、测试或 GT**；探针只在 `/tmp` 做。
3. 判「不成立」必须给出**具体反例或矛盾点**；判「无法判定」要说清楚缺什么才能判。
4. **不要因为清单没列就放过明显问题** —— 清单外的发现单列一节。
5. 出口：**APPROVE / APPROVE-WITH-CHANGES / REWORK** + findings 分级。

**背景（一句话）**：这三条缺口的施工版已被连续三轮判 REWORK，每轮都在同一形状上换新脸。所以本轮评审的核心不是「方案好不好看」，而是**「这套判据会不会在第四个位置再破一次」**。

## 1. 核心原则的覆盖性（P1–P3）

**P1**：设计稿 §0 的核心原则——「判卷结论必须由可复算的证书支撑，不能由执行顺序、错误文案、浮点偶合或未保留的语义前提支撑」——是否**逐一覆盖**了三次失败的病因？
- 验：把四个禁止项与三轮的实际病因一一对应（r2 = advisory 抢跑执行顺序；r3-B1 = reason 白名单即错误文案；r1/r3 = 固定窗与零容差即浮点偶合；R2-B2 = 来源身份丢失即未保留的语义前提）。
- **不成立** = 存在某一轮的病因不落在这四类里，或某一类是事后套上去的（并非该轮真实病因）。

**P2**：三条机制的**依赖顺序**（C 提供来源事实 → A 仲裁 → B 计量）是否是**规范的一部分**而非实现细节？
- 验：设计稿是否明确规定了顺序，且**顺序改变时行为不变或明确报错**。
- **不成立** = 顺序只是叙述习惯，实现可以任意排列而结论不同 ⇒ 那就是 r2 「谁先跑谁定案」的复发。

**P3**：§6.3「为什么不会在下一个位置再破一次」的五条论证，是否每条都能对应到一个**结构性保证**而非承诺？
- 验：逐条问「如果有人新加一种诊断/几何形态，这条论证还成立吗」。
- **不成立** = 任一条实质上是「以后写代码的人记得这么做」。

## 2. 缺口 A · 证书式仲裁（P4–P8）

**P4**：`CERTIFIED_CONFLICT` 的定义（「在该 capability 不确定域的所有可接受解释下仍成立」）是否**可机械判定**？
- 验：不确定域怎么表示、「所有可接受解释」怎么枚举或如何用闭式判定。
- **不成立** = 需要枚举无穷多解释，或判定依赖某个未定义的「可接受」。

**P5**（**承重**）：新机制能否区分「advisory 扰动**派生**出来的 duplicate」与「**独立真实**的 duplicate」？
- 验：用 r3 裁决书 §2 R3-B1 的活体（footprint `0.1×0.1`；cell A、B 都等于完整 footprint；cell C 左半幅梯形右边从 `x=.05` 斜到 `x=.05+5e-10`；上游 overlap `0.015 m² < coverage_area_tol_m2=0.05` 故生产五项全绿）。设计稿的机制**应当**判 CERTIFIED_CONFLICT（红），因为 A、B 的重复占用与那条 advisory 边**无关**。
- **不成立** = 按设计稿的规则推演，该活体仍得 NA；或规则推不出确定结论。

**P6**（**承重**）：新机制会不会把**既有合法**的 advisory 形态重新误判为红？
- 验：既有锁 `test_r4_live_counterexample_is_unsupported_not_identity_invalid` 的形态（两 cell、生产五项全绿、mismatch advisory：一侧 `dx=5e-10`、另一侧 `dx=4e-10`）在新机制下应当仍是 **NA**。
- **不成立** = 该形态在新机制下变红 ⇒ 假红复发（这正是「简单把 reason 加白名单」会犯的错，设计稿必须避开）。

**P7**：`reason` 是否**真的**被降级为纯展示、永不参与严重性判定？
- 验：通读设计稿，找有没有任何判定路径仍读 reason 的值。
- **不成立** = 存在任一处用 reason 做分支。

**P8**：仲裁是否**覆盖整次请求的所有楼层**，而非某个 helper 的局部 bucket？
- 验：多楼层且不同楼层分别有 CERTIFIED_CONFLICT / CAPABILITY 时的结论。
- **不成立** = 存在某个楼层的红被另一楼层的 NA 掩盖，或反之。

## 3. 缺口 B · 区间原子账本（P9–P14）

**P9**（**承重**）：对 r3 的 **1-ulp 假红活体**，新机制给出什么结果？
- 活体：GT 上方一长 zone、下方三相邻 zone（T 型接头切出三段目标墙，`x0=0.6615103026426206 / x1=10.189556344280527 / x2=16.84636437455466 / x3=21.523013020575195`，两两 `previous.p2 == next.p1`），correction 上下各一长 cell 得一条完整产品墙；correction 生产五项全绿。
- **必须**：不拒绝（合法铺满），且计分正确。
- **不成立** = 按设计稿规则仍拒绝，或结论依赖某个未定义的容差。

**P10**（**承重**）：对**真实过计**（一条产品墙覆盖两道平行答案墙，`covered=8 > length=4`；以及 sol r2 实测的 `covered=4.0000000005`）新机制是否仍响亮拒绝？
- **不成立** = 任一真实过计被放过 ⇒ 假绿复发（r0 原病）。

**P11**：「observation 原子若同时被两个不同 target 收费即结构性重复记功」——这条判据是否**不依赖任何数值容差**？
- 验：判据是否纯粹是 owner 集合的重数问题。
- **不成立** = 仍需要一个阈值来决定「同时」或「不同」。

**P12**：`extra` 改由「observation 域中未覆盖原子的并集长度」得出，是否**结构上不可能为负**？
- **不成立** = 存在使其为负的路径，或负值仍需靠比较吞掉。

**P13**：**exact-rational** 账本的正确性与代价：
- 验：binary64 转 exact rational 是否**无损**（binary64 本身就是二进制有理数，验证设计稿是否正确利用了这点）；分母增长是否有界；对 sm24 规模（约 50 顶点 / 16 段内墙）与更大 case 的性能估计是否可信。
- **不成立** = 转换有损、分母可能爆炸且无缓解、或代价估计明显失实。

**P14**：相邻 target「只共享切点、不构成重叠」这条，是否在**闭区间**表示下自洽？
- 验：闭区间端点重合是否被判为重叠。
- **不成立** = 相邻即判重叠（那 P9 必然失败）。

## 4. 缺口 C · 来源身份（P15–P19）

**P15**（**承重**）：来源 key 是否**真的在现有输入里就有**，不需要改 GT schema / wire / 已签字的答案？
- 验：逐个核 GT / correction / reading 三类适配器的来源 key（如 `(floor_id, zone_id, vertex_index)`）是否都能从**现有数据结构**取到。
- **不成立** = 任一类需要上游新增字段 ⇒ 违反「gt 一字节不许动」与「不改输入格式」。

**P16**：「距离只生成**可能归并**的候选，真正焊成同一原子需要 alias 证书」——这是否真正打破了「用距离反推意图」的循环假设？
- 验：alias 证书的来源是什么，是否独立于距离本身。
- **不成立** = 证书最终仍由距离推出 ⇒ 循环仍在。

**P17**：合同版本（§3.3 称「内存协议，不改输入格式」）是否有**真实的运行时发射路径**？
- 验：什么情况下会抛 `score_identity_contract_mismatch`。**注意现码里这个错误码全仓只在码表出现一次、零 raise。**
- **不成立** = 新设计里它仍然没有可达的 raise 路径。

**P18**：合同④ 的完整拓扑合同是否覆盖了现码遗漏的全部形态？
- 验：**非相邻**重复顶点 / 归并后自触自交 / 同一 owner 与自己反向配对。活体：环 `(0,0),(4,0),(4,4),(0,4),(0,2),(2,2),(0,2)`，现码产出 `zone_ids=("Z","Z")` 的「内墙」，新设计应当拒绝。
- **不成立** = 任一形态仍被静默接受。

**P19**：审计上下文是否记录了足以**事后复现判定**的信息？
- 验：原始 binary64（hex）、归并直径、来源 key、owner 关系、合同版本。
- **不成立** = 任一关键字段缺失（r3 已发现 boundary duplicate-after-merge 连原始两对端点都没记）。

## 6. 施工可行性（P27–P30）

**P27**：施工拆分（Slice 0–4）的**依赖顺序**是否正确，是否存在「半交付即危险」的项被排在可半交付的位置？

- **不成立** = 存在某个 Slice 交付一半就会让系统进入比现在更差的状态，而设计稿未标为不可半交付。

**P28**：Slice 0「先落会红的锁」是否真的会红？
- 验：A-L3 / B-L4 / C-L1 / C-L7 / C-L11 在**当前代码**上是否确实变红（可在 `/tmp` 实际构造验证，至少推演到能确信）。
- **不成立** = 任一条在当前代码上其实是绿的 ⇒ 那它就不是这批要修的问题的锁。

**P29**：总成本估计（§7.1）是否可信？影响面（§8 对既有测试与地基的影响）是否覆盖了真实的改动面？
- 验：对照现码估算实际要动的文件与测试数量。
- **不成立** = 明显低估（如漏掉某个大面积改动）。

**P30**：三条机制**组合**后的总状态机（§6.1）是否自洽、无死角？
- 验：三条各自的 NA / 红 / 通过状态两两组合，是否都有确定出口。
- **不成立** = 存在某个组合状态没有定义，或两条规则冲突。
