## 二 ⭐⭐⭐ 把 B2 刚证过的五类攻击原样打到本单的冻结机制上

09-05 B2 返工 3 复核**正面证明**过：入口收窄**不属于**有效解那一族。实测五类攻击里有**三类把入口封印整个绕过去**：

1. `deepcopy` 走 `cls.__new__`，不经过任何 `__init__` / 工厂；
2. 私有 minter（`_mint`、`__new_token` 之类）**可以被外部直接调用且铸造成功**；
3. `__class__` 重赋值，不触发任何钩子。

本单的承重机制是 `TickBatch(batch_id, record: bytes)` + `TickSession.consume(expected_batch_id, batch=None)`，
交件称它「精确核当前身份、字节、packet 及 source……普通重新 finalize、换 ref/tier/元素、
拿另一有效批次替换，均不能通过这个入口」。

⭐⭐⭐ **注意它自己写的限定词：「这个保证只覆盖给定当前持有者和独立预期 ID 的正常 API 消费」。**
⇒ **把上面三类攻击逐条实打**，外加两条你自己设计的。要回答的是：

- `batch_id` 是 canonical JSON bytes 的 `sha256` —— ⭐ **立门三问的第 ② 问：canonical 化本身能不能被换掉？**
  （字段顺序、浮点格式化、`ensure_ascii`、`separators`、嵌套容器类型……全在门自己的计算之外）
  构造两份**语义不同但 canonical 后同 bytes** 的 record，或**语义相同但 canonical 后不同 bytes** 的 record。
- `consume` 是**入口检查**还是**出口全检**？⛔ 若是入口收窄，按 B2 已证的结论，它不属于有效解那一族。
- ⭐⭐⭐ **反查「哪个方向没有锁」并问为什么** —— 若答案是「加了就会红」，那是缺陷本身在挡锁。
