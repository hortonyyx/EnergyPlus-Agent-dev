## 0. 背景（你是冷启动，这节自包含）

### 0.1 项目

建筑图纸 → EnergyPlus 模型的多模态管线。第 0 段 `0_reading`（识图）由 VLM 读图纸产出结构化 JSON
（墙的笔画 strokes、窗、尺寸标注转录 ocr_texts 等），后续段是确定性几何代码 + LLM 物理语义。

**判卷（gate②）= 把识图产物与人工签字的标准答案 GT 逐元素对账**，产出
「内墙命中多少米 / 外轮廓 / 多画了多少米 / 窗的 existence·along·width·sill·head 各命中几项」。
另有 **gate①** = 确定性自检（代码，产出 `*_checks.json`），按 `run_profile` 分档决定 fail 是否阻断。

**这把尺子是我们判断识图质量的唯一定量手段。** 我们最近几周所有关于「识图是变好了还是变坏了」的结论，
全部建立在它之上。

### 0.2 为什么现在这件事压倒一切

2026-08-02 主控做了一次纵向回放：把 **07-07 的老识图产物**（Haiku 4.5 + CV 工具箱）
喂进**今天的判卷层**（同 GT / 同 view bindings / 同容差 / 同全卷五张图）：

| | 内墙命中 | 外轮廓 | 多画 |
|---|---|---|---|
| **07-07 老件** | **57.86 / 57.86 = 100 %**（20 行全 `complete`） | 60 / 60 | **0 m** |
| 08-02 今天的 Sonnet（无监督全卷） | 53.31 / 57.86 = 92.1 % | 60 / 60 | 6.77 m |

⇒ **「一条能做对的路径确实存在」由推断升级为已证实**，我们拿到了上限锚。
用户由此定下方法论：**目标是「维持这个上限往下降档」，不是「从 9 % 往上爬」。**

**但同一轮回放暴露出：尺子本身在说谎。** 于是有了本轮的排序原则（用户与主控共识）：

> **尺子没修好之前，任何新跑测的分数都不可用。先修测量，再谈能力。**

## 1. ⭐ 修复目标（这是本问题书的正文）

**总目标：让这把尺子量出来的数字可以被信任。** 拆成五条**可验收**的目标：

### G-1 · 分辨力 > 0

**尺子必须对「达标产物」和「不达标产物」给出不同结论。**

现状反例（可复核）：两份质量差很多的识图产物，其判卷 `claim_summaries` 哈希**逐字节完全相同**。
在窗这一侧，两份产物的 existence / along / width / sill / head **全部记 0**。
一把对好坏无差别的尺子，等于没有尺子。

### G-2 · 按规范如实填写的产物，不得被判零

读图器只能看到图纸，很多世界坐标层面的事实它**在信息上无从知道**，规范也**明令它不许声明**。
规范为此提供了「我不知道」这类合法取值。

**目标：产物在规范内的诚实回答，不能导致它被扣分或被丢弃。**
换句话说 —— 尺子不该惩罚诚实、奖励瞎猜。

### G-3 · 声明什么档位，就执行什么档位

每个 run 在 `run_config.yaml` 里声明能力档（`capability_profile`）与严格档（`run_profile`，
其中 `regression` = fail-closed，检查不过就拒收）。

**目标：声明的档位必须真的生效，且落盘的产物头部能证明它生效了。**

现状反例（可复核）：`case_tests/e2e_tests/sm24_anchor/run_2026-08-02_sonnet_full_unsup/` 的
`run_config.yaml` 声明 `capability_profile: orthogonal_polygon`、注释区写明 `run_profile = regression`；
而该 run 落盘的 `0_reading/attempts/001/checks.json` 头部是
`{"capability_profile": "rectangular", "run_profile": "exploratory"}`。

### G-4 · 该考的题必须真的考

判卷会把一部分检查项标成 `not_applicable`（N/A）而不计分。N/A 用对了是诚实（考生没见过的图不该考），
用错了就是**静默放水**。

**目标：N/A 只能因为「这一项在本 run 的输入上真的无从判定」，不能因为配置缺件、
标志位没接线、或某个上游字段恰好没填而产生。**

现状反例（可复核）：sm24 的五张图**都带完整尺寸标注链**（识图产物自己就抄下了 48–51 条尺寸），
但 view manifest 里五张图的 `dimensioned` 标志**全是 false**，
致使一大批尺寸相关检查记 N/A —— 那一轮 31 条 N/A 里尺寸类占大头。

### G-5 · 修完之后必须能做「修尺前 / 修尺后」对照

修完尺子，下一步（R2）主控要**离线重判**六份历史产物
（07-07 老件 · 08-02 全卷 · 08-01 sonnet 减卷 · W5 两抽 d1/d2 · 07-08 GPT-5.4-mini），
出一张同尺同 GT 的对照表，**据此重写此前所有关于识图质量的结论**。

**目标：修复方案必须让这件事做得成。**
⚠️ 特别注意：如果修复让严格档生效，历史产物可能大批被 gate① 拒收 ——
**请判断「gate① 拒收」会不会连带导致「判卷根本不出分」**。若会，方案里要给出出路
（否则对照表做不成，我们就失去了验证修复是否有效的唯一手段）。

## 2. 其余已知观察（事实陈述，未附主控的因果判断）

以下是同一轮排查中记录下来的现象。**主控不给因果解释**，请你自行判断它们是不是同一个病、
优先级如何、是否值得纳入本批。

- **O-1**：识图产物在走「硬隔离合并」这条路径落盘时，**标准流程不产出任何产物图**（`*_render.png`）。
  用户看不到识图画出来的东西长什么样，肉检门实际失效。
  盘上 `run_2026-08-02_sonnet_full_unsup/0_reading/` 与 `run_2026-08-01_haiku_w5_scoped_d1/0_reading/`
  **有** render png（经查是上一轮主控**手工**补的），而 `run_2026-07-27_haiku_e2e/`、
  `run_2026-07-31_haiku_retry_r2/` 两轮**一张没有**。

- **O-2**：判卷产出的 `grade.png` 现在是标签互相压住、读不出信息的柱状图；
  历史版本（如 `run_2026-07-02_sonnet_flow_e2e`）是两层平面 + 四立面的几何叠图带图例。

- **O-3**：`skills/intake_pipeline/0_reading/session_kickoff.md` 里，
  通则（`:51`）与同一文件的对照表（`:57`–`:65`）对产物文件名给出的规则**不一致**；
  图片名本身以 `_view` 结尾时两者算出的文件名不同。曾有识图轮因此被合并门拒收。

- **O-4**：识图产物里 `ocr_texts[].anchor` 曾被填成像素坐标 `[360, 450]`
  （该建筑实际只有约 10 × 20 m），gate① **0 阻断放行**，下游据此渲染出约 3.3 亿像素的 PNG、打不开。

- **O-5**：2026-08-01 引入过一个「本轮只考哪几张图」的机制（可在 `run_config.yaml` 里声明
  `reading_exam_scope` 收窄考试范围）。实测**收窄考试范围会让识图质量本身下降**
  （同模型同文档同零监督：全卷内墙 92.1 %、多画 6.77 m；收窄到两张后 70.9 %、多画 46 m），
  机制解释是五张图本来互为佐证。该机制配套的冻结/守卫/哈希锁本身是好的。

- **O-6**：那一轮 gate① 实际**抓到了 5 条 fail**（`dimension_chain_closure` ×4 +
  `stroke_dimension_consistency` ×1），但落盘的阻断结论是 **0 条**。
  这 5 条指向的正是「产物是看着画的、没有真去量尺寸」这一质量病灶。

## 4. 治理约束（施工阶段会写进派工单，先让你知道，也请据此设计验收）

- **「探针 ≠ 锁」**：临时跑一次验证通过的探针**不具备回归效力**。
  本项目要求**每条新守卫都要有「摘掉即红」的锁** —— 把守卫代码去掉，恰好有一条测试变红，且零连带。
- **「非 None ≠ 成功」**：曾有一条锁断言 `score_vs_gt is not None`，而判卷器**拒绝**时产出的侧车也不是
  None ⇒ 锁绿着、判卷其实是拒的，三道审全漏。断言写在返回值存在性上 = 等于没断言。
- **「门是真的、锁是缺的」**：多批出现过守卫逻辑正确但没有任何测试绑住它。
- **「边界写窄就会被实现得同样窄」**：主控把裁定写窄过三次，都被精确实现成同样窄。
  ⇒ **如果你认为本问题书的目标定窄了、或漏了更重要的东西，请直接说，并给你认为对的边界。**
- 全仓当前 **2051 绿 + 10 strict xfail · 零红**。
- 实质改动走执行档 + 升一档跨家族交叉审 + 主控轻门；谁写谁不批。

## 5. 交付形态

写到 `AI_agent/logs/reviews/verdict/2026-08-02_reading_ruler_r1_discussion_sol.md`：

1. **诊断**：你认为 G-1 … G-5 各自的病根在哪，引到**具体文件行**或**实跑证据**。
   若某个目标你认为现状其实已经满足、或者主控把现象描述错了，**直接说**。
2. **修复方案**：每条给「改什么 / 为什么这样改 / 有没有你考虑过但否决的替代方案及否决理由」。
3. **风险与副作用**：尤其是会不会影响历史产物的可重判性（G-5）、会不会动到已签字 GT 的信任链、
   会不会让某类真实缺陷从此检不出来（**放水比冤枉危险**，这是本项目的既定口径）。
4. **验收锁**：每条修复对应的「摘掉即红」的锁**具体断言什么**。
5. **优先级与批次建议**：哪些必须在任何新跑测之前完成，哪些可以往后放。
6. **无法判定的**：明说无法判定 + 「要判定需要跑什么」。
   **不要用推测填充** —— 本项目吃过「未验证的假设被当事实继承」的大亏
   （一个 judge 的判语被当成事实，导致整个归因方向错了好几轮）。

鼓励在 `/tmp` 里跑只读探针来验证你的判断，但**不要动仓库工作树**。
