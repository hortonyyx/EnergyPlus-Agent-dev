# Deterministic Naming Refactor Review

Date: 2026-06-23
Verdict: REWORK

The direction is right: keep correction `Cell.id` as source identity, mint public names in code, and backfill interzone references after final names exist. I would not approve this proposal as written because it still leaks LLM order into byte artifacts, keeps an obsolete `Cell.id`-derived zone-name guard, and plans to leave active golden runs unre-recorded even though validation compares old artifacts against a new rebuild exactly.

## Findings

### BLOCKER 1 - Naming-only post-pass is not enough; output order still leaks LLM order

Evidence:
- Proposal only says to sort `ZoneVolume`s to assign serials, then write `zv.zone` back (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:59-62`).
- The build output keeps whatever order `build_zone_volumes()` returns: `out.zones = [zv.zone for zv in zvs]`, `out.zone_volumes = zvs` (`src/agent/geometry/build.py:35-37`).
- Surfaces are created by iterating `zvs` and insertion-ordered `by_floor` groups (`src/agent/geometry/split_pairing.py:46-54`, `:76-89`).
- The serializer preserves `bg.zone_volumes` order as `zone_order` and then emits surfaces in list order per zone (`src/agent/geometry/specs.py:152-161`).

If the correction LLM emits the same cells in a different order, assigning `Z01/Z02` inside a sorted side list does not make `bg.zones`, `building_geometry.json["surfaces"]`, or `geometry_specs.md` byte deterministic. You can end up with the same final names but a different JSON/spec ordering.

Recommendation:
- Make the canonical order part of the data flow, not only the name assignment. After computing absolute serials, return `zvs` sorted by `(floor_rank_by_z, -centroid_y, centroid_x, tie_breakers...)`.
- Iterate `pair_surfaces()` using canonical zone order and sorted floor keys, and after final surface names are assigned, either sort `surfaces` by final deterministic key or make `building_geometry_dict()` / `serialize_geometry()` sort by that key.
- Sort windows by `(parent_wall_name, along-wall position, z_min, source-id fallback)` before serialization. This changes artifact order only, not verts/OBC/topology/counts.

### BLOCKER 2 - Keeping the sanitized `Cell.id` zone-name collision guard re-couples public naming to LLM ids

Evidence:
- The proposal says to keep the existing id/zone-name uniqueness guard even after public names are generated by code (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:61-62`).
- The current guard rejects two raw ids that collide only after `_safe()`: `zn = _safe(c.id)` and `if zn in id_of_zone: raise ... EP-safe zone name ...` (`src/agent/geometry/modelling.py:302-308`).
- The stated goal is to decouple zone/surface/window names from LLM `Cell.id` (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:18`, `:41`).

After the refactor, `_safe(c.id)` should no longer be the public zone name. Rejecting `Room-1` and `Room_1` because their old public names would collide is an obsolete failure mode and makes the new deterministic naming layer still depend on LLM id spelling.

Recommendation:
- Keep the raw `Cell.id` uniqueness guard because `Window.room`, `zv_by_cell`, and `cell_by_id` need unique source identity.
- Remove the sanitized public-zone collision guard or replace it with a much narrower guard only for actual internal maps that still key by `_safe(c.id)`.
- Add a regression with two source ids that sanitize to the same string but have distinct raw ids and valid `Window.room` refs; it should build if geometry is otherwise valid.

### BLOCKER 3 - The active golden tests cannot stay on old artifacts

Evidence:
- The proposal says real sm20/sm21 golden artifacts are not re-recorded in this round (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:92`, `:100-101`).
- `validate_case()` rebuilds `building_geometry.json` and `geometry_specs.md` from snapped correction, then compares old disk artifacts to the rebuild exactly (`src/agent/execution/validation_run.py:139-180`).
- The positive sm20 and sm21 baseline tests call `validate_case()` and require all reports to pass (`tests/test_validation_run_baseline.py:35-44`, `:203-209`).
- The approval digest also hashes the on-disk `building_geometry.json` and `geometry_specs.md` bytes (`src/agent/execution/approval.py:8-11`; `src/agent/execution/validation_run.py:221-234`).

Renaming surfaces/zones/windows, adding `zone_meta`, and changing serialization order will make the deterministic rebuild differ from committed baseline artifacts. The count-only assertions are not the gate; the exact artifact reconciliation runs before those counts matter.

Recommendation:
- Either re-record every committed run fixture that `validate_case()` tests in this branch, or explicitly move those tests to old-name fixtures / downstream-only scope until the sm21 batch re-record happens.
- Do not claim "pytest full green" and "no real golden re-record this round" at the same time unless the active golden tests are removed from the exact-rebuild path.

### DISAGREE 1 - Object-reference pairing is the right shape, but the proposal needs stricter implementation constraints

Evidence:
- Current reciprocal references are set immediately from names for interzone walls and cross-floor floor/ceiling pairs (`src/agent/geometry/split_pairing.py:69-71`, `:107-110`).
- The validator requires every `OBC=Surface` target to exist and point back exactly (`src/validator/interzone.py:148-186`) and kernel self-consistency also checks `obc_obj` names (`src/validator/checks/kernel.py:194-213`).
- `Surface` is a mutable dataclass (`src/agent/geometry/modelling.py:33-40`), so using `Surface` objects as dict keys will not work by default.

The proposed "object reference -> final name -> backfill" pattern is safer than any geometry/name rematch. It only stays safe if the implementation mutates the original `Surface` objects in place and stores pair refs as `list[tuple[Surface, Surface]]` or explicit temporary ids. It can mis-pair if it recreates surfaces during naming, backfills by `(zone, stype, verts)` matching, or uses list positions after sorting.

Recommendation:
- Store `pair_refs.append((sa, sb))` at creation time, do all naming in place, then run `for a, b in pair_refs: a.obc_obj = b.name; b.obc_obj = a.name`.
- Do not backfill by final name, geometry equality, centroid, or list index.
- Add a focused test with multiple equal-area cross-floor pieces and multiple same-zone wall cuts to prove the reciprocal pairs survive surface list sorting.

### DISAGREE 2 - Wall ring order needs a fully specified canonical key

Evidence:
- The proposal uses "SW-most start + CCW + segment midpoint ring position" (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:49-53`).
- `_cell_polygon()` only normalizes orientation to CCW; it does not rotate to a canonical start vertex or remove collinear vertices (`src/agent/geometry/modelling.py:111-117`).
- Split/cut wall segments come from Shapely boundary operations and `_iter_segments()` only filters by minimum edge length (`src/agent/geometry/modelling.py:148-167`; `src/agent/geometry/split_pairing.py:75-86`).

"SW-most" is ambiguous for non-rectangular rings where the westernmost vertex and southernmost vertex differ, for repeated/collinear vertices, and for near-equal coordinates after snapping. Segment midpoint projection is good, but it needs a canonical exterior ring and deterministic tie-breakers.

Recommendation:
- Define SW start as a lexicographic coordinate, e.g. minimum `(y, x)` after rounding to the kernel coordinate tolerance. Rotate the exterior coordinate list to that vertex after ensuring CCW.
- Compute each wall segment's key as `(projected_midpoint_distance_mod_perimeter, rounded_endpoint_a, rounded_endpoint_b, length, obc_rank, paired_zone_handle_or_empty)`.
- For equal projected distances after rounding, fail loudly or use the endpoint/length tie-breakers; do not let Shapely iteration order decide `W{k}`.

### DISAGREE 3 - Absolute serial tie-breaks should be geometry-first, not `cell_id`-first

Evidence:
- The proposed primary order is floor index, N->S, W->E (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:49`).
- The proposal itself asks whether `cell_id` lexicographic fallback is enough (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:109`).
- The overall goal is to decouple public names from LLM `Cell.id` (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:18`).

Centroid ties are rare for rectangular tilings but real for symmetric non-rectangular zones, equal-centroid degenerate overlaps, or rounded coordinates. Falling straight to `cell_id` makes the serial handle change when only the LLM id spelling changes.

Recommendation:
- Use a quantized geometry fingerprint before `cell_id`: `(floor_rank_by_z, round(-cy), round(cx), bounds, area, canonical exterior-ring coords/hash)`.
- Use sanitized raw `cell_id` only as the final impossible-tie fallback, and consider raising if two same-floor zones have the same geometry fingerprint because that usually means overlap/duplicate geometry.

### DISAGREE 4 - `C` center tolerance at ~15% of half-extents is too wide

Evidence:
- Proposal suggests a center band of about 15% of footprint half-width/half-height (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:50`).
- Roles can already create non-unique human descriptors, while the unique handle is the serial (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:35-38`).

A 15% half-extent band is a 30% wide central rectangle. In large or narrow footprints it will label too many ordinary rooms as `C`, reducing the usefulness of the suffix and making small centroid jitter flip a zone between `C` and compass labels near a wide threshold.

Recommendation:
- Make `C` a small near-origin case, not a broad core-zone classifier. Use normalized offsets and start with something like `abs(dx)/half_w <= 0.05` and `abs(dy)/half_h <= 0.05`, with a small absolute tolerance for snapping noise and an upper cap in meters.
- Add tests for a centered corridor, a just-off-center room, and a large-footprint core room so the band is intentional.

### DISAGREE 5 - `zone_meta` viewer integration is incomplete as described

Evidence:
- `build_viewer_html()` uses the explicit `roles` argument if it is not `None`, otherwise it reads `data.get("roles", {})`; it does not read `zone_meta` today (`scripts/tool_scripts/render_geometry_viewer.py:561-569`).
- The CLI default always calls `discover_roles(j)` and passes that explicit map to `build_viewer_html()` (`scripts/tool_scripts/render_geometry_viewer.py:593-600`).
- `run_stage` and `report_assembly` also pass `roles=discover_roles(bg)` explicitly (`scripts/tool_scripts/run_stage.py:337-340`; `scripts/tool_scripts/report_assembly.py:184-190`).
- `discover_roles()` is documented and implemented around `cell.id == building_geometry zone name` (`scripts/tool_scripts/render_geometry_viewer.py:535-557`).

If `zone_meta` is merely added to JSON and `build_viewer_html()` is changed to look at it only when `roles is None`, both live viewer generation paths will still pass the stale correction-id map and override the additive metadata.

Recommendation:
- Make `discover_roles(bg_path)` first read `zone_meta` from the `building_geometry.json` itself and return `{meta["name"]: meta["role"]}` when present.
- Or stop passing `roles=` at the call sites and let `build_viewer_html()` derive roles from `zone_meta`.
- Update `tests/test_geometry_viewer.py:96-107` to cover deterministic public names where `cell_id != name`.

### DISAGREE 6 - Role token normalization is underspecified for existing multi-word roles

Evidence:
- The proposal says `Cell.role` becomes Title-case in the zone name (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:36`).
- Existing tests and fixtures already use roles such as `entrance lobby` and `meeting room` (`tests/test_geometry_kernel.py:156`, `:169-170`).
- The MEP naming rule allows only letters, digits, and `_` (`skills/intake_pipeline/4_mep/authoring.md:128-130`), and `_safe()` is the local sanitizer (`src/agent/geometry/modelling.py:95-97`).

Plain `.title()` would produce spaces in names (`Meeting Room`), and arbitrary role punctuation can produce invalid or awkward public names unless the role token is normalized before joining.

Recommendation:
- Define a role-token helper: strip, title-case word parts, `_safe()`, collapse repeated underscores, trim underscores, and fall back to `Office` or `Unknown` when empty.
- Add tests for `meeting room`, `entrance lobby`, punctuation, and non-ASCII/blank roles if those can appear.

### NIT 1 - Window naming length is fine, but the ordering key needs ties

Evidence:
- Current attachment iterates `geom.windows` in source order (`src/agent/geometry/modelling.py:365-376`).
- Proposal wants `{parent.name}_Win{k}` ordered along the wall (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:73-75`, `:113`).

`Z01_W1_Win1` is short and readable. The risk is not length; it is source-order leakage and ties. Multiple windows can share the same parent, same start coordinate, or even same span with different z ranges.

Recommendation:
- Attach all windows first, group by final parent wall, sort by projected along-wall start, projected end, `z_min`, `z_max`, and final `w.id` fallback, then assign `Win{k}`.
- Serialize windows sorted by `(parent, k)` so JSON/spec order is canonical.

### NIT 2 - Additive `zone_meta` is structurally safe for most consumers, but it must be declared as artifact version drift

Evidence:
- Main consumers read explicit keys: viewer copies `zones/surfaces/windows` (`scripts/tool_scripts/render_geometry_viewer.py:564-568`), record_baseline counts those keys (`scripts/tool_scripts/record_baseline.py:78-85`), and MEP tests read `bg["zones"]` (`tests/test_checks_mep_assembly.py:32-33`).
- Exact rebuild/digest paths compare or hash the full top-level dict (`src/agent/execution/validation_run.py:155-180`, `:221-234`).

Adding `zone_meta` should not break loose JSON consumers that ignore unknown keys, but it is not byte-neutral and changes the approved geometry checkpoint.

Recommendation:
- Put `zone_meta` in `building_geometry_dict()` immediately after `zones` and generate it from canonical `zone_volumes` order.
- Add one test that a JSON with extra top-level `zone_meta` still renders and that validation equality expects it after the serializer change.

### NIT 3 - Blast radius misses a few live docs/call sites outside the recon table

Evidence:
- `report_assembly` regenerates the viewer and passes `discover_roles(bg)` (`scripts/tool_scripts/report_assembly.py:184-190`).
- The viewer CLI help still describes the correction-file role default (`scripts/tool_scripts/render_geometry_viewer.py:583-600`).
- `src/mcp/api/core.py` auto-generates surfaces as `{zone_name}_Wall_{i+1}`, `{zone_name}_Floor`, `{zone_name}_Ceiling` (`src/mcp/api/core.py:198-225`, `:243-250`).
- `zone_tools` still documents `F1_Office_North` as the example zone name (`src/agent/tools/zone_tools.py:20-24`).

These are not all blockers for the kernel path, but they are public/tooling naming contracts that will become stale.

Recommendation:
- Add these to the blast-radius checklist. For MCP/core helpers, decide explicitly whether they remain a separate generic API naming convention or should align with the new deterministic kernel convention.

### NIT 4 - Prefer carrying the short handle explicitly

Evidence:
- The proposal wants full zone names in `Surface.zone` but short handles in surface/window names (`AI_agent/logs/review/request/2026-06-23_deterministic_naming_proposal.md:35-38`).
- `ZoneVolume` currently has no separate handle field (`src/agent/geometry/modelling.py:50-64`).

Parsing `Z01` back out of `zv.zone` will work until a future rename format changes. It is a small coupling but easy to avoid.

Recommendation:
- Add a `handle: str = ""` field to `ZoneVolume`, or maintain a local `zone_name -> handle` map from the deterministic naming pass. Use that for surface/window names instead of splitting strings.

## Direct Answers To The Review Asks

1. Reciprocal OBC resolution survives the rename if and only if the implementation stores actual pair refs from creation and mutates existing `Surface` objects in place before backfilling names. It can mis-pair if it rematches by geometry/name/list index after sorting. Object-ref tuples are the safest shape; a one-pass final-name scheme fights the wall-ring requirement and is not safer.
2. SW-most + CCW + midpoint projection is not fully specified yet. It needs rounded lexicographic start selection, canonical ring rotation, and tie-breakers for collinear/cut/sliver cases.
3. Floor/N->S/W->E is not sufficient. Use floor rank by `z_floor`, quantized centroid, bounds, area, canonical ring fingerprint, and only then source id as last resort.
4. A 15% half-extent `C` band is too broad. Start smaller, cap it, and test centered corridor vs near-center room behavior.
5. `zone_meta` is safe for loose consumers but not byte-neutral. It will invalidate exact artifact comparisons/digests until committed baselines are updated.
6. Missed blast radius: `report_assembly` viewer regeneration, viewer CLI help/default role lookup, MCP core auto-surface naming, and tool docstring examples.
7. `Z01_W1_Win{k}` is a good length/readability tradeoff. The important fix is deterministic grouping/sorting, not another absolute window serial.
