# Review: run report organization proposal

Verdict: REWORK

The additive `report/` view is the right direction for preserving the hard validation contract. `validate_case()` still reads the load-bearing artifacts in-place and rebuild-compares `2_modelling/building_geometry.json` plus `3_split_pairing/geometry_specs.md`, so a copied/curated report folder does not by itself threaten byte equality as long as it does not move or rewrite the stage outputs (`src/agent/execution/validation_run.py:85-110`, `:139-180`, `:217-234`). The proposal's weak points are elsewhere: it overclaims enforceable evidence discipline, underspecifies stopped/partial runs, misses current visual artifact names, and underestimates the rename/compatibility and overwrite blast radius.

1. **BLOCKER** - The proposed evidence-id discipline is not enforceable against today's `baseline.json`.

   Evidence: the proposal says `REPORT.md` recommendations must cite fact-layer evidence and that tests can validate citation ids against `baseline.json` (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:21`, `:93`, `:98`). But `record_baseline` only writes judge summaries as `{stage, attempt, blocking, root_stage}` (`scripts/tool_scripts/record_baseline.py:92-94`, `:270`), and the sample `baseline.json` has no verdict id, criterion id, or criterion evidence to cite (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/baseline.json:63-75`). The actual `StageVerdict` schema has free-text `criterion` and `evidence` fields, not stable ids (`src/agent/judge/verdict.py:40-45`), while gate summaries only give `stage/check/message` for blocking and `stage/check/message/evidence` for flags (`src/agent/execution/orchestrate.py:81-87`).

   Recommendation: add a deterministic `evidence_index` to `baseline.json` or `report/FACTS.md` before making citation discipline a requirement. It should assign stable ids to gate flags/blockers, judge criteria, correction-audit conflicts/unsupported/capped corrections, orchestration stop reason, EP result, geometry digest, and copied eyeball artifacts. Then add a linter that parses structured citations in `REPORT.md` (for example `[E:gate:1_correction:correction.zone_count_tripwire]`) and fails if every actionable recommendation does not cite at least one existing id. Without this, the proposal only tests that a report has some headings, not that advice is grounded.

2. **BLOCKER** - Partial/stopped runs need first-class report semantics; copying today's `RUN_REPORT` into `FACTS.md` preserves misleading noise.

   Evidence: full-scope validation deliberately records missing downstream artifacts when a run stops early (`src/agent/execution/validation_run.py:85-110`). In a stopped sample, the report correctly says the root stop is `human_redraw_required@1_correction` (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_sonnet_reading/RUN_REPORT.md:3`), but then lists missing `2_modelling`, `3_split_pairing`, `4_mep`, and `5_intakeoutput` artifacts as blocking facts (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_sonnet_reading/RUN_REPORT.md:29-33`) and still asks the user to open a 3D viewer that cannot exist because `geometry_digest=None` (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_sonnet_reading/RUN_REPORT.md:38-44`). The underlying baseline confirms this is a stopped upstream run with no geometry (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_sonnet_reading/baseline.json:10-12`, `:125-140`).

   Recommendation: make report assembly state-aware. `FACTS.md` may still include raw full-scope gate facts, but `REPORT.md` should separate "root stop reason" from "consequential missing downstream artifacts", suppress unavailable inspection links, and produce an "available artifacts only" eyeball section. Add golden coverage for at least: `human_redraw_required`, `awaiting_reread`, `awaiting_geometry_approval`, and a clean completed run.

3. **DISAGREE** - The `report/eyeball/` collection spec does not match current produced artifact names or locations.

   Evidence: the proposal says to copy `*_zones.png`, `*_elev.png`, and `*_source.png` into `report/eyeball/` (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:46-49`, `:91`, `:106`). The current step runner writes `1_correction/zones.png` and `1_correction/elev.png`, not per-floor/per-facade `*_zones.png` / `*_elev.png` (`scripts/tool_scripts/run_stage.py:302-309`). Source images live in the parent case's `case_data/`, as `_source_images()` shows (`scripts/tool_scripts/run_stage.py:346-354`), not as `*_source.png` files under the run. The existing checklist still names the old glob patterns (`scripts/tool_scripts/record_baseline.py:223-228`), so implementing the proposal literally can create an empty or incomplete curated folder.

   Recommendation: implement an explicit collector from actual producers, not wishful globs. For v1, copy `1_correction/zones.png`, `1_correction/elev.png`, `0_reading/*_render.png`, and parent `case_data/*_view.png` with collision-safe names; include missing/unavailable entries in `FACTS.md`. Better, read `attempts/NNN/judge_packet.json` `source_images` / `renders` where present and copy those paths deterministically. Test against `case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/`.

4. **DISAGREE** - "Directly abandon `RUN_REPORT.md`" has wider blast radius than the proposal admits.

   Evidence: the proposal leans toward dropping the old top-level `RUN_REPORT.md` and says the change is mostly `record_baseline.py`, guide, golden tests, and `.gitignore` (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:105`, `:115`). Current tests hard-code `RUN_REPORT.md` in multiple assertions (`tests/test_orchestrate_baseline.py:159-163`, `:166-171`, `:188-190`, `:238-243`, `:260-261`). Baseline docs and registries also describe `RUN_REPORT.md` as the human report (`case_tests/test_baseline/README.md:31-37`, `:57-62`; `case_tests/test_baseline/index.md:3-9`; `AI_agent/guides/new_case_guide.md:40-53`, `:183-193`).

   Recommendation: keep a compatibility shim for at least one transition. Either leave top-level `RUN_REPORT.md` as a short pointer to `report/REPORT.md` and `report/FACTS.md`, or keep writing a deterministic alias to `report/FACTS.md` while all tests/docs are migrated. Do not claim "small blast radius" until the grep-visible references are intentionally updated or covered by compatibility tests.

5. **DISAGREE** - The dynamic `REPORT.md` workflow can overwrite Agent-authored narrative unless preservation is designed.

   Evidence: the proposal assigns code to write `report/REPORT.md` skeleton and the main Agent to fill it after `record_baseline` (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:90-98`). Today's `record_baseline` unconditionally overwrites `baseline.json` and `RUN_REPORT.md` on every run (`scripts/tool_scripts/record_baseline.py:278-283`). If the new implementation follows that pattern for `report/REPORT.md`, rerunning the deterministic recorder will erase the curated Agent/judge narrative and recommendations.

   Recommendation: split generated and authored files. Options: write `report/REPORT.template.md` and only create `report/REPORT.md` if absent; preserve user-authored fenced regions by marker; or make `assemble_report.py --force-template` explicit and non-default. Add a regression test that writes custom narrative into `REPORT.md`, reruns deterministic assembly, and proves the narrative is not destroyed.

6. **DISAGREE** - A pointer-only 3D viewer policy must verify or regenerate the gitignored viewer.

   Evidence: the proposal settles that `geometry_viewer.html` stays in `manual_review/` and `REPORT.md` only points to it (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:106`). The viewer HTML is intentionally ignored because it is regenerable (`.gitignore:299-302`). The step runner generates it best-effort and returns an error string instead of failing the run (`scripts/tool_scripts/run_stage.py:318-343`, `:461-468`). Therefore a committed run or copied workspace may have a valid `building_geometry.json` but no existing viewer file.

   Recommendation: report assembly should check `manual_review/geometry_viewer.html`. If missing and geometry exists, regenerate it from `2_modelling/building_geometry.json`; if generation fails, record an explicit unavailable fact and do not emit a dead "open this viewer" instruction. This can still honor the decision not to copy the viewer into `report/`.

7. **NIT** - Force the four recommendation buckets as headings, not as invented content.

   Evidence: the proposal's four buckets match the user request (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:68-73`) and decision E proposes "each bucket at least one item or `本 run 无`" (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:108`). The risk is not the headings; the risk is a model filling a bucket with weak advice to satisfy a quota.

   Recommendation: require every bucket to be present, but allow exactly `本 run 无可证据支持的建议` when the evidence index has no support. The linter should treat unsupported prose in a bucket as a failure, not a success.

8. **NIT** - Fix adjacent stale guide commands/paths while touching `new_case_guide.md`.

   Evidence: the guide's example `record_baseline.py` command omits the required `run` positional argument (`AI_agent/guides/new_case_guide.md:183-187` vs `scripts/tool_scripts/record_baseline.py:387-397`). The guide also still says the 3D viewer is generated under `2_modelling/geometry_viewer.html` (`AI_agent/guides/new_case_guide.md:148-151`), while the runner writes `manual_review/geometry_viewer.html` (`scripts/tool_scripts/run_stage.py:331-340`).

   Recommendation: update these while adding the final report-authoring step, otherwise the guide will keep sending the main Agent to the old path and an invalid recorder command.

## 二审 (v2 focused)

Verdict: REWORK

Scope limited to v2 §8 B1/N7/B2 plus new contradictions. The v2 direction is right, but the new enforcement surfaces are not yet precise enough to implement safely: the evidence id namespace is not collision-proof for current artifacts, and state-aware reporting cannot use `stop_reason` as a clean-vs-stopped discriminator.

1. **BLOCKER** - `evidence_index` still lacks a deterministic, collision-free id recipe for several listed sources.

   Evidence: v2 promises stable ids for gate facts, judge criteria, correction-audit rows, stop reason, EP, geometry digest, and eyeball artifacts, with an example shaped like `E:gate:1_correction:correction.zone_count_tripwire` (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:125-128`). That shape is not safe for current gate data: `validate_case()` creates per-view keys such as `0_reading::<view>` (`src/agent/execution/validation_run.py:116-121`), but `summarize_gates()` collapses them to `0_reading` and keeps only `stage/check/message/evidence` (`src/agent/execution/orchestrate.py:76-87`). The same `check_id` appears in multiple reading view reports (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_sonnet_reading/0_reading/1f_view_checks.json:8-15`, `case_tests/e2e_tests/sm21_anchor/run_2026-06-20_sonnet_reading/0_reading/2f_view_checks.json:8-15`), so `E:gate:0_reading:<check_id>` would collide if that check flags/blocks in more than one view. Judge criteria are also only ordered free-text strings (`src/agent/judge/verdict.py:40-45`; `case_tests/e2e_tests/sm21_anchor/run_2026-06-20_sonnet_reading/1_correction/attempts/001/judge.json:4-29`), while `record_baseline` currently records only `{stage, attempt, blocking, root_stage}` summaries (`scripts/tool_scripts/record_baseline.py:72-95`). Correction audit rows are heterogeneous: some rows lack `id` (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/1_correction/corrections.json:121-128`), and the current summary caps displayed correction rows at 20 (`scripts/tool_scripts/record_baseline.py:165-173`; `tests/test_orchestrate_baseline.py:219-222`), but v2 does not say how no-id or capped-out rows are indexed.

   Recommendation: define the id namespace as source coordinates, not just `stage:check` or free-text slugs. For example: gate ids must preserve the full report key (`0_reading::1f_view`) plus result index/check id; judge ids must include verdict source path or stage+attempt plus criterion ordinal and optional slug/hash, with explicit "run-local stable" semantics unless rubric criterion ids are added; correction ids need a fallback row ordinal/hash when `id` is absent and a stated policy for rows beyond the display cap. Build the index from raw `res.reports`, raw `attempts/NNN/judge.json`, and raw `corrections.json`, then add a duplicate-id test.

2. **BLOCKER** - State-aware reporting is feasible from disk, but v2's state model misses non-clean states where `stop_reason` is `null`.

   Evidence: v2 says REPORT should separate root stop from consequential downstream missing artifacts and proposes golden coverage for `human_redraw_required`, `awaiting_reread`, `awaiting_geometry_approval`, and clean completed (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:130-133`). The state machine has more report-relevant statuses: `awaiting_judge`, `judge_block`, `quarantined`, `deterministic_defect`, and `judge_block_human` (`src/agent/execution/step_orchestrator.py:71-84`). The module explicitly calls `awaiting_judge` a stop point and `judge_block` a blind-resample point (`src/agent/execution/step_orchestrator.py:13-20`). But `update_state()` only writes top-level `stop_reason` for terminal stops plus `awaiting_geometry_approval` / `awaiting_reread`; all other outcomes clear it (`src/agent/execution/step_orchestrator.py:507-523`). `run_stage.py` persists both run and judge outcomes through `update_state()` (`scripts/tool_scripts/run_stage.py:447-458`, `:491-497`), and a `judge_block` outcome then asks for a resample while leaving `stop_reason` null (`scripts/tool_scripts/run_stage.py:498-502`). A report assembled at either point can be neither clean nor root-stopped, yet v2's four-case matrix does not force that distinction.

   Recommendation: define an explicit derived `run_state` from per-stage statuses, not from `stop_reason` alone. `completed_clean` should require all expected stages to be in advance-ok/completed states and no pending judge/resample/approval status; root-stop should cover terminal statuses; pending states should cover at least `awaiting_judge`, `judge_block`, `awaiting_reread`, and `awaiting_geometry_approval`. Add golden cases for `awaiting_judge` and `judge_block` at minimum, plus one terminal stop outside `human_redraw_required` such as `quarantined` or `judge_block_human`.

3. **DISAGREE** - The citation linter still depends on an undefined natural-language category.

   Evidence: v2 says the linter fails when any "可执行建议" lacks at least one existing `[E:...]` citation (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:127-128`) and that unsupported bucket prose fails (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:152-153`). It does not define a syntactic boundary between actionable recommendations, explanatory prose, section summaries, and the exact no-evidence sentinel. That leaves either a heuristic NLP linter, which is not deterministic, or a lax regex linter that can miss ungrounded advice.

   Recommendation: make the REPORT recommendation section a parseable mini-format. For each bucket, allow either the exact sentinel `本 run 无可证据支持的建议` or bullet records with required fields, e.g. `- action: ... evidence: [E:...] owner: ...`. Treat free prose inside the four buckets as context-only only if it is explicitly marked as such, or disallow it. The linter should be purely lexical/structural and should not infer "actionable" from prose.

4. **NIT** - v2 leaves a stale internal contradiction about the `RUN_REPORT.md` transition.

   Evidence: §7 now says the wider `RUN_REPORT.md` blast "已改为指针过渡" (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:117`), but §8 D4 says the ratified plan is an atomic migration with `record_baseline` no longer producing `RUN_REPORT.md`, "不留 shim" (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:139-142`).

   Recommendation: update the stale §7 parenthetical to match §8 D4's atomic migration wording, or reverse §8 D4 if the intended design is actually a pointer shim.

## 三审 (v3 recipes)

Verdict: REWORK

Focused scope only: v3 §9 recipes plus §7/§8 D4 consistency. Several parts are now grounded: `validate_case()` exposes raw per-view report keys before `summarize_gates()` collapses them (`src/agent/execution/validation_run.py:116-121`; `src/agent/execution/orchestrate.py:76-87`), duplicate gate `check_id`s are real and the proposed `#<n>` ordinal covers them (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/1_correction/correction_checks.json:8-21`), per-attempt judge verdicts are written and parseable from `attempts/NNN/judge.json` (`src/agent/execution/step_orchestrator.py:348-355`; `case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/0_reading/attempts/002/judge.json:1-45`), and `STAGE_ORDER` gives the expected 0-5 stage list (`src/agent/execution/stage_runner.py:57-75`). The V3 citation mini-format is deterministic as a line-oriented grammar, and §7 now matches §8 D4's atomic no-shim migration (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:117`, `:139-142`).

1. **BLOCKER** - V1's correction-audit id recipe can mint ids that the V3 linter cannot cite.

   Evidence: V1 says correction audit ids "prefer row `id`" and only fall back to `E:corr:<kind>:r<ordinal>` when absent (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:173`). Real correction rows do have raw ids such as `corr_1F_S_spans`, and conflicts have ids such as `conflict_cross_floor_corridor` (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/1_correction/corrections.json:3-5`, `:441-444`). Those raw ids do not match the V3 evidence token shape `[E:...]` (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:190-196`), so a report action grounded only in such a correction/conflict row cannot cite its evidence under the proposed linter. Rows without `id` are mintable by ordinal (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/1_correction/corrections.json:121-128`), but mixed raw/non-`E:` identities break the single evidence namespace.

   Recommendation: keep the source row id as payload, not as the evidence id. Always mint correction ids inside the evidence namespace, e.g. `E:corr:<kind>:<sanitized-row-id>` when `id` exists and `E:corr:<kind>:r<ordinal>` otherwise. Keep the duplicate-id assertion, but do not rely on model-authored row ids as global evidence ids.

2. **BLOCKER** - V2's `completed_clean` rule is not correct as written for the real geometry-gated clean run.

   Evidence: V2 defines `completed_clean` as all expected stages present, last stage in `ADVANCE_OK`, and no `PENDING/TERMINAL` (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:183-186`). The checked-in clean GPT-5.4 run has all 0-5 stages and a final `5_intakeoutput` `deterministic_pass`, with `stop_reason: null`, but its earlier `3_split_pairing` status remains `awaiting_geometry_approval` after geometry approval and later stage advancement (`case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/orchestration_state.json:39-42`, `:63-76`). That shape is produced by the real ledger: `update_state()` persists each stage summary as-is, while `mark_geometry_approved()` only sets `geometry_approved` and clears `stop_reason`; it does not rewrite `3_split_pairing.status` (`src/agent/execution/step_orchestrator.py:516-523`, `:530-542`). A literal "no PENDING anywhere" implementation would therefore fail to classify a known clean completed run as clean.

   Recommendation: make the precedence and supersession rule explicit. Use `STAGE_ORDER` for `expected` and `latest` rather than JSON object order; define `pending` from the latest effective stage only; define `completed_clean` as all expected stages present, the latest expected stage in `ADVANCE_OK`, and no current terminal stop. Either rewrite the geometry checkpoint stage to an advance-ok status when approval is recorded, or explicitly ignore a superseded `awaiting_geometry_approval` once a later stage has advanced.

## 四审 (v4 W1/W2)

Verdict: REWORK (1 BLOCKER / 0 DISAGREE / 0 NIT)

Scope limited to §10 W1/W2. W1 closes the third-pass correction-id blocker: the real correction rows with raw ids and conflict ids now mint citeable `E:corr:<kind>:<slug>` ids, no-id rows have ordinal fallback, `kind` is defined by the three `corrections.json` top-level buckets, and the retained duplicate-id assertion would catch a sanitization collision inside the final evidence id. W2 correctly classifies the checked-in clean geometry-gated run: `STAGE_ORDER` gives the expected 0-5 order, the run has all expected stages, `5_intakeoutput` is `deterministic_pass`, `stop_reason` is null, and the stale `3_split_pairing` geometry wait is superseded by a digest-matched approval (`src/agent/execution/stage_runner.py:57-75`; `case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/orchestration_state.json:39-42`, `:63-78`; `src/agent/execution/validation_run.py:231-234`; `src/agent/execution/approval.py:79-83`; `case_tests/e2e_tests/sm21_anchor/run_2026-06-20_gpt54_reading/geometry_approval.json:1-6`). 1. **BLOCKER** - W2 overgeneralizes geometry supersession into a latest-stage-only clean predicate.

   Evidence: §10 says `pending` checks only the latest effective stage and `completed_clean` requires only all expected stages present, latest expected stage in `ADVANCE_OK`, and no current terminal stop (`AI_agent/logs/review/request/2026-06-22_run_report_organization_proposal.md:215-219`). That is safe for the real `3_split_pairing` geometry wait only because `res.geometry_approved` is a separate digest-bound supersession signal. There is no equivalent supersession signal for `awaiting_judge`, `judge_block`, or `awaiting_reread` (`src/agent/execution/step_orchestrator.py:71-80`). `update_state()` also updates only the current stage entry and clears `stop_reason` on later forward moves; it does not rewrite earlier stage summaries (`src/agent/execution/step_orchestrator.py:516-523`). Therefore a ledger with `5_intakeoutput: deterministic_pass` plus an earlier non-geometry pending status would satisfy W2's `completed_clean` predicate even though the earlier pending stage was never resolved.

   Recommendation: keep the geometry-specific supersede, but make `completed_clean` require no non-superseded `PENDING` or `TERMINAL_STOP` anywhere in the expected stages. The only pending status allowed to be ignored should be `3_split_pairing: awaiting_geometry_approval` when current `res.geometry_approved` is true, preferably with a later expected stage already in `ADVANCE_OK`. Then derive `pending` as the latest non-superseded pending stage by `STAGE_ORDER`, with terminal precedence unchanged.
