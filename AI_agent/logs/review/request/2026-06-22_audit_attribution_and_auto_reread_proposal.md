## 0. Context — the same-origin triad

The founding framework's discipline = **make errors visible → make changes attributable → make unrecoverable errors recoverable by re-read**. The 2026-06-22 commit landed *visibility* (reading provenance/confidence + J0 recoverability routing). This proposal lands the other two, which are the same-origin debt:

- **Debt ①  audit → evaluation attribution** (contracts §5.4): correction's `corrections[]/conflicts[]/unsupported[]` audit is PRODUCED and completeness-CHECKED, but never SURFACED to the baseline/eval, so "看错 (reading error correction faithfully passed) vs 改错 (correction-introduced wrong change)" cannot be attributed. Code-only, landable now.
- **Debt ②  auto re-read**: J0 routing can `halt → re-read` an unrecoverable reading, but 0_reading is `MANUAL` and the orchestrator dead-ends at terminal `HUMAN_REDRAW_REQUIRED`. **Correction to an earlier mis-scoping: this is NOT blocked on an external VLM API.** In the dev model executors are isolated cold-start sub-agents (decision_log 2026-06-16); the **0_reading runner = a sub-agent the main Agent spawns** to re-read the case images. So auto re-read is landable now: spawn a fresh blind re-read sub-agent, file it as the next attempt, re-gate①+judge, ≤3 attempts → terminate — fully consistent with the 0–5 per-stage loop.

## 2. Debt ② — auto re-read via sub-agent runner

### Current state (code-grounded)
- The re-read MECHANISM already exists: `run_one_stage` (step_orchestrator.py) has a disk-derived per-stage budget (`per_stage_draws`, default 3), blind-resample discipline (injects `None`, never judge commentary), `QUARANTINED` termination, and the J0/J1 routing incl. the recoverability axis (2026-06-22).
- The ONLY gap: `0_reading` capability = `MANUAL` (`stage_runner.py:60`); on a gate①-block or a routable J0 block targeting a manual stage, `run_one_stage`/`_verdict_outcome` return **terminal** `HUMAN_REDRAW_REQUIRED` (step_orchestrator.py:248-252, :347-349) — it cannot loop, because there is no programmatic reading runner.
- **Resolution**: the runner is a **cold-start isolated sub-agent** the main Agent spawns (the dev executor model). So 0_reading becomes runner-drivable.

### Plan
**(a) Orchestrator code — make 0_reading re-read loop-aware (backward-compatible).**
- Add a non-terminal `StepStatus.AWAITING_REREAD` (NOT in `TERMINAL_STOP`): "manual stage blocked, blind re-read available, budget remains".
- Gate the new behavior on a **reading-runner-available** signal (a `RunPolicy` flag, e.g. `reading_runner_available`, default False). When True: a manual-stage gate①-block or routable J0 block returns `AWAITING_REREAD` while `_existing_attempts < per_stage_draws`, else `QUARANTINED`/`HUMAN_REDRAW_REQUIRED`. When False: current behavior (terminal `HUMAN_REDRAW_REQUIRED`) — **existing tests unchanged**.
- Budget + 3-strikes termination reuse the existing disk-derived counter. Re-read stays BLIND (no judge commentary injected — mirrors invariant 6 / `retry.py`).

**(b) Main-Agent protocol — the runner (new_case_guide.md + J0 rubric disposition).**
- On `AWAITING_REREAD`, the orchestrator (main Agent) spawns a **fresh isolated cold-start sub-agent** (Agent tool) to re-read the case images → produce a new `0_reading` JSON → file it as the next `attempts/NNN` → re-run gate①+J0. Repeat ≤ `per_stage_draws` → terminate. The sub-agent is BLIND: it gets the images + the 0_reading skill, **not** the prior attempt's strokes nor any judge commentary (no pollution / no teach-to-test).
- Same shape for 1_correction (already STOCHASTIC; the sub-agent IS the resample). So "every step: judge + pass/block, 3-strikes" is uniform across 0–5; the only per-stage difference is the decision logic (J0 recoverability routing for reading; J1 confirm-gate for correction) — already built.

**(c) Blind-convergence lever (discipline-safe).** A blind re-read by the same model class can repeat the error (Sonnet variance). Convergence comes from (i) sampling variance (the diagnosis showed run-to-run variance on the same images), and (ii) **escalating the runner model/effort per re-read attempt** (e.g. attempt 2→stronger model or higher reasoning) — this is runner CONFIG, not judge-commentary injection, so it does not pollute training data or teach-to-test. The deterministic gate① flags and judge commentary are NOT injected into the re-read.

### Blast radius
`step_orchestrator.py` (new status + gated manual-block handling) + `stage_runner.py`/`policy.py` (the runner-available flag) + `tests/test_step_orchestrator.py` + protocol prose in `guides/new_case_guide.md` and `skills/intake_pipeline/0_reading/judge_rubric.md`. Backward-compatible: default flag False ⇒ current `HUMAN_REDRAW_REQUIRED` behavior preserved.

## 3. Non-goals
- gt-diff mechanical 看错↔改错 join (N4); only surface the audit now.
- Wiring an external/API VLM runner (Pivot-era); the runner here is a sub-agent.
- correction A1–A4 / deterministic core / IntakeOutput contract / golden geometry baselines — untouched.

## 4. Test plan
- `record_baseline`: a synthetic run with corrections/conflicts/unsupported → `baseline.json.corrections_summary` populated + `RUN_REPORT.md` has the attribution section; a run with empty audit → section absent/empty, no crash; missing `corrections.json` tolerated.
- orchestrator: `reading_runner_available=False` → manual block still `HUMAN_REDRAW_REQUIRED` (current tests green); `=True` + budget remaining → `AWAITING_REREAD` (non-terminal); `=True` + budget spent → `QUARANTINED`; J0 routable manual block honors the same gating.
- Full suite stays green; no golden geometry byte-diff.

## 5. Open questions for Codex
1. `AWAITING_REREAD` as a new non-terminal status vs reusing `HUMAN_REDRAW_REQUIRED` with a flag — is the new status the right model, and does any consumer of `TERMINAL_STOP`/`StepStatus` need updating?
2. Where should `reading_runner_available` live — `RunPolicy`, or inferred from a `reading_runner` callable being injected into `run_one_stage`? (A real `draw_fn` for 0_reading can't be a pure CLI callable since spawning a sub-agent is a main-Agent capability — confirm the flag/protocol split is the right boundary.)
3. Blind-convergence: is model/effort escalation per re-read attempt acceptable under the blind discipline, or does even that risk teach-to-test? Any better discipline-safe convergence lever?
4. `corrections_summary` shape in `baseline.json` — full entries vs capped summary; should conflicts/unsupported be surfaced as `flags` in the existing flags list too (so they show in the gate table) or only in the new section?
5. Bundle both debts in one PR (proposed) or split?
