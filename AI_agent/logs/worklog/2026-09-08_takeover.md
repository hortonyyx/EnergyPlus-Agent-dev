### 本地完整恢复包

路径：`backup/2026-09-08_takeover/`（位于当前挂载的 Windows C 盘项目目录内）。

- `repository.bundle`：接手前完整 Git 对象/引用包，含原分支和归档标签；已 `git bundle verify`。
- `restart.bundle`：清理提交与 ready 标签建立后的完整 Git 包，用于离线恢复新起点。

- `worktrees/<编号-目录>/tracked.patch`：相对 HEAD 的完整 tracked 差异（含二进制）。
- `staged.patch` 和 `index`：额外保留暂存区状态。
- `extras.tar.gz` / `extras.json`：所有未跟踪及 ignored 文件（含本地配置）；原 `.env` 没有上传。
- `excluded-caches.json`：明确排除虚拟环境、Python/测试缓存和 node_modules 等可重建文件。
- `claude-memory/`：容器项目和原 Windows 项目两份完整记忆。

这是本地私有恢复包，不进入 Git；代码和可共享文档另通过 `main` 与标签推送远端。

### 恢复操作

先恢复到独立目录查看，避免直接覆盖正在开发的主目录：

```bash
git clone backup/2026-09-08_takeover/repository.bundle /tmp/energyplus-recovery
git -C /tmp/energyplus-recovery switch --detach checkpoint/2026-09-08-pre-takeover
```

上面恢复的是接手瞬间。需要清理后的版本，改用 `restart.bundle` 克隆并切到 `checkpoint/2026-09-08-ready`，或直接从当前仓库/远端取该标签。
初始 `repository.bundle` 创建在清理前，不包含后来才建立的 ready 标签。

恢复某棵旧树的未提交内容时，先切到 inventory 记载的 HEAD，再将对应 `tracked.patch` 用 `git apply` 应用，
然后解开对应 `extras.tar.gz` 到恢复目录。只在隔离恢复目录操作，私有配置不提交。
需要恢复当时的暂存划分，可在应用完整 tracked patch 后使用 `git apply --cached staged.patch`。
`index` 是原始兜底副本，不建议跨环境直接替换新仓库索引。

本轮已实际从 bundle 克隆 `/tmp/ep-takeover-restore-check`，核对接手标签和最新开发标签能解析到原提交。
另外从恢复副本实还原两棵典型脏树（一棵有源码/测试修改，一棵有 staged 文档及 untracked 文件），
还原后的 tracked/staged patch 与备份逐字相同。恢复验证用临时目录验证后清理，不保留新的开发树。
已推送改动若需在主干撤销，优先新建 `git revert` 提交，不强推改写共享历史。

## 为什么会推进困难

这些结论来自仓库、代码、历史记录与归档产物，不把单一根因当作全部问题：

1. **进度分散在不同树和不同文档。** 今天的 66 个后续提交在次级树，主目录仍是旧进度。入口还引用更早全量数据与“零接线”状态。
2. **治理要求相互叠加。** “默认探索、快速跑通”与核心代码必派工、跨家族必审、施工和主控分别全量同时存在。调度和验锁逐渐变成主线工作。
3. **全量并不能替代真实链路。** 旧 memory 明确记载某些模块测试只模拟邻居，集成仍有断点；同一状态又被按角色反复验证。新规按影响验证并复用证据。
4. **共享环境和并行写入增加了假故障。** 历史实测记录了 worktree 启动 `uv run` 改共享 editable 路径、全量期间其他写入影响结果。本轮没有重装环境，导入直接落主目录。
5. **当前确实还有业务问题，但已经不是“没有接线、没有跑任何东西”。** 最新真实归档已经走到建模阶段，尚未端到端完成。

当前 case 的直接证据：

- [校正 output](../../../case_tests/e2e_tests/sm25-L_anchor/run_win_e2e/1_correction/attempts/001/output.json) 中 `windows` 长度为 **31**。
- [建模 checks](../../../case_tests/e2e_tests/sm25-L_anchor/run_win_e2e/2_modelling/attempts/001/checks.json) 中 `kernel.pairing_gate` 失败：两张配对面最短边约 **0.065 m**，当前门要求至少 **0.1 m**。
- 该 run 没有 `3_split_pairing`、`4_mep`、`5_intakeoutput` 的已完成 attempt 检查，不能报告全链完成。
- 本轮只读扫描 [GT](../../../case_tests/test_baseline/gt/sm25-L_anchor/gt.json) 的外环，**280 个坐标分量中 8 个**不在整毫米格上，涉及 `15.9996` 与 `9.9999`。
  旧 memory 写“312”与本轮外环扫描范围不一致，本轮不照抄该总数。
- 这 8 个数只能证明 GT 自身有量化不一致，**不能据此推导它造成了 65 mm 薄片**。
  [旧溯源报告](../experiments/2026-09-08i_sliver_trace/README.md) 另有源图跨层约 60 mm 差异的证据与尚未确定的项，留待功能开发时核查。

本轮保留上述问题，不动 GT、不删除薄片、不放宽仿真检查来制造“跑通”。
