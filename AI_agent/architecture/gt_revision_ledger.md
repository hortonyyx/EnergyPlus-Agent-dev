> **它解的问题**（用户 2026-08-29 提出后暴露）：

## 一、三截结构

```
as_measured    机器从【未经手改的原图】量到的        ⛔ 永不修改
     +
revisions      ⭐ 人签的每一条修订（原值→新值→理由→签字）  ← 清单上一项项签的产物
     ‖
as_signed      = as_measured 应用 revisions            ⭐ 机械派生，⛔ 不手写
     ↓
  派生器 → 形式 A 多边形 / 形式 B 多边形 / reading 题目册 / 净空面积表
```

**四件事一次解决**：**忠实性**（`as_measured` 一字不动）· **可修**（修正是显式记录，⛔ 不是暗改 DXF）·
**可追溯**（每条带理由与签字）· **确定性**（`as_signed` 机械算出，不是人手填）。

⭐ **这就是「两层 gt」该有的样子** —— 修正前 / 修正后是**同一份数据的两个视图**，
⛔ 不是两份要各自维护的图。用户 08-29 撤销「两份图」撤对了；那两层本身是对的，它们该长在这里。
⭐ 并且它补上了跨家族审点名缺的东西（sol：「我没看到独立的**修订台账**」）。

⛔ **判分仍然只用 `as_signed`**（与用户「gt 只有一层、入库即修正后」一致）；`as_measured` 是**来源记录**，⛔ 不是第二个判分参照。

## 三、一条 revision 长什么样

```jsonc
{
  "id": "rev-001",
  "target":  { "kind": "wall_line", "floor": "F1", "axis": "y", "f0": 159400, "f1": 160600 },
  "finding": { "check": "cross_floor_misaligned", "magnitude_mm": 60.0,
               "detected_by": "consistency_v1",
               "detail": "F1 中轴 16.0000 这堵墙，F2 同位墙在 16.0600（差 60 mm）；两条墙带重叠" },
  "verdict": "drawing_error",
  "action":  { "kind": "translate", "axis": "y", "delta_0p1mm": 600 },
  "reason":  "二层同位墙在 16.00/16.12，一层这段整体低 60 mm；两层其余三段完全对齐 ⇒ 判为画图手滑",
  "signed_by": "<user>", "signed_at": "2026-08-30T..."
}
```

### ⭐ `verdict` 三种出口（= 清单的处置口，⛔ 缺一不可）

| verdict | 含义 | 产出 |
|---|---|---|
| **`drawing_error`** | 图画错了 | 带 `action` ⇒ **改 `as_signed`** |
| **`as_designed`** | 本该如此 | ⛔ **不改几何**，但**记账** ⇒ 下次不再问同一处 |
| **`producer_defect`** | 不是图的错，是**工序缺守卫** | ⛔ 不改几何 ⇒ 产出一条**缺陷登记草稿**（进 plan.md）|

⛔ **`producer_defect` 这个出口不能省。**实证：F-96 那根 0.03 m 碎片，
「图画错了」与「切分工序在 0…0.1 m 窗口内必出碎片」**两者同时成立**；
只签 `drawing_error` 会让碎片消失、看起来解决了，而**下一栋楼里一个真实的 0.06 m 设计错位照样崩**。

## 四、⭐ 与 reading 容差的联动（⛔ 这是一道门，不是纪律）

reading 看的是**截屏图**（= 原图），题目册从 `as_signed` 算。
⇒ 人签了「拉回 16.00」而截屏图上还是 15.94 ⇒ **忠实的 reading 会读出 15.94**。

**今天不咬人是运气**：60 mm < reading 位置容差 **80 mm**（`POS_TOL_M`）。

⇒ **落库时必须逐条比对**：
```
magnitude_mm  <  reading_pos_tol_mm   ⇒ 无害，照常
magnitude_mm >=  reading_pos_tol_mm   ⇒ ⛔ 响亮失败，必须二选一：
                                          (a) 改原图、重出截屏（则该修订消失）
                                          (b) 显式登记为 reading 的免罚项（进 as_signed 的免罚集合）
```
⛔ **不许默默穿过去** —— 否则 reading 会**因为画对了而挨罚**。
⭐ 用户原来提「两层 gt」担心的正是这件事；它没消失，只是搬进了这里，而且现在有**可计算的触发条件**。

## 五、签字流程（= 用户 08-29 定的第 4、5 步）

```
1. 转换器跑 source.dxf ─────────────→ as_measured.json
2. 一致性检查（⛔ 无阈值·互为最近邻）─→ 清单
3. 复原式渲染（⛔ 只照搬不推导）────→ 标注图
   ──── orchestrator 反复空跑到清单稳定，⛔ 不占用户时间 ────
4. 【预览】用户只判「检查类别够不够」，⛔ 不签字
5. 【正式签】用户逐条判 drawing_error / as_designed / producer_defect ─→ revisions.json
6. 机械派生 ────────────────────────→ as_signed.json →（选形式）→ gt.json
```

⛔ **第 4 步与第 5 步必须分开**。实证：同一个一致性检查 orchestrator 连错三版
（面线比面线 625 条 → 墙比墙仍爆炸 → 互为最近邻 1 条）；
**尺子没定型就请人签，同一处会被叫去签三遍，而且每次清单还不一样。**

## 六、为什么 `as_signed` 要落盘（而不是每次现算）

⭐ 因为**判分器要读它，而且要能对它做哈希与信任根**。
⚠️ 但落盘就有不同步风险 ⇒ **配一道可复现门**：

> **`as_signed` 必须能从 `as_measured` + `revisions` 逐位重算出来**，不一致 ⇒ 响亮失败。

⭐⭐ 并且这条顺带解掉 **F-130**（两把尺子代码版本不同步）：
今天 reading 的题目册是**现跑转换器**算的、correction 的 gt.json 是**冻在盘上**的
⇒ 一改转换器只有一边动。**事实层一落盘、两把尺子都从它派生，就一起冻住了。**

## 七、信任根

| 层 | 信任根 |
|---|---|
| `as_measured` | `source.dxf` 哈希 + `request` 哈希 + **转换器实现指纹**（⛔ 后者正是 sol 的 **B1** 要解的，未解）|
| `revisions` | ⭐ **人的签字**（逐条 `signed_by` / `signed_at`）；整份 revisions 的哈希**进 `as_signed` 的派生键** |
| `as_signed` | ⛔ **无独立信任根**（它是派生的），⭐ 但**必须可复现**（§六那道门）|

## 十、⭐⭐⭐ 2026-08-28 用户拍板：**`as_measured` 从 as-received 图出**（sol B3 的裁定）

| 文件 | sha256 | 是什么 |
|---|---|---|
| `sm25-L_t3_as_received.dxf` | `4a949224…` | ⭐ **真正未经手改的原图** ← **`as_measured` 从这份出** |
| `sm25-L_t3.dxf` | `1251f651…` | 签字前**修过 5 条线**的版本（`13AD 13AC 13AF 160A 13AE`，最大移动约 **6 mm**）|

⇒ **代价**：要在 as-received 图上**重跑一次转换器**。
⇒ **收益**：`as_measured` 名副其实；「授权」与「原始观测」按 sol B3 的要求**分名**；
   与三截结构自洽（`as_signed` = 今天签字件所代表的东西，可**逐位复现**）。

⛔ **不选「就从签字图出」** —— 那等于把一次人工修改**烤进历史**，
与 08-29 否掉「`as_designed` 记账后从清单里删」是同一个理由。
⚠️ 那时该层也必须按 sol 的要求**改名** `ReviewerNormalizedFactsV1`，
并**删掉文档里所有「忠实保留图纸偏差」的承诺** —— 代价比重跑一次转换器大得多。

### ⭐ 与 §四「reading 容差联动」那道门的关系

那 5 条线最大 **6 mm** ≪ reading 位置容差 **80 mm** ⇒ **该门放行**，⛔ 不触发「响亮失败」。
⚠️ 但**必须逐条跑那道门**，⛔ 不许因为"知道它小"就跳过 —— 门的价值在于**下一份图不一定这么小**。
